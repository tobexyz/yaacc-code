# YAACC Changelog

## [Unreleased]

### Added
- Sendspin: this phone as a player can also be a display (three switches, off by default): metadata (title, artist, album, progress), artwork (the album cover) and color roles, shown full screen with *Open the display* in the gear of the phone's card
- Sendspin: the app sends FLAC to a player that lists it before PCM (about half the bandwidth), with its own FLAC encoder
- Sendspin: pairing with a code (CPace): a player that offers a dynamic code (digits or QR) or a fixed 8 digit code can be paired with *Pair with a code…* (the code is a password for the key exchange and is never sent); this phone as a player offers it too (*Open pairing window* in the gear of its card, code shown as digits and QR code)
- Sendspin: a discovery report with a *Copy report* button in the lists of players and servers (switches, Wi-Fi, multicast lock, what was browsed and reported, devices known), as the FCast and Snapcast settings have
- Sendspin: the cover of what a Sendspin server plays is the soft background of its card (and of the merged card of a YAACC phone), not only in the server's sheet
- Sendspin: one card per YAACC phone: the player and the server of the same phone are joined by an id in both announcements; the gear of the player's card has *Remote control of this phone*
- Sendspin: the YAACC server offers the controller role: other Sendspin controllers (another YAACC phone, or any client of the protocol) see what plays (title, artist, album, progress, cover) and control it (play, pause, stop, next, previous, volume, mute, repeat, shuffle, seek, switch group); only paired devices, or all with *Allow unpaired devices to use this phone* (one setting for all roles); *Add a device by its pairing token* in the settings (text or QR code); group volume follows the protocol's rule
- Sendspin: groups are easier to read: the leader's card names its members, a member (also the card of this phone) says whose group it plays in, and members are listed directly under their leader
- Sendspin: the phone itself can be a member of a group: the link sheet of another player lists the card of this phone, so that the music plays on both in sync (the app's own hub dials its own player over the loopback address, no pairing needed for it)
- Sendspin: the pairing token of the phone as a player can be shown as a QR code (*Show QR code* on the token screen, which now blocks screenshots); and a *Scan QR code* button in the dialog that enters a player's token (camera permission asked only when it is tapped); uses the ZXing library
- **The phone as a Sendspin player** (#325, experimental, **off by default**): *Settings* > *Sendspin* > *Let servers play on this phone* starts a service with a notification that listens (port 8928) and announces the phone on the local network (`_sendspin._tcp`), so that Music Assistant or another Sendspin server can play on it. One server plays at a time, by the rules of the specification for several servers (the playback activity ranks first, an equal activation displaces the holder, the server that played last is remembered, a connection that does not activate within 30 seconds is dropped), plus one rule of this app: an unpaired server can not displace a paired one that plays; at most 3 connected; local network addresses only. The stream plays through the engine of the phone's Snapcast client (exact start, drift correction without a change of pitch), PCM 16 bit stereo at 48000 and 44100 Hz, or FLAC (checkbox *Prefer FLAC for the phone as a player*, off by default: PCM is offered first); the volume, mute and output delay of the server are kept. Servers that are not paired may play only with the checkbox *Allow unpaired servers to play on this phone* (its own switch, **off by default**); the gear of the phone's card has the pairing token for the others. Tested with a fake server and a simulated output; **not tested on a phone or with Music Assistant.** The receiver list has a card of this phone as a player (what it does, volume and mute, a gear with the connected servers and the switch-off). Not yet: Opus, dialling a server from the phone. The FLAC decoding on the phone was not heard with a Sendspin server (the stream and its header from the reference server arrive and are taken by the engine).
- **Pairing with Sendspin servers as a client** (#325, experimental): a server that demands pairing (or one you want to know who it is) can be paired with this app. The gear on the card of a Sendspin server (or *Pairing…* in its sheet) shows the pairing token of this app (`SP:...`) with *Copy token*, *New token*, *Connect again* and *Forget pairing*; the server's operator enters the token in the server. YAACC then runs the Pairing PSK flow of the protocol (`client/pair-init`, `client/pair-finalize`), takes the server's re-handshake as the responder and keeps the long-term key of the server (up to 8 servers, in the app's private storage, not wrapped by the Keystore yet); later connections use it. Tested with a fake server using the real handshake code; not tested with Music Assistant.
- **Linking Sendspin players into a group** (#325, experimental): the card of a Sendspin player has a link button that opens a sheet with the other players and a tick each; the ticked players play together with this one in sync (one queue, one stream, one timeline of timestamps, one common PCM format). The card you opened leads: its slider and mute symbol are the group's (every player moves by the same number of points; the card shows the average), the other players' cards say "in the group of ...", and playing to a member plays to its group. Every player that is found can be linked (linking approves it, as playing to it does; a player that needs pairing first is refused), at most 8 players per group. A member that drops out comes back by itself; groups are not kept across a restart; a player linked while a single player already plays joins at the next play. Tested with fake players on a simulated clock (the shared timeline, a late join, a member with a small buffer, a failing member, seek, pause); not tested with several real players.
- **Older Sendspin players without encryption, and a server that players can find** (#325, experimental, two switches, **both off by default**): *Settings* > *Sendspin* > *Allow players without encryption (less secure)* lets YAACC speak the older, unencrypted version of the protocol (the reference library calls it "transition mode"; it is not part of the specification YAACC implements) with players that know nothing else, for example the Kodi add-on. *Let players find this phone (listen on the network)* makes the phone announce itself on the local network as a Sendspin server (mDNS `_sendspin-server._tcp`, port 8927) and accept connections from players that look for a server (the add-on does, it never connects by itself); it listens and announces only while a page with the receivers is open and only while *Use Sendspin players* is on, accepts only addresses of the local network and at most 8 players at once. The two are independent: with the listener alone only players that speak the encrypted protocol connect, with the first alone you can add such a player by its address. **Nothing an unencrypted player sends or receives is protected, and the connection does not prove who the other side is: anyone on the network can read it and pose as the player or as the phone.** A player you have not approved gets no audio (playing to it is the approval, as before); a player that connected to the phone is listed while it is connected and has to connect again after a break (YAACC does not dial it). Built from the add-on's own code and the reference library's behaviour and tested with a simulated player in unit tests; **not tested with the real Kodi add-on or on a phone.** Also: the test rig's `run-local.sh` takes `RIG_SERVER_ARGS` (for example `--allow-unencrypted`).
- **Sendspin players as receivers** (#325, experimental, off by default): YAACC can play the music of its queue to players of the Sendspin protocol (Music Assistant, ESPHome and others). *Settings* > *Sendspin*: the switch *Use Sendspin players* (off by default), the switch *Find Sendspin players* and the list *Sendspin players* (add by address, at most 16). The players appear among the receivers with their name, address and state; the sound goes to the player and the phone stays silent; the volume and mute of the card are the player's. The server role speaks the protocol in plain Java: WebSocket, the Noise `KKpsk2` handshake with both cipher suites (Bouncy Castle 1.87 for X25519 and ChaCha20-Poly1305, which the platform lacks on Android 8), timestamped PCM chunks at a fixed lead with the player's buffer limit, `stream/clear` on a seek and `stream/end` on a pause. YAACC declares the playback activity only while it plays to a player, so it does not take a player from another server (Music Assistant) by merely being connected. A player that is not approved gets no audio; playing to it approves it (unpaired access; the protocol says such a connection is not authenticated). A player that accepts only paired servers is paired with its **pairing token** (the text starting with `SP:` that the player shows): tap its card, paste the token; YAACC checks that the token belongs to that player, runs the *Pairing PSK* flow of the protocol (pair-init, pair-finalize, then a new Noise handshake under the long-term key it received) and uses the long-term key from then on, without a token. A player that forgot the server is shown as such and can be paired again; *Settings* > *Sendspin players* lists the paired and the approved players with a button to remove each. The tokens and keys are kept in the app's private storage (not yet wrapped by the Android Keystore). Tested with the reference player of the project in a test rig (`tools/sendspin-rig/`): the player's own sync error converges to 0 ms in about 25 seconds and stays within about 3 ms; not yet tested on a phone with real players. Players are found by **mDNS** (`_sendspin._tcp`) while a receivers page is open (*Find Sendspin players*, on by default but only while Sendspin is on; only local network addresses are accepted) or added by address. **Not yet:** pairing with a code (dynamic or static pairing code), groups and linking, FLAC and Opus, the phone as a Sendspin player. Not affiliated with the Open Home Foundation; Sendspin is its trademark. See the documentation, section *Sendspin*.
- **Controlling Sendspin servers** (#325, experimental, off by default): *Settings* > *Sendspin* > *Control Sendspin servers* and *Sendspin servers* (add by address, at most 8). A server such as Music Assistant appears among the receivers as a card that shows what plays (title, artist) and controls the group of this phone on that server: play, pause, stop, volume and mute on the card; previous, next, seek, shuffle, repeat and the switch of group in a sheet. The phone connects out to the server (no listening socket) with the roles controller, metadata and artwork: the sheet shows the cover the server sends (a 512 by 512 JPEG over the same connection, nothing is fetched from a web address). Servers are found by mDNS (`_sendspin-server._tcp`, *Find Sendspin servers*, on by default while the controller is on, local network addresses only) or added by address. Pairing as a client is not supported yet (*Allow unpaired servers*, on by default); tested with the reference server of the project, not with Music Assistant or on a phone. YAACC also declares the playback activity to a player only while it plays to it, so it no longer takes a player from another server by merely being connected.
- **Live streams from the card "Play from this device"**: the card has the two live stream buttons of the server card (device audio and screen cast, Android 10 and newer). A tap sends the live stream of this phone to a receiver, as the other content of this card: the receiver list opens (a screen cast is offered to receivers that show video) and, after you confirm, the receiver gets a short-lived link of its own (the address works only for the receivers you chose and ends with the play, like a shared file). It needs neither the *UPnP server* switch nor the media provider; the capture of the device audio or of the screen starts for the link and stops when it ends, and the system asks for its permissions first when they are not there (recording and screen capture, as for the server card). The stream switches of the server card are not changed. If the server serves that stream already (the *UPnP server* switch, the media provider and the stream button of the server card are on) the receiver gets the same link as the server's *Live Streams* folder. **Limit:** the screen cast is MJPEG; the FCast desktop receiver (3.0.4) does not play it, with the server's link nor with this one (the device audio plays); other receivers were not tested.
- **FCast receivers** (#327): YAACC is an FCast sender (protocol versions 3 and 4). *Settings* > *FCast* has *Find FCast receivers* (mDNS, **on by default**, not authenticated; searches only while a receiver page is open) and the list *FCast receivers*. A receiver is added by an address, by the name of the device, by a pasted connection link (`fcast://r/...`) or by opening the QR code of a receiver with the camera app of the phone (a dialog shows what will be added, nothing is stored before *Add*; no camera permission). The addresses of a link on the phone's network are tried first, all at the same time. Each receiver is a card with its state, the volume and a gear that opens a settings sheet (device, volume, mute and speed while a player plays, stop, connection check, trace, remove). Music, video and pictures play to a receiver with your queue, play, pause, stop, seek and volume; the next item starts when the receiver reports the end. Not supported: a playlist on the receiver, grouping. Version 3 is neither encrypted nor authenticated, and the receiver gets the full address of every item. This application is an independent community implementation of the FCast protocol, not affiliated with FUTO; FCast is a registered trademark of FUTO. See the documentation, section *FCast*.
- **FCast version 4** (#327): on Android 10 or later YAACC speaks the encrypted FCast protocol version 4 (TLS 1.3, FlatBuffers) to a receiver whose key it knows: from the connection link of the receiver (the QR code; the strong source, the key is stored with the receiver) or from its announcement. A key that does not match is an error, never a fall back to version 3; a receiver added by its address or name, and Android 9 or older, stay on version 3. With version 4 the settings sheet shows the audio and subtitle tracks, *Add subtitle file* (a web address) and what the receiver can play, and says where the key came from. The FlatBuffers runtime `flatbuffers-java` 25.2.10 (Apache-2.0) is a new dependency.
- **Volume keys with an FCast player** (#327): with the player screen of an FCast receiver in front, the hardware volume keys change the receiver's volume (5 percent per press) instead of the phone's. On the receivers page the keys change the volume of the one active player that plays to a receiver (a short message shows the new volume); with no active player, several, or one that plays on this phone, they stay the system's.
- **A test receiver for FCast** (#327): `tools/fcast-rig/` is a small receiver for development (announces itself by mDNS, logs what it is sent, answers like a receiver, no media player).
- **Control of Snapcast servers** (#319): Every group of a Snapcast server (a server you added by address, or found by the search, see below) appears among the receivers with its server address, stream, connected clients and volume. The slider and the mute symbol of the row (the symbol of the other receiver cards) are the group volume (the average of the connected clients, moved by the same number of points) and the group mute; the link icon (as on a MusicCast row) opens a sheet to link clients to the group and unlink them (a group keeps at least one client); the settings button opens a sheet with the stream of the group and the clients with their volume, mute symbol, name and latency (0 to 10000 ms); the hardware volume buttons change the volume of the Snapcast group that has the focus or was touched last, on the receivers page (default and classic layout) and in the device sheet (5 points a press, the up button unmutes a muted group; otherwise they change the phone's volume as before). The rows follow changes that another controller makes on the server. No login is supported. What is stored, on the phone only (YAACC takes part in no backup): the server addresses you typed in, the receivers you selected, the address of a discovered server that holds a selected group, and, once the play option was used, a random marker of the stream name. Tested on the author's devices with a snapserver. Description in the documentation under "Snapcast".
- **Settings for Snapcast** (#319): *Settings* > *Snapcast* has the list *Snapcast servers* (add a host name or address with an optional port, at most 16, no credentials; remove) and the checkbox *Find Snapcast servers*, which is **on by default** (also for an installation that never changed it): it sends mDNS queries on the network while the receivers are shown (also on the first screen of a fresh install) or the server list window is open, and the receivers page contacts every server that announces itself. Announcements are not authenticated (any device in the network can announce a server); clear the checkbox in networks you do not trust.
- **Play music to a Snapcast group** (#319): The checkbox *Play to Snapcast groups* (**on by default**; an installation that stored "off" keeps it off; tested on the author's devices with a snapserver) lets YAACC play music to a group: it adds a TCP stream to the snapserver while it plays (`Stream.AddStream`, the audio is raw PCM at 48 kHz, 16 bit, stereo, sent in real time), puts the group on it and gives the group its previous stream back afterwards. If the server does not take the stream, the message adds that the server must allow adding a TCP stream source at run time (when every stream port is in use, or a stream with YAACC's own name is configured differently, the reason in brackets is the cause, not the hint). The clients play about one second behind the display (the buffer of the server). Music only (the "Play on…" list does not offer a group for images and videos), one group per server at a time. The audio goes unencrypted to the address of the server, and the stream name carries the name of the phone. A Docker test rig for development is in `tools/snapcast-rig/`.
- **Media renderer output: play into a Snapcast group** (#319): *Settings* > *UPnP server* > *Output* (under *media receiver service*) chooses where the YAACC renderer (the one other apps and UPnP/OpenHome controllers play to) plays: *This device* (the default, as before) or *Snapcast group*. With the group the renderer only feeds the group you chose under *Snapcast group* (first the server from the server list, then one of its groups, read from the server); this phone stays silent, nothing is added to the group (which clients are members is your choice, in the link sheet of the group) and the phone does not become a Snapcast client. The volume and mute of the renderer (RenderingControl *SetVolume*/*SetMute*, the OpenHome Volume service) are then the volume and mute of the group, and the volume the controller reads is the group's. A missing or unreachable server, a group that is gone, no group chosen, and video or images (a group plays music only) give a message on the phone and the controller sees *STOPPED*; nothing plays on the phone instead. Switching the output stops a running renderer play on the other output; the next play uses the new one. The renderer opens the connection for the audio only when a play is requested, and nothing changes while the output is *This device*. A damaged stored value falls back to this device with a note. **The audio goes unencrypted to the server; tested on the author's devices with a snapserver** (the same feed as the checkbox *Play to Snapcast groups*; choosing this output does not need that checkbox). The type of the content is read in one way everywhere (trimmed, lower case, without parameters), so a controller that writes `Audio/Mpeg` is treated as music and its Stop, Pause and Seek find the player. A flood of volume or mute changes from a controller becomes one coalesced change on the server (the mute of the group card in the app is coalesced the same way); a server that did not answer is not waited for again for five seconds, and the messages of refused plays appear at most every three seconds. The summary of the setting says that any device that can reach the receiver can change the volume and mute of the whole group. A content whose type is unknown (the controller sent none and the address has no known file extension) is refused with a message of its own. A controller's own volume or mute read, and the first subscription to the renderer's events, bring up the control connection to the server of the group (the idle close of the connection does not bring it back); the OpenHome renderer opens it once when it starts in group mode and when a play is requested, so the volume an OpenHome control point sees can be out of date until the next play. Anything on the network that can reach the renderer can change the volume and mute of the whole group (UPnP and OpenHome have no login), as it can already start a play there. In the app, the volume row of YAACC's own renderer is the group's volume in this mode; the hardware volume keys still change the phone's volume. Not done: audio focus, the pause when headphones are pulled, and a ramp of the gain.
- **Snapcast discovery report** (#319): *Settings* > *Snapcast* > *Snapcast servers* shows what the search browses and what the system reports (the switch, Wi-Fi, multicast permission and lock, the services seen per type with the system's failure codes, the servers listed, the last events) with a *Copy report* button, so that a server that does not announce itself can be told from one the phone does not hear. The report names the servers found and their addresses and carries the manufacturer, model and Android API level of the phone; the copy is marked as sensitive on Android 13 and newer.
- **The phone as a Snapcast client** (#319): *Settings* > *Snapcast* > *Snapcast client* (off by default) lets this phone play as a member of a Snapcast group, in sync with the other clients of the group: a foreground service with a notification connects to the stream port (1704) of a server and plays the stream. It plays **PCM and FLAC**; a server that sends Opus or Vorbis is refused with a message (those codecs are a possible future enhancement). The phone estimates the server's clock, places every chunk at its time (the server's buffer, one second by default, minus the latency) and keeps the output there by exact padding or skipping at the start and by dropping or repeating single frames (no change of pitch) while playing; the output keeps about 250 ms of audio queued (a field of 40 to 350 ms in the details, raised by itself in steps of 40 ms when the platform reports that the output ran short). The wake lock and the Wi-Fi lock are held only while it plays (plus a minute of grace), a session without audio for 15 minutes ends by itself, and a session never ends silently: the state, the reason of the last end and a *Stopped: reason* notice say why. The entry *Snapcast client details* shows the connection state, the numbers of the sync, what the server says about this client, a *Move my group to a stream* button (a client that connects gets a group of its own on the server's default stream) and a trace that can be copied for a report. **Limits:** how well the sync holds depends on the phone and on the Wi-Fi (the output latency the phone reports, Wi-Fi power saving and Doze, the output's buffer, a Bluetooth route needs the latency field; from Android 14 no Wi-Fi lock works with the screen off); no audio focus, no pause when headphones are pulled, no ramp of the gain; audio and control are unencrypted; a server with a login is not supported; FLAC is decoded by the phone's native decoder. It was heard on one phone with a snapserver; no measurement against other clients over a long time exists. The Hello that the server shows in its client list carries the name of the phone (the generic *YAACC* for a public address), generic program and system words, and a version text made of the name of your YAACC server and the app version, for example *Yaacc 6.1.0* (*YAACC 6.1.0* for a public address; cleaned, at most 40 characters). The client details sheet has a field for the server's address and *Choose server*, which lists the known servers (typed in, remembered, found, and the one used last; the address first, then the name the server gave itself; a server that was only found on the network is never filled in by itself). The three entries in the settings are *Snapcast client* (enables the feature), *Connected to the Snapcast server* (the state, below) and *Snapcast client details*.
- **Power button on the cards of MusicCast and OpenHome devices** (#319): a device that supports power has a power button in the title line of its card (MusicCast: `power` in the features of the main zone; OpenHome: the Product service has *Standby* and *SetStandby*). It shows the state aloud ("On", "Standby", "State unknown"), reads the device again first when tapped and then does the opposite of what the device says, reads it once more, and says why when it could not (no answer, no state, refused). A MusicCast card follows the device's events; an OpenHome device is read every ten seconds while the receivers are shown. The app's own OpenHome renderer and the phone's own Snapcast client have one too (see below); other Snapcast clients and groups have none, because Snapcast has no way to switch another device on or off.
- **Snapcast groups as sources of the OpenHome renderer** (#319): the source list that an OpenHome control point sees for YAACC's renderer has, next to *Playlist* (this device), one source per Snapcast group the app knows (at most 16, by name). Choosing one sets the same *Output* setting as the settings screen (and the settings screen, or another controller, changes the source the controllers see); a group that vanished is refused with a message and the output stays as it was. The renderer does not connect to a server to fill the list: only the groups the app has read since it started are listed. Any device in the network that can reach the renderer can already set the output; this adds that it can choose among the groups of your servers that the app knows.
- **Remove an offline client from a Snapcast server** (#319): the menu of a client in the group sheet has *Remove from server* for a client that is offline, after a confirmation. The app reads a fresh status first and never removes a connected client, a client that is not in the status any more, or the client of this phone's own Snapcast session. A client that was once seen under another id (a reinstalled phone, a client that came under another address) stays on the server for ever as an offline entry; this is how to clean them.
- **The phone's own Snapcast client: a switch, a power button, one id, a server rule** (#319): (1) With the option *Snapcast client* checked and a server known, the first page has a row *Snapcast client* above the *UPnP server* switch, built like it (label, switch, and a gear that opens the settings at the entry *Connected to the Snapcast server*); the state in words and the reason of an ended session are read aloud with the switch and shown in the details, a refused start is a message when you tap. The same choice is the checkbox *Connected to the Snapcast server* in the settings, *Start*/*Stop* of the details, and the power button of (2). Switching on checks the option and the server again and starts the client; a refusal is shown with its reason and the choice stays on. Only your own off clears it (not the exit, the shutdown timer, the idle close or the end of the process). When the app starts, a client that was on is started again (once per process; also when a reboot with *autostart server on boot* checked created the process; not right after the exit button; not while the last end is a failure you have not seen yet; a start that Android refuses in the background is tried once more when you open the app). (2) The Snapcast group card whose first member is the phone's own client (and its row in the group sheet, labelled *This phone*, also as an offline entry) has a **power button**: on while the client has a session, a tap switches it on or off (off disconnects it); no other Snapcast card has one. (3) The client uses **one client id for all servers** (derived from the install secret only, no hardware id), so the app recognises its own client in any server's status; any server can recognise the phone and two servers can tell they saw the same phone, the disclosure texts say so. (4) The client connects to the server it was **last connected** to, else the **first known** server; the menu of the own row has *Server* (all known servers, the current one marked; another one restarts the session while the client is on). No automatic failover; only the host is used (stream port 1704).
- **Power button on the card of the app's own OpenHome renderer** (#319): when the renderer is on in OpenHome mode, its card in the receiver list has the power button of the other OpenHome cards. It shows the same state as the power switch in that renderer's OpenHome settings (the *Standby* state of its Product service) and a tap does what the switch does: standby stops the playback and keeps the queue. The card follows a change of the switch, of a control point or of a play at once, and the switch shows what the card did. Only that card has it.
- **A Snapcast client is listed once** (#319): a client that is known to several servers (the phone, whose client id is now the same on all servers, or a device that moved) is shown on the server where it is connected, else on the server where it was last seen (`lastSeen` of the status; the first server on a tie). Its offline copies on the other servers are left out of the group cards, the group sheet, the link picker and the counts, and a group card with no client left to show is not listed. The link picker lists only the clients the sheet's server shows. This is a view only: nothing is removed from a server and a client that is hidden stays in its group when you link or unlink the others.
- **The phone is listed once, also with its old Snapcast entries** (#319): builds of this branch before the one id gave every server its own client id for the phone and left an offline entry on each server, so the receiver list could show the phone twice (a card with its current entry and another card with an old one, and old entries as members named *Yaacc* in other groups). The app now computes those old ids again from the secret of this installation and treats them as this phone: it is shown once (connected, else last seen), the other copies are left out of the cards, counts and member lists (display only: nothing is deleted or dropped from a group by it), and the *This phone* label and power button also recognise them. The menu of the phone's own row has *Remove old entries of this phone* (only when the server has offline ones; confirmation with the count; connected entries, the current id and other installations' entries are never removed). Entries of other YAACC installations stay visible.

### Fixed
- Sendspin: the gear sheet of a connected player that is not paired offers *Enter pairing token* even when the player accepts unpaired servers, so a pairing can be tested or made on purpose
- Sendspin: the texts of the pairing dialogs now say where a token comes from and where it goes: the token of a player is shown only on that device (card of this phone, gear, Pairing token) and is entered on the other device, in the card of that phone
- Sendspin: a connection to the optional server listener that is no player (for example the controller of another YAACC phone) no longer shows up as a receiver card with "no usable format"
- Sendspin: when a pasted pairing token belongs to another player, the message now names the short key ids of the token and of the player, and the token screen of the phone shows its own key id, so a token copied from the wrong device is easy to spot
- **Sendspin, after the second review** (#325): a player that lists a sample rate the streamer refuses (11025 Hz) no longer crashes the app (the rate is skipped); a stream that is stuck in a write breaks only the member that is stuck, not the whole group; stopping within seconds of starting no longer starts the player later; a player that connects to the phone keeps its card and links when it comes back from another port; the stream is never sent at another rate than the one the audio was converted to; a player that gave no buffer size no longer stalls the stream; the slot of a listener that throws is given back once; the disconnect button of the phone's card can no longer hit the wrong server; the phone as a player has its own switch for unpaired servers (off by default).

- **Fast clicks on the play / pause button of Home Assistant no longer give an error** (issue #296): A second Pause that met the already paused renderer was answered with UPnP error 701 ("doesn't support signal 'pause'"); Pause while paused, stopped or idle is now accepted and changes nothing. Seek while paused moves the position and keeps the pause, Next and Previous while paused are accepted and do nothing (they were listed as possible actions but refused).
- **A music track without a cover no longer shows the app logo** (issue #296): The server's music lists (all titles, albums, artists, genres) gave every track a cover address, and for an album without a cover the server sent the YAACC logo, so the logo appeared in front of some tracks and a generic music icon in front of the others. Such tracks now get the music note symbol of the app (a small gray picture with a transparent background) and the picture is sent with a one day cache header, so a control point can keep it; a cover that exists is sent as before. Photo thumbnails are unchanged.
- **Browsing a SAF folder with thousands of files no longer times out in Home Assistant** (issue #299): A folder with 5570 files took 6.8 s to build and more to write (Home Assistant waits 5 s and then reports `UpnpConnectionTimeoutError`). The time went into work that was done again for every file: looking up the device's IP address (it lists the network interfaces), asking the system for the read permission of the file, and, with a cold SAF cache, one lock and one cache write after another. Now the address is looked up once per Browse, the permission once per folder (a file is still asked on its own when the folder itself is not readable), the cache is read and written in one go, the duration preload waits while a Browse is answered, and a big answer (300 entries and more) is written without the DOM and XML transformer. The answer is the complete list with the same ids and content as before. The debug log shows where the time goes: `SAF browse ... (permissions ..., metadata ..., ip ..., items ...)` and `CDS didl <n> items <bytes> bytes in <ms> ms`.
- **New files and folders in a shared SAF folder show up by themselves** (issue #299): Files and sub folders that appear inside an added SAF folder (a torrent that downloads a folder tree into it, a copy from a computer) were served after at most 30 seconds, but UPnP control points that keep the listing they have (VLC, BubbleUPnP, Kodi, Windows, Home Assistant ...) were never told, so you had to remove and add the folder again. The server now checks the shared SAF folders (and the folders a control point browsed in the last 15 minutes) every 30 seconds while it runs and a SAF folder is shared, and tells the subscribed control points when something changed (a new *SystemUpdateID*, at most once every 15 seconds; many changes are one message). Nothing runs while no SAF folder is shared. The size shown for a file is the one the folder listing has now, not the one from the first time it was seen (a download that was still growing). Ticking or unticking a shared folder in the server settings tells the control points too (one change per action, also when a folder is added).
- **Content that changed while the server was stopped is announced after a start** (issues #298 and #299): The content directory started its *SystemUpdateID* at 0 on every start, so a control point that last saw 0 kept showing its old listing although files had been added or removed while yaacc was not running. The number now starts with the current time in seconds, so every start has a higher number than the one before and the control points look at the content again. There is no setting for it.
- **A client that hangs up is no longer an error in the log** (issue #299): When a control point (seen with Home Assistant) closes the connection while the server is still answering, the log had an error with a 35 line stack trace (`Broken pipe`). That is normal, so it is one debug line now (`client disconnected: ...`). Other connection errors are unchanged.
- **The `Date` header of the server is a correct HTTP date** (found while testing #294): The HTTP library wrote the date of its answers in the language of the phone (`So., 01 Nov. 2026 17:55:36 GMT+00:00` on a German phone), and the answers of the UPnP protocol (SOAP, events) carried the time as a plain number. Both are `Sun, 01 Nov 2026 17:55:36 GMT` now (English, GMT), as HTTP and strict clients expect.
- **Ranged answers of large files** (issue #294): A request for a part of a local file above 50 MB (or a part above 50 MB), as VLC does for an MP4 whose index is at the end, got a body that was cut short at a multiple of 8192 bytes and a connection that never ended, until the player timed out. The answer is now complete and ends at once. Thanks to maitelorf, whose analysis of the cause and proposed fix this is based on. The same check was made for shared (SAF) documents: a start position is now reached even when the provider skips less than asked, and a chunk that a slow client did not accept is no longer dropped. `bytes=0-0` is the first byte only, an end beyond the file is cut at the file end, and `Content-Range` names the bytes that are sent (also for a suffix range).
- **Ranges that cannot be served and ranges of smaller files** (issue #294): A range request that selects nothing (a start at or beyond the end of the file, `bytes=-0`) is answered with `416 Range Not Satisfiable` and `Content-Range: bytes */size` instead of a `206` with an empty body. Files up to 50 MB are now streamed like the big ones: before, their ranges were one byte short of the announced `Content-Range`, `bytes=0-0` returned the whole file and a start beyond the end caused an error; and a `Range` header that cannot be understood (another unit, garbage, a huge number) is ignored (the whole file is sent) instead of causing a server error. The same applies to shared (SAF) documents, album art and thumbnails. A range request to a live stream is answered with `200` instead of `206` without `Content-Range`.
- **Home Assistant could not start music right after an announcement or a finished track** (issue #296): The renderer kept saying `PLAYING` after its player had played the playlist to the end (repeat off), was stopped with the stop button of the app or was closed, so Home Assistant, which acts on the last state it was told, skipped its *Play* for the next item (an announcement played, the music after it never started). The renderer now goes to `STOPPED` in all three cases, the same way it does for a *Stop* from a controller (state, the possible actions and the position update), and tells the subscribed controllers at once. A change of the transport state (or of the possible actions) is also no longer held back by the 250 ms pace of the events: a controller that sends *Stop* and *SetAVTransportURI* in a row and then looks at the state used to see the old one. Other changes (play mode, URIs, volume) keep the pace. The log (debug level) shows `AVT player ended: transport -> STOPPED` and `AVT event: TransportState=STOPPED (instance 0) sent to n subscribers`.
- **The repeat and shuffle settings say what they do** (issue #296): The settings *replay playlist* and *shuffle music* are called *Repeat for new players* and *Shuffle for new players* now, and their texts say that every player has its own repeat and shuffle buttons (a change at one player, also one from Home Assistant, does not change the others or the settings). The log says which play mode a new player starts with and, at every item change of the local player, the play mode (to find out why a player repeats).
- **Volume and mute in the receiver list follow the receiver**: While the device sheet (or the Receiver tab) is open, the volume slider and the mute box of this phone follow the system volume at once when Home Assistant changes it and within two seconds when the hardware keys change it (before, the local row always went back to 50 % on a status update), and those of the other receivers are read every few seconds (before, a change was only seen after closing and reopening the sheet; mute never). Nothing is read while the sheet is closed, a receiver that does not answer is asked less and less often, and a slider you are holding or just moved is not changed by a value that was read.
- **Volume and mute in Home Assistant**: The renderer's volume and mute were only answered when asked and never sent: Home Assistant (and any controller that relies on events) showed a stale mute state. YAACC now sends the volume and mute of the renderer to subscribed controllers, with the full state to a new subscriber and every change (from the controller, from the volume controls in YAACC, from the hardware volume keys and the system's volume panel) a fraction of a second after it happens. The system volume is only watched while a controller is subscribed. The log (debug level) shows `RCS event: Mute=... Volume=... (instance 0) sent to n subscribers`.
- **Server events**: A content directory that is browsed by a controller which is subscribed to it now gets a new *SystemUpdateID* when the shared folders are changed in the settings (it never changed before, so controllers kept an outdated listing), and no change is dropped by a rate limit any more. The connection manager of the renderer no longer has a missing (null) list of sink protocols.
- **Log full of `doSetTrackInfo` lines**: The renderer's position update ran several times a second and wrote a debug line each time, also when no player was active. Every new `SetAVTransportURI` while playing, and every Play, left another update running for ever. There is now one update, only while the renderer plays and a player is active, it writes nothing (and sends no event) when nothing changed, and its line is verbose level.
- **Two crashes**: The app no longer crashes when the network is lost while the kind of network is read (NullPointerException on the connectivity thread), nor when a music player is closed while its media session is being set up.
- **Unreachable event receivers are dropped**: A control point whose event callback cannot be reached is dropped after three failed deliveries in a row, instead of blocking a thread for the connect timeout on every event. It subscribes again when it renews.
- **Crash when an event receiver is unreachable**: A control point whose event callback address cannot be reached from the phone (for example Home Assistant behind a proxy) crashed the whole app after the 5 s connect timeout. A protocol that fails to reach its peer is now logged as a warning and the app keeps running.
- **Repeat and shuffle in Home Assistant**: Home Assistant (and any controller that relies on events) never got an event from YAACC's renderer: it was answered when it subscribed but the subscription was never established, so it showed a stale repeat and shuffle state whether the mode came from Home Assistant or from the buttons in YAACC's player. YAACC now establishes the subscription, sends the full state to a new subscriber and the changes (play mode, transport state, media URI) a fraction of a second after they happen, without ever holding up a command. The mode set from outside is also forgotten when the last player of the renderer is gone (the next playback starts with the settings again, and Home Assistant is told). The log (debug level) shows `AVT event: CurrentPlayMode=... sent to n subscribers` and `AVT SetPlayMode ... applied to n players`. `SetPlayMode` also accepts lower case and surrounding spaces.
- **Add to playlist while music plays**: Items added to the playlist of the music player on this device during playback are appended to the player at once (with shuffle at a random place behind the current song). Before, they were only played after the next start of a song.
- **Repeat and shuffle changed from outside**: When the system media controls, a Bluetooth device, the notification or a watch change the repeat or shuffle mode of the local music player, the buttons in the player screen and the renderer's *CurrentPlayMode* follow (before, they kept showing the old mode). The playlist dialog also no longer keeps a stale delete button position after an item was moved.
- **Repeated songs (Home Assistant)**: The local music player repeated a single song or a text-to-speech sentence for ever, whatever the setting "repeat playlist" said. It now follows the setting, and at the end of the playlist without repeat it stops and reports the stopped state to the controller.
- **Images in a SAF folder**: Tapping an image (or audio) in a folder that mixes images and videos, as SAF folders like DCIM/Camera do, queues only items of the same kind, so it opens in the in-app image viewer (or player) instead of the "open with" chooser of other apps.
- **Stop on an idle renderer**: A control point such as Home Assistant that sends *Stop* to YAACC's renderer while nothing is loaded no longer gets the UPnP error 701; the renderer just stays idle.
- **Device announcements after a network change**: After switching networks or coming back from sleep, the app's own announcements (alive messages of the local server/receiver) and the renewal of event subscriptions use the new network connection instead of the closed first one, and the local devices are announced again.
- **Crashes without a network**: Searching for devices, reading or changing a receiver's volume or mute, and controlling a player no longer throw an error when the network service is not up (for example right after a network change); the action is skipped or reported as failed instead.
- **Details of shared (SAF) folders and files**: Control points that ask for the details of a single shared folder or file now get its name, the right parent folder and the "[X]" mark; before, sub folders and files were answered wrongly or empty. An unknown item is answered with "no such object".
- **SAF metadata cache**: The durations and short ids of shared (SAF) files are kept in their own file and written in batches in the background, so indexing no longer rewrites the app settings for every file and the cache no longer slows the screen down when the app stops. Existing entries are moved over once; short ids stay valid.
- **Smoother content list**: Sorting a finished folder no longer blocks the screen, thumbnails are not loaded again when you scroll back, and the type icons are no longer rebuilt for every row.
- **Android TV remote control**: The action buttons of the content items (add to playlist, download, play, play all, share) can be reached with the D-pad: right from the item moves through the shown buttons, left moves back, and the focused icon button shows a ring.
- **Sub folders marked "[X]"**: Sub folders of a shared SAF folder are now checked and browsed through the permission of the folder you picked, so they are no longer marked "[X]" (no permission) although they are readable.
- **Server configuration**: The folder tree shows only folders (files could not be selected anyway), which also makes large folders load faster.
- **Shared folders screen with large folders**: The server configuration screen no longer freezes when you open a shared (SAF) folder with thousands of files or scroll through it: folders are read in the background in one query, rows no longer ask the storage provider while they scroll in, and all children are inserted at once. Every folder shows the expand arrow until it has been opened and found empty.
- **Large shared folders**: Browsing a shared (SAF) folder with thousands of files no longer takes longer than the connection timeout: the folder is read from the storage provider once and reused for the next pages, only the page that is shown is processed, and the app waits up to 30 s for the answer of a content directory request.
- **Requests to the app's server without a network**: A UPnP request (control, subscribe, event) that arrives while the app has no working network connection is answered with "503 Service unavailable" instead of an internal error, and the app's server uses the connection of the current network after a network change instead of the one it started with.
- **Durations of shared (SAF) files read twice**: The durations that the background indexing of shared files stores are now readable by the cache, so a file is no longer analyzed a second time when it is first listed; durations stored by older versions are taken over.
- **Details of a single object**: A control point that asks for the details of one folder or file (BrowseMetadata) now gets a total of 1, as the UPnP standard says, instead of the number of items in the folder, and the folder is no longer read for it.
- **Protocol handler accessors** (internal): The registry had two pairs of methods for the same protocol handler; one pair is removed. No visible change.
- **Short network drops while browsing**: A folder that cannot be read because the connection is gone is tried up to three times (after 0.5 s and 1.5 s) before it counts as failed, and a failed load no longer empties the list: what was shown stays, and when the network is back the folder continues to load by itself. Errors the server answers (for example an unsupported sort order) are not repeated.
- **Suspend and resume**: When the app comes back after the screen was off or it was in the background for a while, it checks its network connection, searches for devices again (if the last search is older than 30 s) and keeps the folder you were browsing instead of emptying it when the server is not found yet; the folder continues to load as soon as the server is back. Starting a playback waits up to about 5 s for a selected receiver that was lost meanwhile instead of refusing and forgetting the selection.
- **Sharing a file from a gallery on Android 15 and newer**: The share was turned away because the check of the sending app is answered "denied" when the file comes through the system share sheet. The check is only logged now; the system already makes sure that the sender can read the file it passes on.
- **Log viewer**: A pause button stops the automatic refresh so text can be selected and copied. The view no longer jumps while you scroll: it is not updated while you touch or scroll it (scrolling itself writes log lines), and an update keeps your scroll position. Once the system's log window is full and old lines drop off the front, only the new lines are appended (the whole text used to be replaced then, which sent the view to the top).
- **Shutdown timer in portrait** (new layout): The remaining time is shown under the title of the toolbar, so it is also visible on narrow screens, where the toolbar drops the text next to the timer symbol.
- **Receiver with several players**: When one receiver runs more than one yaacc player (e.g. an image show with background music), its row in the Receiver tab now always shows and opens the most recently started one that is playing (or, if none is playing, the most recently started one), instead of an arbitrary one.
- **Leaks**: The shutdown timer listener, the screen-capture stop callback and the share handler's worker thread are released when their screen goes away, instead of keeping the old screen alive. Browser screens that were destroyed also stop receiving device updates.
- **Shutdown timer state**: The Server tab now takes the shutdown timer's state (switch and remaining time) from the running timer itself, so it is correct whenever the screen is recreated or the layout is switched, and a destroyed screen is no longer kept alive by the timer.

## [5.4.0] - 2026-10-22

### Added
- **Sort by Name/Date (#252)**: Added a "Name"/"Date" sort toggle to the Content tab's folder header. Uses server-side UPnP `SortCriteria` (`-dc:date`) when the browsed server supports it, with a client-side fallback sort once a folder finishes loading for servers that don't. The Date option is disabled when a folder has no `dc:date` metadata at all. The chosen sort order is persisted across app restarts.
- **Server-side Sort Honoring (#252)**: yaacc's own UPnP/DLNA server now honors the `SortCriteria` other apps/devices send when browsing yaacc's shared media, instead of silently ignoring it. `GetSortCapabilities` now advertises `dc:title,dc:date` instead of an empty list, and a `Browse` request for `+dc:title`/`-dc:title` (name) or `+dc:date`/`-dc:date` (date) returns music, images, video, and SAF-backed folder results in that order across every content type the server exposes. A request for an unsupported sort property is rejected with `UNSUPPORTED_SORT_CRITERIA` rather than being accepted and ignored. Browsing without `SortCriteria` is unaffected and keeps today's existing order.
- **Android TV support (#244)**: Added a leanback launcher entry so yaacc can be launched from Android TV's home screen.

### Fixed
- **Play-all sort order**: "Play all from here" now follows the active on-screen sort order instead of silently reverting to the server's default order for every item after the one tapped.
- **Path display**: Fixed the sort toggle overlapping the content list on the root folder, and several path-label layout/alignment bugs (server name not always shown, incorrect indentation in landscape).
- **httpclient5/httpcore5 crash**: Reverted a dependency update that crashed on Android; pinned back to the last known-safe versions.
- **Oversized bitmap decoding (#285)**: Several code paths (the full-screen image viewer, thumbnail/icon loading, and embedded album art decoding) decoded bitmaps at full native resolution with no downsampling, which was slow and could crash with `Canvas: trying to draw too large bitmap` for high-resolution photos (e.g. 50MP camera output). Bitmaps are now downsampled during decode instead of being decoded at native resolution and scaled down afterward.

## Technical Details

### SAF Short ID Implementation
- Bidirectional URI ↔ shortId mapping in SAFCacheManager
- Persistent ID counter in SharedPreferences (`saf_id_counter`)
- Automatic migration of old cache entries
- ObjectID format: `1100999` + shortId (e.g., `11009991`, `11009992`)
- URL format: `http://ip:port/saf/11009991/1.mp3`

### Performance Optimizations
- Eliminated Cling Property/ArrayList overhead in item creation
- Cached ProtocolInfo for common MIME types
- Lightweight wrapper classes instead of heavy Cling objects
- Deferred Cling conversion until UPnP response generation

### Cache Improvements
- Memory cache: LRU with 1000 entry limit
- Disk cache: SharedPreferences with automatic trimming
- Preload: Background indexing with timeout and permission checks
- Metadata: Duration, MIME type, file size, shortId for all media files
