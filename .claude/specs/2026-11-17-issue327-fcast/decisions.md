# Decisions: FCast receivers (#327)

Status 2026-11-20: the owner answered D1 to D12 and the questions Q2 to Q8 (below, each entry says **Decided** with the answer); D13 and D14 record the last answers, D15 the discovery reuse decision. No question is open.

## Decisions (owner, 2026-11-20)

### D1. YAACC is an FCast sender only
**Decided (owner, 2026-11-20): agreed.** No receiver, no mirroring, no companion resource protocol. A receiver is a separate feature with a listening socket and its own security rules.

### D2. Phase 1 speaks protocol v3, v4 follows
**Decided (owner, 2026-11-20): v3 first.** v3 is plain JSON over TCP (no dependency). v4 (TLS 1.3 plus FlatBuffers) is phase 2 (Group 7), see D3 and D4.

### D3. v4 on Android versions that support it; minimum level unchanged
**Decided (owner, 2026-11-20): v4 on devices with a suitable Android version, the minimum level should not change if possible.**
The platform has TLS 1.3 from API 29 (Android 10). So v4 is used on API 29 and later; API 27 and 28 stay on v3. **minSdk stays 27** and no TLS provider library (Conscrypt, native code) is added. Whether API 29 really offers `TLSv1.3` through the default `SSLContext` for a plain socket upgrade is verified in task 7.1.

### D4. Choosing between v4 and v3
**Decided (owner, 2026-11-20): v4 is preferred, v3 is the fallback, decided by the Android version.**
Rule: use v4 when the Android version supports it and the receiver supports it (it announces `v` 4 or answers `Version` 4); otherwise v3. The v4 document's advice to refuse any fallback for a receiver known to support v4 is not followed (it would shut out API 27 and 28 devices and v3-only receivers). Two guard rails stay: (1) a **pin mismatch** (the certificate does not match `fp`) is an error shown to the user, never a silent fall back to v3; (2) the settings sheet shows which version is in use and whether the connection is encrypted, and says so when a v4-capable receiver is used with v3.

### D5. Naming: package, classes, UI
**Decided (owner, 2026-11-20): use `de.yaacc.fcast` if possible.** Package `de.yaacc.fcast` (an internal package of an app that is not named FCast; FUTO's policy forbids "FCast" as or at the start of a product name and as a *published* package name; descriptive use is fine, `notes.md`), class names `FCast...`, "FCast" as plain text in the UI ("FCast receiver", "compatible with FCast"), the policy's disclaimer in the About screen and the README, no FCast logo (Q8, answered in D14: text only). If FUTO objects, a rename is mechanical.

### D6. Identity of a receiver
**Decided (owner, 2026-11-20): agreed.** The id is `fcast:<host>:<port>` (the endpoint), parsed from the right, like the Snapcast server key; a changed IP makes a new receiver.

### D7. Discovery switch default
**Decided (owner, 2026-11-20): agreed.** *find FCast receivers* is on by default, searches only while the receivers page or list is shown, and the summary says announcements are not authenticated.

### D8. The queue stays in YAACC; no playlist push
**Decided (owner, 2026-11-20): agreed.** One `Play` per item; the end of an item moves to the next item in YAACC. The v3 `application/json` playlist container is not used in phase 1; a short gap between tracks is the known cost (playlist push or the v4 queue messages are the later fix).

### D9. URLs are sent as they are
**Decided (owner, 2026-11-20): always send the links as they are.** The owner asked why not. There is no good reason to treat FCast differently: the URL of an item goes to a receiver the user chose, as it already does for UPnP renderers, and a URL that needs user information or a token would not play at all if it were stripped. The earlier proposal (refuse such URLs) is dropped. What stays: the docs say that the receiver sees the full URL, and the one refusal is a request that does not fit the packet limit (32 KB in v3).

### D10. Mute is emulated
**Decided (owner, 2026-11-20): agreed.** The protocol has no mute; YAACC sets the volume to 0 and remembers the previous value; unmute restores it; a volume change from outside forgets it.

### D11. No connection for an idle card
**Decided (owner, 2026-11-20): agreed.** Discovery shows presence; a TCP connection exists only while a player exists, the sheet is open, or 30 s after that. Volume on an idle card connects on demand.

### D12. No sender SDK
**Decided (owner, 2026-11-20): agreed.** FUTO's Rust sender SDK (native code) is not used; v3 and later v4 are written in Java from the documents.

### D13. Test receiver rig for a notebook
**Decided (owner, 2026-11-20):** the owner has no receiver hardware and tests with a software receiver on a notebook; a Docker setup or an equivalent is wanted. **Outcome:** official desktop receiver on the notebook for real media, plus `tools/fcast-rig/` (task 1.5): a small test receiver with Docker and native instructions (design, "Test rig and real receivers"). A Docker image of the real receiver is task 1.6, optional.

### D14. Trademarks
**Decided (owner, 2026-11-20): text only, respect all trademarks.** Brand names appear as plain text (FCast, Snapcast, MusicCast, Yamaha, Chromecast and the like), used descriptively with the owners' disclaimers; no third-party logos or icons (Q8 answered: no FCast logo); no name that suggests an official product.

### D15. Reuse of the Snapcast discovery code (task 1.2, 2026-11-20)
**Decided (spec author, by reading the classes; the owner may veto):** **no extraction and no change to any Snapcast class** (they are finished and owner-tested). The neutral ones are used as they are from `de.yaacc.fcast.discovery`; the Snapcast-specific ones get a small FCast counterpart.
- **Used as they are (logic is service-type neutral, only the class names say Snapcast):** `SnapcastResolveQueue<T>` (serial `NsdManager` resolves, bounded, timeout), `SnapcastResolveRetry` (which failures are retried), `SnapcastBrowseHandle` (a stop before the start is confirmed), `SnapcastNsdErrors` (names of the NSD failure codes for the report), `SnapcastAddressFilter` (local-network address ranges for discovered hosts), `SnapcastPreferencesStorage(context, key)` with the `SnapcastManualServers.Storage` interface (a plain string list under a key of our own), `SnapcastEndpoint.parse(text, defaultPort)` (host or IP with optional port, IPv6, validation; called with 46899), `SnapcastResolver` (name lookup for a typed host name, takes a `SnapcastEndpoint`), `MonotonicClock`, and (found in Group 3) `SnapcastDiscoveryGate` (the page counter and the switch, `de.yaacc.multiroom`).
- **New FCast classes (the Snapcast ones are tied to Snapcast types):** `FCastNsd` (one browse `_fcast._tcp`, the lifecycle of `SnapcastNsd` without the type list, role logic and `SnapcastDirectory` coupling), `FCastDirectory` (small: id, name, endpoint, TXT hints, last seen, caps; no server-group rules), `FCastManualReceivers` (the list on top of the storage, default port 46899, cap 16), `FCastDiscoveryLog` and `FCastDiscoveryReport` (small, one type), `FCastServiceType` (the type string and its canonical form: `NsdManager` reports types with a trailing dot, in any case).
- **Why not extract a neutral base:** it would touch the Snapcast classes and their tests for no behaviour gain; the neutral classes are already public and final. **Cleanup option (owner's call, later):** rename the neutral ones to neutral names in one mechanical commit once the Snapcast review of Group 12 is done.
- **Risk:** `de.yaacc.fcast` depends on `de.yaacc.multiroom.discovery` and on `MonotonicClock`, which lives in `de.yaacc.multiroom.control`; if the Snapcast code is ever removed or reshaped, those classes must move first. Recorded here and in `tasks.md` 3.1 and 3.3.

### D16. More ways to add a receiver: connection URL, QR scan, device name (owner's request, 2026-11-20)
**Decided (owner): add the QR scan and the input of a device name as alternative connection types.** Tasks 5.5 (connection URL, pasted), 5.6 (QR scan) and 5.7 (device name) in Group 5. Reading the sources showed that both FUTO receivers already show a QR code with an `fcast://r/<base64url JSON>` URL (name, addresses, services, optional `txt` with `v` and `fp`), so the scan needs no protocol work, only the URL parser and a scanner. **Owner's idea (2026-11-20, adopted): no scanner in the app.** The device's own camera or scanner app reads the QR code and opens the `fcast://r/...` link; YAACC registers the `fcast` scheme (task 5.6) and shows a confirmation dialog before anything is added; copy and paste (5.5) is the fallback; an in-app scanner stays an optional follow-up. No camera permission, no new dependency. The `fp` in the URL is the trusted channel for the v4 pin (7.2). The device name is resolved as: IP, then a receiver already discovered, then the system name lookup, then a short `_fcast._tcp` search; the failure text says what was tried.

### D17. Details of the player (Group 4, 2026-11-21, spec author; the owner may veto)
- **A `Play` carries no volume.** The design said "the current card volume"; sending it would override the volume the receiver's user set. The volume is changed only by the user's volume control or the mute.
- **Only a picture advances by a timer.** The base class starts a timer from the item duration for every item; for audio and video that would race with the end the receiver reports (event, paused at the duration, silence rule), so `FCastPlayer` keeps the timer for images only.
- **Another sender's pause or resume is adopted** (the player shows paused or playing); a stop by the receiver stops the player and does not advance.
- **The URL is not rewritten** (the per-device proxy path of the server-side seeking option is an AVTransport feature and is not offered for FCast).
- **Leaving:** the player stops the item, waits up to 2 s for the receiver's answer and then closes the session, so no connection is left; the 30 s idle close is only the fallback.
- **An earlier player of the same receiver is ended first** when a new one is made; the old Stop leaves before the new connection can send a Play.

### D18. Review of Group 4, cycle 1 (2026-11-21): what was fixed and what is deferred
**Fixed:** an error of the receiver is acted on only for our own active item (not after our stop, not for another sender's item); a deferred end or stop is dropped if the user started or stopped something meanwhile (a play serial in the logic); our Stop and the Stop on leaving are not sent while the receiver shows another sender's item (our own `Play` claims the item in the session state until the receiver says otherwise); `FCastPlayerLogic` is synchronized; an Idle after the end is no stop of the receiver; a Paused update with our Resume or Seek pending is no end; the safety net ignores the state of the old item after our `Play`; the size check counts the speed; the base class `updateTimer` acts for pictures only.
**Deferred (written into the tasks):** the end event lost during a reconnect, the player then shows playing until the user acts (gate 6.2, and the settings sheet shows the link state, task 5.3); a host-name receiver has no share allowance until its name is resolved (task 5.7: store the resolved address); pictures go through the same state rules as audio and video (gate 6.2); the tick runs for the whole life of the player (a cost of one wake per second, to be revisited if the owner sees battery use); `createSession` is called from the constructor (works, a factory argument is a cleanup for later).

### D19. Review of Group 4, cycle 2 (2026-11-21)
**Fixed:** "is it our item" no longer depends on the receiver echoing our URL byte for byte: the first `PlayUpdate` after our `Play` (while the Play is pending) is ours whatever form of the URL it reports; only later updates are compared. The play serial is read before the logic decides, not after. **Known limit:** a `MediaItemEnd` event whose URL is in another form than ours is ignored by the end rule (the safety net still ends the item two seconds after the last update near the end); gate 6.2 should include a URL with a space, an upper-case host and a bare host. A foreign `PlayUpdate` that arrives while our `Play` is pending is taken for the answer to it (a window of at most the pending time, 3 s).

### D20. Details of the UI (Group 5, 2026-11-21, spec author; the owner may veto)
- **Mute and speed need a player.** The mute is emulated by the player (it remembers the old volume), and the speed is a property of what plays and of the following items, so the card and the sheet offer them only while a player plays to the receiver. The volume works always (a short-lived session is opened for it, D11).
- **One connection per receiver.** The sheet and the volume of the card use the player's session if there is a player, otherwise a session of `FCastReceiverLinks` (at most 8 receivers, closed 35 s after the last use); when a player is made for a receiver, the screens' session of it is closed at once.
- **The trace of the sheet is what the sheet saw** (connection, protocol version, what the receiver reports, errors, with URLs shortened to host and path), not the raw packets; 50 lines.
- **Adding:** an IP address is added at once without a test (a receiver that is off can be added); a connection link is added with the first address that answers (3 s each); a name is looked up among the receivers found, then by the system, then by a 4 s search while discovery runs; the failure says what was tried. Names with spaces are matched against announced names only. The hints (`v`, `fp`) of a link are not stored in phase 1.
- **The link activity** needs the user's tap on *Add* before anything is stored; if another app registers `fcast://` the system shows its chooser.

### D21. Review of Group 5, cycle 1 (2026-11-21)
**Fixed:** the non-English texts were English copies (a bug of the script that wrote them: it looked the translations up under the wrong key); they are real translations now and a test fails if more than 14 texts of a language equal the English ones; IPv6 link-local addresses (typed, or found by a name) are refused, a typed one with its own message; a recycled card row shows no old volume or mute; each receiver of the screens has its own session thread (a receiver that does not answer blocks only itself) and volume commands that are queued while a connection is made are coalesced to the latest; the guards of the links (grace, stale link) and of the live source (a stop and a start) are pinned; an upper-case `HTTP://` is shortened in the trace.
**Deferred:** the play, pause and stop buttons of a card without a player do nothing (there is no queue to start; stopping a receiver that another sender plays is the sheet's *Stop*); the link activity finishes on a rotation within 2 s (the same intent counts as a repeat), and a new link during an add leaves the new dialog's *Add* waiting for the running add.

### D22. The gate with real receivers (task 6.2), state of 2026-11-22

### D23. Phase 2 (Group 7): FlatBuffers runtime and how v4 plugs in (task 7.1, 2026-11-22, spec author; the owner may veto)
- **Runtime library:** `com.google.flatbuffers:flatbuffers-java` **25.2.10** (released 2025-02-11, the newest on Maven Central, Apache-2.0 which fits GPL v3+, pure Java, 110 KB, no reflection, so no R8 rule), pinned exactly. Checked with `javap`: `Table` (accessors extend it), `FlatBufferBuilder` (`startTable`, `addOffset`, `addInt`, `addFloat`, `createString`, `startVector`, `endTable`, `finish`, `sizedByteArray`). **No `flatc` and no generated sources in the build.**
- **Only the tables we use are written by hand** as thin accessors and builders (`Packet`, `Load`/`MediaItem`, `ProgressChanged`, `VolumeChanged`, `PlaybackStateChanged`, `SpeedChanged`, `SenderIntroduction`, `ReceiverIntroduction`, `StopPlayback`, `TracksAvailable`, `ChangeTrack`, `AddSubtitleSource`, `Error`, `SetProgressUpdateInterval`, `Time`). The field slots (4, 6, 8, ...) come from `fcast.fbs` and are cross-checked against the `VT_*` constants of the reference `v4_generated.rs`. **Safety against a hand-written mistake:** golden buffers produced by the reference Rust crate (`cargo` is available in the session) are read by our accessors in the tests, and buffers built by our builders are read back by a tiny Rust reader (or, if the crate cannot be built offline, by the Python `flatbuffers` package of the rig); every reader checks bounds with the library's own checks and the packet limit (512 KiB) so a hostile buffer cannot hurt. Unknown union members and messages are skipped, not errors.
- **Why not generated code:** it needs a `flatc` binary or a committed 8000-line generated file with a licence header and a regeneration step; of the 23 messages we use 14 and a thin hand-written layer is smaller, readable and reviewable. If the owner wants the generated sources instead, only the codec classes change.
- **v4 plugs in below the session, not into it.** `FCastConnection` stays the one class that owns the socket, threads, heartbeat and queues; for a v4 connection it speaks `Flatbuf` packets and a *translator* maps them to the same `FCastMessages.Incoming` objects the session already understands (PlayUpdate/PlaybackUpdate/VolumeUpdate built from `ProgressChanged`, `PlaybackStateChanged`, `VolumeChanged`, `SpeedChanged`, `Load`; the end of an item from `PlaybackStateChanged(Ended)`), and maps the session's commands (Play, Pause, Resume, Stop, Seek, SetVolume, SetSpeed) to v4 messages. The player, the card and the sheet therefore do not change for the base features; tracks, subtitles and capabilities are new `Incoming` types and commands (task 7.4). A packet gets a binary body (`byte[]`) next to the text body; the maximum packet is 32000 bytes (v3) or 512 KiB (v4).
- **Queue messages are not used** (YAACC keeps the queue, as in phase 1).

### D24. Which version is spoken, and where `fp` comes from (task 7.1)
- **v4 is attempted only when all hold:** Android API 29 or later, the receiver is known to offer v4 **and** we know its `fp`. The knowledge comes from (a) the mDNS record (`v` of 4 or more and `fp`), or (b) an `fcast://r/` link with `txt.fp` (stored with the receiver, which phase 1 did not do; task 7.2 adds the field to `FCastStoredReceivers`). A link is the stronger source (the channel is the receiver's screen, the document's threat model), the mDNS record only protects against a passive listener; the sheet says which one pinned the connection (task 7.5).
- **In that case the sender sends `Version 4` at once and goes to TLS when the receiver answers `Version 4`.** Any other answer, a failed handshake, a wrong key or a closed connection is an **error shown to the user, never a fallback to v3** (the document: the sender knows in advance, the plaintext `Version` can be downgraded by an attacker). A receiver that is *not* known to offer v4 (no `fp`: an address typed in by hand, an older record, API 27 or 28) is spoken to in v3 as in phase 1, `Version 3` goes first; this is the only path that a v4-capable receiver can still reach in plaintext, and it is the owner's current behaviour. A later improvement (not in this group): learn the `fp` of a receiver from discovery by the same endpoint.
- **A changed `fp` of a known receiver** (the receiver was reinstalled and made a new key) is the same error: the user sees "the receiver's key changed", and removes and adds the receiver again (a link or a new discovery gives the new `fp`). No silent trust-on-first-use.

### D25. The TLS client (task 7.1)
- `SSLContext.getInstance("TLSv1.3")` from API 29 (checked in the Android reference, the `SSLContext` table); the socket is the connected plaintext socket wrapped with `SSLSocketFactory.createSocket(socket, host, port, true)`, `setEnabledProtocols({"TLSv1.3"})`, then `startHandshake()` with a timeout. The plaintext reader is unbuffered (`FCastFrameReader` reads exactly the bytes of a frame), so no byte of the TLS stream is consumed before the wrap.
- **The trust manager accepts exactly one certificate:** the chain is one certificate and the SHA-256 of its `SubjectPublicKeyInfo` (`getPublicKey().getEncoded()` is the SPKI DER) equals the decoded `fp` (constant-time compare). Validity dates and the host name are **not** checked (the receiver makes a self-signed certificate with fixed long validity and no names; the key is the identity); the TLS stack still verifies `CertificateVerify` with that key, which proves possession (the document requires it). The receiver's certificate is ECDSA P-256 (rcgen), the sender offers the platform's default TLS 1.3 groups and signature schemes.
- No client certificate (the document: server authentication only). No session resumption state is kept.
- **Tests (JVM, no device):** a local TLS 1.3 server with a self-signed EC key made by the test (a `keytool`-generated PKCS12 resource, JDK 21 serves TLS 1.3), the right `fp`, a wrong `fp` (refused, no fallback, the error names the cause), an `fp` of another key, a server that answers `Version 3` although `fp` was known (error), a v3-only receiver without `fp` (v3), API below 29 (v3 even with `fp`). The API gate is an injected `int sdk` so the test does not need a device.

### D26. Order of the work (Group 7)
7.2 (TLS and version choice, with the stored `fp`) first, because it is the part with security meaning and can be tested with `Version` messages alone; 7.3 (FlatBuffers codec, translator, `FakeFCastReceiver` v4) second; 7.4 (tracks, subtitles) and 7.5 (sheet, docs) after; 7.6 (rig) can be done after 7.3 so the owner has a v4 test receiver. ### D27. Details of 7.2 and 7.3 (2026-11-22, spec author)
- **The key of a link is now stored** (`FCastPinStore`, one line per receiver, at most 32; D20 said the hints were not stored in phase 1). A receiver that was added by its address and later by its link gets the key then (the add counts as done); a different key from a new link replaces the old one (the user did it on purpose). Removing a receiver removes its key. The stored key wins over the announced one: a receiver that announces another key is refused until the user adds it again.
- **v4 is attempted only with a key and API 29 or later; the key is asked at every connection attempt** (`FCastAppSessions.PinSource`), so a link added while a session exists applies at its next connection.
- **The first message inside TLS is our `SenderIntroduction`**, then commands. We send no `SetProgressUpdateInterval` (the receiver's default of 500 ms is enough for the position display) and no queue messages.
- **`Buffering` is shown as playing**, `Ended` as an update Paused at the duration plus the end event of the item (the v3 behaviour of the Android receiver), a `StopPlayback` or `Idle` as idle.
- **Not yet checked with a real v4 receiver:** how the desktop receiver reports pictures and what it does with a `Load` while an item is Ended; the owner's gate (task 6.2 style) for v4 is task 7.6 and the rig, plus the owner's own receiver.

### D28. A switch for version 4 (2026-11-22, spec author; the owner may veto)
*Settings* > *FCast* > *Use the encrypted version 4*, **on by default** (`settings_fcast_v4`). Off: no receiver has a key to connect with, everything is spoken in version 3 (the stored keys stay). Why: version 4 was checked against the reference's own bytes, against a rig written independently and against a real TLS 1.3 handshake, but **not against the official desktop receiver** yet. A found desktop receiver announces `v` 4 and `fp`, so with the switch on it is spoken to in v4 on Android 10 or later; if that does not work with a real receiver, the owner can go back to version 3 without a new build. The error of a refused key is never answered with v3 by the app itself (D24), only by this switch.

### D29. Review of Group 7, cycle 1 (2026-11-22)
**Fixed:** (1) the v4 reader limits every text before it decodes it (16 KB for an item's address and title, 1 KB for names and format tokens) and gives one buffer 256 KB of text in all, so many fields that point at one long string can not blow up the memory; (2) a v4 `Error` fails the item only if it is of a kind that means the receiver could not load it (not found, unsupported, malformed, internal) and comes before the item plays; every other error, and any error while it plays, is a notice in the sheet (a clamped seek or volume, a refused subtitle file no longer skip or stop the track); (3) the plain socket under a TLS connection is closed first, so a write that is stuck in the TLS socket ends and `onClosed` is delivered (a test with a receiver that stops reading); (4) a repeated track list keeps the selection whose tracks are still in it; (5) a refused key or a failed secure connection is told to the player's user with its own text in 7 languages (the state carries the reason); (6) the CHANGELOG no longer says version 4 is unsupported. README says that v4 was not yet tried with the official desktop receiver.
**Not done (suggestions):** dropping v3 JSON opcodes inside TLS, a total deadline for the handshake, a possession-of-key test, a text for the switch being off in the sheet note, the subtitle address from an UPnP item, unpinned transitive Python packages of the rig.
