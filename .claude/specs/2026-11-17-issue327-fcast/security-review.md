# Security Review: FCast receivers (#327)

## Cycle 1 — 2026-11-23
Reviewing: the whole FCast change (phase 1, v3, and phase 2, v4) on `feat/issue327` after the merge of `develop` (`d23e3aba`): `yaacc/src/main/java/de/yaacc/fcast/**` (49 files, about 9,700 lines), `player/FCastPlayer*`, `browser/FCast*`, `settings/FCastReceiversDialog`, the manifest entry of the link activity, the new dependency and the log calls.

Method: static review by reading the code against the "Security rules for FCast" of `design.md` and the decisions D3, D4, D9, D24, D25. The areas read in full: `FCastTls`, `FCastPin`, `FCastPins`, `FCastPinStore`, `FCastConnection` (handshake, v4 upgrade, queues, timeouts, reader loop), `FCastFrameReader`, `FCastPacketCodec`, `FbTable`, `V4Reader`, `FCastText`, `FCastLinkActivity`, `FCastLinkIntake`, `FCastPlayRequests`; the caps of `FCastDirectory`, `FCastServiceTxt`, `FCastConnectionUrl`, `FCastReceiverLinks`; every log call in the FCast code. The existing tests were not re-run for this review beyond the full suite of the merge (6694 tests, 0 failures). **Not done:** no dynamic test, no run against the official desktop receiver (still open, see `decisions.md`), no fuzzing of its own, and the advisory database for `flatbuffers-java` 25.2.10 could not be reached from the review environment (see S4).

What holds (no finding):
- **TLS pin (D25).** TLS 1.3 only (`SSLContext.getInstance("TLSv1.3")`, enabled protocols set to it), the `X509TrustManager` accepts exactly the leaf whose SPKI SHA-256 equals the pin (`MessageDigest.isEqual`), refuses an empty chain, and refuses client certificates. The handshake signature (CertificateVerify) is checked by the TLS stack against that key, so the peer must hold the key. Dates and host name are not checked on purpose (self-signed certificate; the key is the identity). A pin mismatch, a failed handshake and a missing TLS 1.3 are typed errors.
- **No silent downgrade for a pinned receiver.** `FCastConnection.upgradeToV4` sends `Version 4`, requires the receiver's `Version` to be at least 4 (else `DOWNGRADE`), then upgrades; `FCastSession` turns every `FCastSecurityException` into an error shown to the user and does not retry in v3. A stored (link) key wins over an announced one, whatever version the receiver announces; if they differ the connection is refused.
- **Framing and limits.** Size 0 and a size over the limit (32,000 bytes v3, 512 KB v4) end the connection before the body is allocated or read; a truncated frame ends it; invalid UTF-8 drops the packet; a `Flatbuf` packet outside v4 is dropped; unknown opcodes are skipped. Liveness counts completed packets only, so a peer that trickles one frame is declared dead after 10 s. One reader, one writer thread, a write queue of 64 (overflow closes), a connect timeout of 5 s, a cap of 8 open sessions.
- **FlatBuffers (hand-written layer on the runtime).** Root offset checked; every text has a byte limit and shares one 256 KB budget per message; vector lengths are checked against the buffer; tracks at most 256 and formats at most 128; nothing is followed recursively; every `IndexOutOfBounds`, `IllegalArgument`, `BufferUnderflow` and `NegativeArraySize` becomes one `BAD_BODY`; the reader loop also catches `RuntimeException` and `StackOverflowError`. The earlier tests mutate and randomise 24 reference buffers.
- **Text from the receiver** is cleaned (controls, separators, zero-width and bidirectional marks, lone surrogates; code point limits) before it reaches a notice, a name or the UI; JSON depth is limited to 16. The log calls log opcodes, class names and counts; no URL, no title, no fingerprint, no receiver text, and the exception messages that are logged are the app's own fixed texts.
- **Discovery input.** Announced and linked addresses must pass `SnapcastAddressFilter.isAcceptedForDiscovery` (local network, no loopback, no public address); port 1024 or higher; at most 64 discovered receivers and 128 service names, a flood does not push out known receivers; TXT: 32 attributes, 256 bytes a value. A link: at most 4096 characters, strict base64url, at most 16 addresses.
- **The exported link activity** (`fcast://r/`, `BROWSABLE`) never adds anything by itself: it shows a confirmation dialog in plain text with the cleaned name, the addresses and the note on encryption; the same link twice within 2 s is ignored; the add runs on a worker and tries only filtered addresses.
- **Pin store.** Only a link can write a pin (the channel the network can not change); at most 32 entries; damaged lines are skipped; the stored value is a public key hash and is not logged in full.
- **Dependency.** `flatbuffers-java:25.2.10` is pinned exactly, released 2025-02-11 (older than 7 days), Apache-2.0, pure Java, listed in `THIRD_PARTY.md`. No other dependency was added. No private key, token or credential is in the repository; `usesCleartextTraffic` is an older app-wide setting (UPnP) and not part of this change.

### Suggestion
- [S1 `FCastPins.java:pinFor`] **A key that only came from the network is not remembered.** For a receiver without a stored link key, the pin is the one announced in the mDNS TXT record right now, and only while the receiver is announcing and says version 4 or more. So (a) a device on the LAN can announce its own key and gets an "encrypted" v4 connection (the sheet shows the key's source, `DISCOVERY`, which is the honest label), and (b) an attacker who keeps a receiver from being seen (or answers for it with a v3 announcement) makes the next connection go in v3 without any trace that this receiver was v4 before. Both are the accepted decision D4 and are documented. A cheap hardening for later: remember the first announced key of a receiver ("first use") and warn when it changes or when a receiver that had one announces none. Not needed for this release.
- [S2 `FCastLinkActivity.java`] The confirmation dialog is the only protection against a web page that opens an `fcast://r/` link for a rogue receiver; the receiver name comes from the link and can imitate a real one. Show the first address before the name (or in the title) so that an address the user does not know stands out. Low risk: a link needs the user's tap on *Add*, and only local addresses are accepted.
- [S3 `FCastFrameReader.java`] The body array is allocated at the size the frame announces (up to 512 KB in v4) before the bytes arrive. Bounded (8 sessions, 512 KB each) and closed after 10 s of silence, so no finding; reading in pieces (for example 16 KB) would remove the pre-allocation.
- [S4 build] The advisory database (OSV) could not be queried from the review environment, so `flatbuffers-java` 25.2.10 was not checked against known advisories. Dependabot is configured for Gradle in this repository; check that it covers this dependency, or run a dependency audit on a machine with network access before the release.
- [S5 accepted by the owner, listed for the record] D4: v3 (plaintext) is used for a receiver that has no key, and when v4 is not announced; D9: item URLs are sent exactly as they are, with any token they carry, to the receiver the user chose; an address typed in by hand is not range-filtered (the user's own entry). The docs and the sheet say so.

### Verdict: PASS
