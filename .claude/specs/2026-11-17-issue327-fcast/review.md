### Warning
- [tools/fcast-rig/fcast_rig.py:298 (`json.loads`), 95 (`math.isfinite`), 235 (`encode_packet` in `Session.send`), 282-286 (`handle`), 360-362 (`on_version`)] The hostile-input fix of cycle 1 is not complete: only `BadMessage` is caught, so three inputs still end in an uncaught exception and a `socketserver` traceback (by reading, not run): (a) `json.loads` accepts the literals `NaN`, `Infinity`, `-Infinity` inside any body, for example `"metadata":{"x":NaN}` in a `Play`; the value becomes `play_data`, and the next `encode_packet` (`allow_nan=False`) raises `ValueError`, which `Session.send` (it catches only `OSError`) and `handle` do not catch. The sender's session dies in the middle of `Receiver.play` (state half applied: `play_data` set, `load_token` raised, no `PlaybackUpdate`, no start timer), and every later v3 sender then dies the same way in `on_version`, because `Initial` carries the poisoned `play_data`, until the rig is restarted. (b) `number()` calls `math.isfinite` on an integer literal larger than a float (`{"time":1000...000}` with 400 digits): `OverflowError`. (c) A body nested deeper than the recursion limit (a few thousand `[` fit in 32000 bytes): `RecursionError`, which is not a `ValueError`. The cycle-1 recommendation was to wrap `handle_packet` so that any bad body is logged and ends the session on purpose; do that for every exception (`except Exception` around `handle_packet` and `self.end(...)`), reject the three constants with `json.loads(..., parse_constant=...)`, convert integers with `float()` inside a `try`, and add a test for each (NaN in `metadata`, a huge integer, deep nesting; the existing 13-case table is the right place).
- [tools/fcast-rig/fcast_rig.py:432-433, 414; README.md ("`--speaks 2` or `1` makes it an old receiver without `Initial`")] `--speaks 2` (or 1) keeps the default `--greeting 3`, so the rig announces `Version 3` (and TXT `version=3`) and then settles on 2. The sender computes min(its version, 3) = 3 and expects `Initial` and v3 behaviour, the rig computes 2: the two sides disagree about the version, which is the one thing task 2.4 (YAACC against an old receiver) must not get wrong, and the README does not say that `--greeting` has to be lowered too. No real receiver does this (the receivers greet with the highest version they speak; the test `anOldReceiver...`/`test_version_2_receiver_sends_no_initial` passes `greeting=2` explicitly, so the trap is known to the author). Make the default `--greeting` follow `--speaks` (`None` meaning `min(3, speaks)`, used for the greeting and the TXT record), or refuse the combination, and add a test that runs `speaks=2` without a `greeting` argument and checks the greeting is 2.

### Suggestion
- [fcast_rig.py:306-308, 339-340] The rig ends a v1 session on `Ping`, `Pong` and `SetSpeed`, but accepts `Initial`, `SetPlaylistItem`, `SubscribeEvent` and `UnsubscribeEvent` from a v1 or v2 sender; the desktop receiver ends the session on all of them (`handle_packet_v1`/`_v2` return `IllegalOpcode`). For the old-receiver mode that proves YAACC's v2 behaviour, end the session on opcodes of a higher version than the negotiated one (the sender's `Initial` in a v3 session is fine).
- [fcast_rig.py:370-390] `--behaviour silent` keeps the default desktop heartbeat, so the rig still ends the session after 6 s without a packet from the sender, although it sent no ping. That hides what YAACC does with a silent receiver (the sender sees a close, not silence). Make `silent` imply `--heartbeat none`, or say so in the README. In `--heartbeat android` mode the rig also pings v1 sessions (the Android receiver pings version 2 and up only), and it drops at about 10.5 s, the comment says "about 10 s" while `docs/tech.md` (correctly) says 12.5 s: use `idle > 12.5`, or one `time.sleep(2.5)` loop that counts unanswered pings like `ConnectionMonitor`.
- [fcast_rig.py:178] `threading.Timer(...)` is a non-daemon thread: with a large `--start-delay` Ctrl+C returns only after it. Set `daemon = True`. `--duration inf` or `nan` would make `json.dumps(allow_nan=False)` fail in the clock thread and stop it silently: validate the options (`finite`, positive).
- [fcast_rig.py:243-244] `sendall` has no timeout, so a sender that stops reading blocks the shared clock thread (and the other senders' updates) once its buffers are full; a per-session writer or `settimeout` would fix it. Slow in practice (hours of 1 s updates), so no Warning.
- [fcast_rig.py:403-422, README] `Zeroconf` is not closed when `register_service` fails; `docker compose down` and SIGTERM end the process without `unregister_service` (no goodbye packet; the receiver stays in the phone's cache until the TTL); a SIGTERM handler that raises `KeyboardInterrupt` would run the `finally`. With `RIG_ADDRESS` required in the compose file, `docker compose down` and `logs` need the variable too (compose reads it for every command): say so in the README or put `RIG_ADDRESS=...` into a gitignored `.env`. `-v` in the compose command also turns zeroconf's debug output on.
- [docs/tech.md, new rule list, last bullet] "Receivers send each message only to sessions that have it: ... `SetSpeed` from version 2": `SetSpeed` is a sender message; the receiver-to-sender list is `PlaybackError`, `Ping`, `Pong` from 2, `PlayUpdate`, `Initial`, events from 3. Also, a real v1 or v2 receiver translates `PlaybackUpdate` and drops it when `time`, `duration` or `speed` is missing (`translate_and_serialize` uses `msg.time?`), so an idle update may not reach a v1 or v2 sender at all; worth a line in "Still to verify" because the end-of-item guard of design section 5 depends on it.
- [Dockerfile, requirements.txt] Carried over from cycle 1, still open and harmless: `FROM python:3.12-slim` is a floating tag and `ifaddr` (transitive) is not pinned; the mDNS TXT keys with `--greeting 4` still use the Android names; `Initial` has no `playData` while the item is in its start delay (no `PlaybackUpdate` follows either); `Play` with a start time beyond `--duration` reports a time over the duration.

The accept/close race of cycle 1 is fixed (the add happens under the list lock and `closed` is re-checked afterwards).
