### Warning
- [yaacc/src/test/java/de/yaacc/fcast/FakeFCastReceiver.java:54, FakeFCastSender.java:35] The fixture classes and all their nested types and members (`Options`, `Session`, `Packet`, `Op`, `Wire`, `Script`, `start`, `port`, `received`...) are package-private in `de.yaacc.fcast`. Their consumers are in sub-packages: `FCastConnectionTest` and the session tests (design section 1 puts the connection in `de.yaacc.fcast.protocol`; tasks 2.3, 2.5, 3.x, 4.x), and the repo convention is that a test sits in the package of the class it tests (`FakeSnapcastServer` is package-private in `de.yaacc.multiroom.control` next to its users). As committed, Group 2 cannot use the fixture. Make the fixture and the members tests need `public`, or record in `decisions.md` that all FCast tests live in `de.yaacc.fcast`.
- [tools/fcast-rig/fcast_rig.py:104-109, 135] `broadcast(..., only_v2_plus=True)` sends `PlayUpdate` (opcode 15, a v3 message) to every session with `version >= 2`. A `--speaks 2` rig therefore sends a v3-only message to a v2 sender (verified: a v2 session receives `play_update` then `playback_update`). The reference receivers do not: Android `isSupportedOpcode` allows only opcodes up to 13 for v2, the desktop `Forward` of `PlayUpdate` is limited to `SessionVersion::V3`. Task 2.4 uses an old receiver to prove YAACC's v2 handling, so the rig must not hide a bug by sending extra messages. Send `PlayUpdate` only to sessions with `version >= 3`. (Optional: a v1 session gets no updates at all from the rig, the real receivers send it translated `PlaybackUpdate`/`VolumeUpdate`.)
- [tools/fcast-rig/fcast_rig.py:67-69, 135] The rig can send a packet over the 32000-byte limit: `encode_packet` has no check, and the `PlayUpdate` echo of a `Play` is bigger than the `Play` (wrapper plus `json.dumps` with the default `ensure_ascii`). Verified: a `Play` body of 31999 bytes (accepted, size 32000) is echoed as a packet with size 32044; a 10 KB body of non-ASCII characters (a long title) is echoed as about 30 KB because each character becomes a 6-byte `\uXXXX` escape, so a slightly larger title gives an oversize packet. The receivers skip such a message instead of sending it (`receiver-core/src/fcast.rs:227`, `send_legacy_body`; Rust `encode` refuses a body of 32000 or more). A sender that closes on it (as designed, section 1) would fail against the rig for a reason no real receiver produces, and the existing test `test_the_limit_itself_is_accepted` (`test_fcast_rig.py:166`) passes only because its URL is about 150 bytes under the limit. Drop messages that would not fit (log a warning), use `ensure_ascii=False`, and make that test hit the exact limit (size 32000).
- [tools/fcast-rig/fcast_rig.py:126-134, 160-163, 235] Input values are not handled consistently: `set_speed` clamps (0.25 to 4) but `play` takes `speed` and `time` as they come, so `"speed":1e999` is stored and broadcast as `Infinity` (invalid JSON for the sender; verified) and a negative `time` becomes the position; a `Version` body with a non-integer value (`{"version":"abc"}`) or a non-numeric `volume`/`time` raises an uncaught exception in the handler thread (traceback from `socketserver`, session dropped; verified). Wrap `handle_packet` so that a bad body is logged and answered with `PlaybackError` (or closed on purpose), and clamp the `Play` fields like the setters.
- [tools/fcast-rig/fcast_rig.py:111-123, 126-138, tools/fcast-rig/test_fcast_rig.py] Task 1.5 requires that `Play` is answered with "a scripted Idle, Playing, Idle sequence". The rig sends `PlayUpdate` and then Playing; there is no Idle report before the item starts, although that early Idle is exactly the case the end-of-item guard of `design.md` section 5 and task 4.2 must handle ("the Idle that is reported before an item starts"). The closing Idle (end of the track, `_tick`) is the behaviour the README promises ("YAACC should start the next item") and is the main reason the rig exists, but no test covers it (no test uses a short `--duration`; the 18 tests cover handshake, controls, limits, heartbeat). Add an option (or the default) that reports Idle after `Play`, and a test that runs a 1 to 2 s track to its Idle.

### Suggestion
- [FakeFCastReceiver.java:466-476] A `Version` of 4 or more from the sender is accepted silently (`negotiated = min(theirs, speaksVersion)`). The design rule "YAACC never sends `Version` 4 before the TLS upgrade exists" is a safety rule (the desktop receiver switches to TLS at once; the Android receiver would stay at v2 without `Initial`), and the rig already closes the connection on it. Give the fixture the same behaviour (an option on by default, or a recorded flag) so that every connection test also guards the rule.
- [FakeFCastReceiver.java:489, accept of 1.3] The fixture exposes `port()` only; the accept criterion says "exposes its bound endpoint". Add `host()` or `endpoint()` (the loopback address and the port) so tests do not repeat the loopback literal.
- [FakeFCastReceiver.java:410-421, 459] When the sender breaks the limits (size over 32000, size 0), `Wire.read` throws, the handler swallows it and the socket stays open; real receivers close. Close the socket on any handler exit, so that "sender sends oversize" is testable in Group 2. For the stalled mode, an option for a small receive buffer (`ServerSocket.setReceiveBufferSize` before bind) would make "queue overflow closes" and "close during a blocked write" (task 2.3) testable without writing megabytes through the loopback buffers.
- [FakeFCastSender.java:91-97] `isClosedByPeer` returns false on any `IOException`, including "Connection reset", which is what a close with unread data looks like. Treat a reset as closed to keep future tests from flaking.
- [FakeFCastReceiver.java:23, 402-409, 562-566] Unused import `ByteArrayOutputStream`; a connection accepted while `close()` iterates `sessions` is not closed (tiny race, daemon thread, only until the JVM ends).
- [docs/tech.md:3790, 3804, 3807] Precision: the desktop receiver reads packets up to 512 KiB even in a v3 session (`PacketReader::new(v4::MAX_PACKET_SIZE)`) and ends on size 0 in every version, not only v4; the Android receiver pings with a retry count that only a `Ping` or `Pong` resets (not any packet), sends 4 pings and drops the sender at the next tick, so 12.5 s rather than "about 10 s"; the Android TXT keys are named `appName`/`appVersion` but carry `VERSION_NAME` and `VERSION_CODE`; an Android receiver that gets `Version 4` stays at v2 (no `Initial`).
- [tools/fcast-rig/fcast_rig.py:176-179, 223, 140-148] Fidelity to the receivers: `Initial` has no `playData` and no `PlaybackUpdate` follows on connect for a sender that joins while something plays (both reference receivers send them; the README row "a second sender gets the same updates" suggests it); `Pause` while idle reports state Paused; with `--greeting 4` the TXT records still use the Android keys (`version`) instead of `v`; `--heartbeat android` resets on any packet and compares a stale `idle` (computed before the 2 s sleep), so the drop comes after about 12 s of silence.
- [tools/fcast-rig/fcast_rig.py:181-192] In `slow` mode the sleep happens in the calling thread, so one slow sender also delays the shared clock thread and every other sender's messages. Sleep in a per-session sender thread, or document it.
- [tools/fcast-rig/fcast_rig.py:323-338, Dockerfile, docker-compose.yml, requirements.txt] Operations: an `advertise` failure (`gethostbyname` error, name conflict, port 5353 busy) ends the program with a traceback; warn when the announced address is a loopback address (`127.0.1.1`); as PID 1 in the container Python ignores SIGTERM, so `docker compose down` waits 10 s and never unregisters the mDNS service (`init: true` or a SIGTERM handler); the compose placeholder `--address 192.168.1.50` is silently wrong when not edited (use `${FCAST_RIG_ADDRESS:?...}` to fail loudly, as `non-interactive.md` asks); `FROM python:3.12-slim` is a floating tag and the transitive `ifaddr>=0.1.7` of `zeroconf` is not pinned (a constraints file or a second pinned line). The README gives the Windows `pip` path but not the run command (`.venv\Scripts\python fcast_rig.py --address ...`), and does not say that the rig listens on all interfaces without authentication by default.
- [tools/fcast-rig/README.md:1, fcast_rig.py default `--name`, `appName`] D14 asks for no name that suggests an official product and FUTO's policy forbids "FCast" at the start of a product name: the heading "FCast test receiver", the default announced name `FCast-rig` (the same pattern as the official `FCast-<hostname>`) and `appName "fcast-rig"` start with the brand. Suggested: default name "YAACC test receiver", heading "Test receiver for the FCast protocol", and the exact disclaimer sentence from `TRADEMARK.md` instead of the short one.
- [tools/fcast-rig/test_fcast_rig.py] Not covered: the exact 32000 boundary for a `Play`, `--heartbeat android`, `--speaks 1`, a body that is not JSON or not an object, hostile numbers. `Receiver._tick` and the heartbeat threads are never stopped, so each test leaves a daemon thread behind.
- [decisions.md D15] Fine as written. If the owner keeps it, note in tasks 3.3 that `SnapcastResolver` still names its thread "snapcast-resolver" (visible in thread dumps only).
