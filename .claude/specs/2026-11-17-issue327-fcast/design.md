# Design (draft): FCast receivers

Plan: `requirements.md` (goals, non-goals), facts and sources in `notes.md`, decisions D1 to D12 and open questions in `decisions.md`. Status 2026-11-17: draft for the owner. Class names are proposals; `Fc` is short for the FCast code in the text only.

## Context
FCast receivers take a URL and play it. YAACC already has three ways to put a non-UPnP receiver into its lists and players: OpenHome (a real Cling device with extra services), MusicCast (a real Cling device plus an HTTP API) and Snapcast groups (a **synthetic device that is never registered with Cling**, `SnapcastGroupDevice`, listed by `UpnpClient.getDevicesProvidingAvTransportService()` after the registry's devices, with its own player `SnapcastPlayer` made in `PlayerService`). FCast receivers are not UPnP devices, so the Snapcast route is the model: a synthetic device, its own directory (mDNS plus manual list), its own player, its own row binder and settings sheet. Code goes into a new package `de.yaacc.fcast` (name: `decisions.md` D5) with `protocol`, `discovery`, `player` logic and the UI classes in `de.yaacc.browser` next to the other binders, as the existing receiver types do.

## Layers

```
Receiver list (UpnpClient)  <- FCastReceivers <- FCastDirectory <- FCastNsd (mDNS) + FCastManualReceivers (settings)
        |                                          
        v  select / play                         
PlayerService -> FCastPlayer (Player) -> FCastSession (state, queue-independent) -> FCastConnection (socket, codec)
                                                      ^
UI: FCastRowBinder, FCastSettingsSheet  -----------+
```

### 1. Protocol layer `de.yaacc.fcast.protocol` (pure Java, JVM-testable)
- `FCastOpcode` (the v3 table), `FCastPacket` (opcode plus body bytes), `FCastPacketCodec` (encode: little-endian `size = 1 + body`, opcode, body; decode: incremental from a stream), `FCastFrameReader` (reads packets from an `InputStream` with the limits below; a read deadline so a stalled peer is detected).
- Message models as small immutable classes with `toJson` / `fromJson` using the platform `org.json` (no library): `PlayMessage` (with `MediaMetadata` generic type 0), `SeekMessage`, `SetVolumeMessage`, `SetSpeedMessage`, `PlaybackUpdateMessage`, `VolumeUpdateMessage`, `PlaybackErrorMessage`, `VersionMessage`, `InitialSenderMessage`, `InitialReceiverMessage`, `PlayUpdateMessage`, `SubscribeEventMessage` and `EventMessage` (media item end only). Parsing is **lenient for unknown fields** (receivers differ), **strict for the types it uses** (a wrong type or a missing required field is a protocol error for that message, not a crash).
- **Limits (security, pure and tested):** a packet larger than 32000 bytes (v3) or with `size = 0` ends the connection; strings from the receiver are cut (names 60 characters like the OpenHome sheet, error text 200, URLs 2048), control characters removed (`LogText.clean` exists for logs); numbers from the receiver are clamped (volume 0 to 1, time and duration finite and not negative, speed 0.25 to 4); unknown opcodes are skipped (their body is read and dropped within the size limit).
- `FCastConnection`: one socket per receiver in use: connect timeout 5 s, TCP no-delay, one reader thread, a write queue that is drained by one writer (a slow receiver must not block the UI or the player thread; queue capped, overflow closes the connection), orderly close. Handshake: send `Version {version: 3}`, wait for the receiver's `Version` (if it is lower than 3 the connection uses what the receiver supports: v2 has no `Initial`, so phase 1 treats 1 and 2 as "plays, with fewer details" or refuses with a message; see task 2.4), then send `Initial` (display name from the existing "UPnP server name" setting, app name `YAACC`, app version) and take the receiver's `Initial`. Heartbeat: answer every `Ping` with `Pong`; send a `Ping` after 5 s of silence and treat 15 s of silence as dead (proposal; the document gives no v3 numbers, verify with receivers, `notes.md`). Listeners get messages in order on one callback thread.

### 2. Session and state `FCastSession`
Owns one connection and the receiver's **state as the receiver reports it**: playback state, time, duration, speed, volume, current item (`PlayUpdate` / `Initial.playData`), last error, receiver app name and version, negotiated protocol version. It exposes commands (`play(PlayRequest)`, `pause`, `resume`, `stop`, `seek`, `setVolume`, `setSpeed`) and a listener. It never assumes a command worked: the state changes when the receiver says so (`PlaybackUpdate`, `VolumeUpdate`), with a short "pending" state for the UI. Other senders on the same receiver show through the same messages (a `PlayUpdate` with another URL means someone else plays; the card shows the receiver's state, YAACC does not fight it). Reconnect: after a lost connection one retry with backoff while a play session exists (the same pattern as the Snapcast control library), then the player reports an error and stops; no endless loops, no connection without a user of it.

### 3. Discovery and the directory `de.yaacc.fcast.discovery`
- `FCastNsd`: `NsdManager.discoverServices("_fcast._tcp")` with a resolve queue (the Snapcast discovery already solved the serial-resolve limits of `NsdManager`, `SnapcastNsd`, `SnapcastResolveQueue`, `SnapcastResolveRetry`, `SnapcastNsdErrors`; **task 1.2 decides** whether to extract those into a service-type-neutral helper or copy the small parts: the first is cleaner, the second does not touch finished and owner-tested Snapcast code), a multicast lock held only while browsing, browsing only while the receivers page or the list is shown (like Snapcast), a discovery report (what was browsed, what the system reported, Wi-Fi, permission, lock) with *Copy report* in the settings.
- `FCastEndpoint` (host or IP, port, validated: port 1 to 65535, host not empty, IPv6 literal handled, link-local zones rejected or kept per the Snapcast address filter; reuse `SnapcastAddressFilter` ideas), `FCastServiceTxt` (reads `v`, `fp`, `version`, `appName`, `appVersion` as hints with length limits; nothing is trusted).
- `FCastDirectory`: the known receivers (id, display name, endpoint, last seen, source: discovered or manual), a cap (64 discovered, 16 manual), expiry of discovered entries that disappear from mDNS (the browse reports a lost service) and entries not seen for a while stay out of the list, **a flood of announcements cannot grow it past the cap** (oldest dropped). Pure, with a fake clock.
- `FCastManualReceivers`: a stored list (preferences, like `SnapcastManualServers` and `SnapcastPreferencesStorage`) of hand-added receivers (`host[:port]`, default 46899); a name for each. No credentials.
- Receiver identity: the id of a receiver is `fcast:<canonical endpoint>` (host and port; IPv6 in brackets), the same idea as the Snapcast server key; **a receiver whose IP changes (DHCP) is a new receiver** and the old card disappears when mDNS says so (risk R2, alternatives in `decisions.md` D6). Two announcements of the same endpoint are one receiver; two instance names for one endpoint use the latest name.

### 4. Device model and lists
- `FCastReceiverDevice`: a synthetic Cling `Device`, never registered, modelled on `SnapcastGroupDevice` (immutable snapshot; equality by id; no services; display string "FCast"; friendly name = the instance name, else the receiver's own `displayName` from `Initial`, else the address). `isFCastId(String)` and `parse(id)` (prefix check, endpoint parsed from the right, bounded length).
- `FCastReceivers` (a source like `SnapcastGroupSource`): `receivers()` and `findReceiver(id)`; `UpnpClient.getDevicesProvidingAvTransportService()` adds the receivers after the Snapcast groups, `UpnpClient.getDevice(id)` returns one for an `fcast:` id. A `Player`-less receiver stays a card only; a click opens the same device sheet flow as other receivers.
- The existing "is this device a receiver that cannot play" checks (`PlayerService.isNotPlayableYet`) stay unchanged for FCast: it can play.

### 5. The player `FCastPlayer` (implements `Player`, extends `AbstractPlayer` as the other players do)
One player per receiver, made in `PlayerService` like `createSnapcastPlayer` / `newOpenHomePlayer`, closed when the user closes the player, the receiver disappears and the player's grace period ends, or the app exits (the cleanup order of the exit, see the Snapcast `ExitHandoff` and `PlayerService.shutdown`).
- **Play an item:** the URL and MIME of the item come from the same place as for AVTransport (the DIDL resource and its `protocolInfo`, or the local file served by YAACC's content server; the URL rewriting that makes a URL reachable for another device is the AVTransport code's job, task 4.1 reuses it). `PlayMessage`: `container` = the MIME type (never empty: fall back to `ContentTypes` by extension), `url`, `time` = start position when resuming, `volume` = the current card volume, `metadata {type:0, title, thumbnailUrl}` with title and album art URL (an art URL that is not reachable from the LAN is left out). `headers` are **never** sent (no credentials or cookies leave YAACC).
- **Queue and transport semantics:** next, previous, repeat, shuffle and the play list stay in YAACC (`AbstractPlayer`); next means a new `Play` for the next item. Pause is `Pause`, play is `Resume` (or a new `Play` after stop), stop is `Stop`, seek is `Seek` in seconds, fast forward and rewind are seeks relative to the last reported time.
- **End of item:** the receiver reports `PlaybackUpdate` with state Idle after the item finished. The player advances **only** when it has seen Playing (or a time close to the duration) for the current item and then Idle without a stop of its own and without an error: this guards against the Idle that is reported before an item starts and against our own stop. `MediaItemEnd` (subscribed event) is an optional second signal if the receivers send it reliably (task 4.3 checks with real receivers). A `PlaybackError` skips the item through the existing `TrackFailurePolicy` and shows the toast with the receiver's text (cleaned).
- **Images:** a picture is one `Play`; YAACC advances after its slide time like for other receivers (`PlayMode` / the picked-images behaviour); `showDuration` is a playlist-only field and is not used.
- **Volume and mute:** the card and player volume 0 to 100 maps to 0.0 to 1.0 (`SetVolume`); `VolumeUpdate` updates the UI (from the receiver or another sender). The protocol has **no mute**: mute sets the volume to 0 and remembers the previous value, unmute restores it; a `VolumeUpdate` from outside clears the remembered value. `hasActionGetVolume()` and `hasActionGetMute()` are true once connected.
- **Position and duration** for the progress bar come from `PlaybackUpdate` (`time`, `duration`); between updates the player extrapolates only while Playing and corrects at the next update. `getAlbumArt` and titles come from the item, as for the other players.
- **Media session and notification** as for the other remote players (lock screen and headset buttons control the remote receiver).
- **Not supported messages** (a receiver that is v1 or v2) are reported once as a limitation, not retried.

### 6. UI
- `FCastRowBinder` (next to `SnapcastRowBinder` and `ReceiverRowBinder`): the card shows the name, "FCast" as the type text, the endpoint, the state (*Not reachable*, *Idle*, *Playing*, *Paused*, with the current title when known), a volume control (enabled while a session is connected; otherwise a tap connects first), and a gear for the settings sheet. No power button (FCast has no standby; the "power" model of the other cards does not apply). A reachable test is cheap: the row shows mDNS presence; "Not reachable" appears only after a failed connect.
- `FCastSettingsSheet` (a bottom sheet like `OpenHomeSettingsSheet` and `YxcSettingsSheet`), content for **phase 1 (v3)**:
  1. **Device**: name, endpoint, discovered or added by hand, receiver app name and version (from `Initial`), protocol version in use, and a plain note "unencrypted (protocol v3)".
  2. **Playback**: volume, mute (emulated), speed (0.5, 0.75, 1, 1.25, 1.5, 2 via `SetSpeed`; applies to the running item and to following items), *Stop*.
  3. **Connection**: *Check connection* (connect, handshake, show the result and the time it took), *Reconnect*.
  4. **Troubleshooting**: the last protocol events (a bounded trace with *Copy trace*, URLs shortened to host and path, no query strings), like the Snapcast client details.
  5. **Manage**: *Remove* for a hand-added receiver; for a discovered one *Hide* is not offered in phase 1 (open question Q6).
  
  Phase 2 (v4) adds: audio track and subtitle track pickers (`ChangeTrack`), *Add subtitle* when a UPnP item has a subtitle resource (`AddSubtitleSource`), the receiver's capabilities (formats, volume step, display size), the progress interval. This is where "settings of the receiver" can grow if FUTO adds more to the protocol; the sheet is built from what the session reports (a section appears only when the receiver supports it), not from a fixed list.
- Settings screen (`preference.xml`, `settings_fcast_*` keys, a category like the Snapcast one): *find FCast receivers* (mDNS, default on, proposal D7), *FCast receivers* (the list with *Add receiver*, remove, the discovery report with *Copy report*), the trademark disclaimer line. Summary texts state what the switch does and that announcements are not authenticated.
- Strings in all languages the app has (`values*/strings.xml`; the repo's convention is checked in task 5.1), `docs/settings.md` rows for every new key.

## Connection lifecycle (battery and network)
- Browsing: only while the receivers list or the receivers page is visible (like Snapcast), nothing runs in the background.
- A connection is opened when the user **uses** the receiver: starts playing, opens its sheet, or changes its volume from the card. It stays open while a player exists for the receiver and for 30 s after the sheet closes with nothing playing, then closes (`FCastSession` idle timer, proposal). An idle card has no connection: its state is the mDNS presence.
- While playing, the connection is kept by the player's own work, **no extra wake lock and no foreground service** beyond what the PlayerService already does for other remote players (checked in task 4.4: the service must keep the process alive for the remote playback the same way it does for AVTransport; the notification of the player is the user-visible hint).
- Receiver reboot or Wi-Fi loss: the connection ends, the player shows an error, the card state returns to "not reachable" until the next mDNS sighting or a manual retry.

## Security rules for FCast (phase 1)
The sender talks to receivers it **chose**; YAACC opens **no listening socket** for FCast.
1. **Announcements are unauthenticated**: any device can announce `_fcast._tcp`. YAACC never plays anything to a new receiver on its own: starting a session needs the user's choice of the card. A rogue receiver would learn the URLs of the items the user sends it (this is the same exposure as with any UPnP renderer; the docs say so). The switch to turn discovery off exists and the manual list works without it.
2. **Everything from the receiver is untrusted** (names, TXT records, JSON, numbers): limits and clamping as in the protocol layer, bounded queues, bounded counts, no reflection of receiver strings into logs without cleaning, no HTML or markup interpretation, no file or intent actions from receiver data.
3. **Plaintext v3:** control messages and the URLs are readable and changeable on the LAN. The docs and the sheet say so. **URLs are sent exactly as they are** (owner, 2026-11-20, D9): an item URL that the user's UPnP server gave out, with whatever user information or token it carries, goes to the receiver the user chose, the same as YAACC already does for UPnP renderers; the docs say that the receiver sees the full URL. The only refusal is a URL that does not fit the packet limit (an unreadable item is skipped with a message).
4. **No headers, no cookies, no stored credentials.** Nothing from the other receivers' config (Snapcast, MusicCast) is shared.
5. **Limits against floods and hostile receivers:** packet size, string sizes, a write queue cap, timeouts for connect and silence, a maximum of one connection per receiver and a small global cap (8), directory caps, rate limit on directory updates from mDNS, Ping/Pong handled without allocation growth.
6. **Brand and disclaimer** (text in About, README, settings): text names only, no FCast logo (owner, Q8), all trademarks respected (D5, D14).
7. **Phase 2 (v4)** adds TLS 1.3 with the SPKI pin from `fp`. v4 is preferred and v3 is the fallback (D3, D4): on API 29 and later a receiver that announces v4 is connected with v4; on API 27 and 28, or for a receiver that speaks only v3, or when the v4 upgrade fails, the connection uses v3. The protocol's advice not to fall back from v4 is not followed (owner's decision D4); the settings sheet shows which version and whether the connection is encrypted, and says when a receiver that supports v4 is used with v3.

## Phase 2 sketch (v4, not part of the first build)
- TLS 1.3 only (`SSLContext.getInstance("TLSv1.3")`, platform support from API 29; **API 27 and 28 stay on v3, no TLS provider library is added and minSdk does not change**, D3), a `TrustManager` that accepts exactly the certificate whose SPKI SHA-256 equals `fp` and lets JSSE verify `CertificateVerify`; `fp` comes from the mDNS TXT record or, safer, from a scanned `fcast://r/` QR code (the QR path needs a scanner: the app has none today, so a typed-in or pasted URL first).
- FlatBuffers for the `Flatbuf` opcode (20): the runtime library (`com.google.flatbuffers:flatbuffers-java`, Apache-2.0, pure Java; version and release date to be checked against the 7-day rule at that time) plus Java sources generated from the published schema and **committed** (no `flatc` binary in the build); or a small hand-written reader and writer for the handful of tables used, which keeps the dependency out but must follow schema changes by hand. Task 7.1 decides with a size and risk comparison.
- Messages used: `SenderIntroduction`, `ReceiverIntroduction`, `Load` (single `MediaItem`), `ProgressChanged`, `VolumeChanged`, `PlaybackStateChanged`, `SpeedChanged`, `StopPlayback`, `TracksAvailable`, `ChangeTrack`, `AddSubtitleSource`, `Error`; the queue messages only if the owner wants the receiver to hold the queue (it removes the gap between tracks but moves queue logic out of YAACC).

## Test strategy
- **JVM tests (the bulk):** codec and framing round trips and malformed input (size 0, oversize, truncated, unknown opcode, split reads), every message's JSON in and out (golden strings written from the documents), the session state machine against `FakeFCastReceiver`, player logic (end-of-item guard, error skip, mute emulation, volume mapping, pending states) with a fake session, directory (caps, expiry, flood, identity), endpoint and TXT parsing, id parsing, `FCastReceiverDevice` equality, the receiver list order in `UpnpClient`, row text and sheet logic as pure helpers (the existing pattern: `...Text`, `...Choices` classes).
- **`FakeFCastReceiver`**: a loopback TCP server on **port 0** (the endpoint is handed to the code under test; no test binds a fixed port: this is the lesson of T.5 in the Snapcast spec), scriptable (versions, `Initial`, state updates, ping behaviour, slow and stalled peers, a second sender).
- **Test rig and real receivers (owner, D13):** the owner has no receiver hardware and tests with software on a notebook. Three levels: (A) the **official FCast desktop receiver** installed on the notebook (downloads on fcast.org: Windows installer, macOS image, Linux Flatpak; it plays real media, so it is the check for formats, video, pictures and end-of-item behaviour); (B) `tools/fcast-rig/`, a small **test receiver** that speaks v3 (and later v4) without any media player: it announces `_fcast._tcp`, logs every message YAACC sends, answers the handshake, reports scripted playback and volume updates, and can misbehave on purpose (slow, silent, oversize, old version); it runs natively or in Docker (with host networking on Linux, because Docker's bridge network does not carry mDNS multicast; on Windows and macOS run it natively); (C) FUTO's `tools/fast` against the real receiver to see what a conforming receiver does. No Docker image of the real desktop receiver is planned: the receiver build compiles a pinned GStreamer from source (`receivers/desktop/README.md`), and the desktop receiver has a `headless` setting, so a headless container build stays an option if the owner wants one later (task 1.6).
- Instrumented or UI tests only where the existing patterns have them for the other receiver types.

## Risks
- R1. v3 acceptance by current receivers (the Rust receiver source says yes; verify). If a future receiver drops v3, phase 2 becomes mandatory.
- R2. Identity by endpoint: DHCP changes. Alternative: the mDNS instance name as identity.
- R3. Receivers differ in what they can play (formats, audio-only items, images) and in how they report end of item; the end-of-item guard and the error path are the parts to harden with real receivers.
- R4. mDNS on Android (the Snapcast experience: multicast lock, serial resolves, networks with isolation); the discovery report and the manual list are the answer.
- R5. A fixed 32 KB packet limit: the URL, title and art URL must fit; very long URLs are refused with a message.
- R6. Trademarks: text names only, the wording and the disclaimers must stay as the owners' policies ask (FUTO's policy for FCast; the same care for the other brand names in the app); a logo needs the owner's decision and the brand owner's permission (not planned).
- R7. v4 only on API 29 and later; a v4 receiver used with v3 (fallback) is readable on the LAN (D3, D4). A receiver that offers v4 but fails the upgrade (pin mismatch) must not silently fall back to v3 when the cause is a wrong fingerprint: a pin mismatch is an error shown to the user, a version mismatch or a missing v4 is the fallback (task 7.2).
