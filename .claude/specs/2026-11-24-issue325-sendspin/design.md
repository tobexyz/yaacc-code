# Design: Sendspin support (#325), a proof of concept first, then server and client

Requirements: `requirements.md`. Decisions and open choices: `decisions.md`. Normative source: `github.com/Sendspin/spec` at `2cfe197` (2026-11-24; the first draft used `c281aeb`), `README.md`; section names are the spec's. Items marked (verify) are assumptions that the checks of Group 1 in `tasks.md` must settle before code depends on them.

## Context
- The spec's **server** orchestrates players and groups, generates streams, manages pairing; a **client** has roles (`player`, `controller`, `metadata`, `artwork`, `source`, ...). A client is in exactly one group; the server owns group membership; a new server can displace the one that currently holds a player's `'playback'` activity (spec "Multiple servers").
- YAACC already is a media controller/server with a queue, a local player and a receivers list with MusicCast linking (`de.yaacc.yxc`, `YxcGroupDirectory`, `YxcLinkCandidates`, `YxcPlayTargets.resolve`, the link sheet). Receivers are Cling `Device` objects.
- **What exists since the draft of 2026-11-09 and is reused** (checked in the code on 2026-11-24; the first column is the need, the second where it is):
  - *A receiver that is not a UPnP device:* `SnapcastGroupDevice` (`de.yaacc.multiroom`) and `FCastReceiverDevice` (`de.yaacc.fcast.discovery`) are `Device` subclasses that never enter Cling's registry; each protocol has its own `Player` (`SnapcastPlayer`/`SnapcastPlayerLogic`, `FCastPlayer`/`FCastPlayerLogic` in `de.yaacc.player`), created by `PlayerService.createPlayer` by `instanceof`, and its own row code in `de.yaacc.browser` (`ReceiverRowBinder` branches, `SnapcastRowBinder`/`FCastRowText`, `ReceiverVolumeLiveUpdater`, `RendererStatusMonitor` exclusion). Sendspin follows this pattern; no new seam. The places it touches are listed by task 1.3.
  - *PCM out of YAACC's own player:* `de.yaacc.multiroom.feed` (`PcmTapAudioProcessor`, `FeedTapChain`, `PcmFormatConverter`, `PcmResampler`, `PcmFeeder`, `RealTimePacer`, the slots and streams). It gives the PCM of the queue in a fixed format at real time, with seek and track changes handled for the Snapcast feed. Sendspin needs the same PCM with timestamps instead of a pipe to a server.
  - *A player-side engine for a synchronized stream:* `de.yaacc.multiroom.client` (`AudioTrackSink`, `DriftController`, `FrameCorrector`, `ChunkScheduler` in `multiroom.protocol`, `MediaCodecFlacDecoder`, `PcmConverter`, `ClientSession`, the foreground service and its power and notification policies). Built for Snapcast's time sync (`ClockOffsetFilter`, a different filter than Sendspin's); the player role of this spec reuses the engine and brings the Sendspin time filter (task 8.1 checks how much is generic).
  - *Discovery:* `SnapcastNsd` plus resolver, queue and gate, `FCastNsd`: `NsdManager` browsing with the multicast lock, only while a receiver page is open. A third copy for `_sendspin._tcp` follows the same shape; a shared base is a later cleanup, not part of the PoC.
  - *Linking UI patterns:* `YxcLinkCandidates`/`YxcGroupDirectory` (MusicCast) and `SnapcastLinkSheet`/`SnapcastLinkChoices`/`SnapcastMemberRows` (Snapcast).
  - *Secrets and settings patterns:* `FCastPinStore`/`FCastPins` (pinned receiver keys), `SnapcastMarkerStore`, `SnapcastSettings`/`FCastSettings` (defaults, discovery switch), the discovery reports. Nothing stores private keys wrapped by the Keystore yet: that is new (task 3.5).
  - *Rigs:* `tools/snapcast-rig/`, `tools/fcast-rig/` (Docker, pinned images, an opt-in JVM switch as a system property).

## Decision
A proof of concept with kill criteria (stage P, 3 steps), then four phases, each releasable, one protocol stack for both roles:
- **P: proof of concept** (Groups 1 to 4 of `tasks.md`): P0 crypto and transport spike in a JVM, P1 hear one player (unpaired with approval), P2 Pairing PSK; ends with the owner's go / reduce / stop.
- **Phase 1 Foundations** (pure Java, no UI) is mostly built by P: WebSocket, Noise, messages, identity and pairing store; what P left out (fragmentation, the full codec, the Kalman time filter) is finished here.
- **Phase 2 Server ("hub")**: several players, groups and linking, group volume, takeover display.
- **Phase 3 Client ("speaker")**: the phone as a player, with a single in-process endpoint shared with the server role.
- **Phase 4 Extras**: controller/metadata/artwork roles, code-based pairing (CPace), FLAC encoding and Opus, source role.

Rejected: a bridge that publishes Sendspin players as UPnP renderers (a second large design, kept possible); a server-only release without ever doing the client (the client carries the main risk but also completes the MusicCast-like picture, so it is gated, not dropped); a PoC that starts with the phone as a player (the server role gives the value the owner wants first and the audio engine for the player role exists, but its sync target is tighter, so it comes after).

## Proof of concept (stage P)
The smallest path that answers Q1 to Q5 of `requirements.md`; everything else of this document waits for the gate.

1. **P0, JVM only, throw-away** (`tools/sendspin-rig/spike/`): WebSocket client (RFC 6455 subset) to a reference player, `client/init` -> `server/init`, Noise `KKpsk2` as the initiator under the Sentinel PSK, encrypted `server/hello` / `client/hello` / `server/activate`, answer `client/time` with `server/time`, read `client/state`. Then the same under a pairing PSK with a token and the re-handshake. Both cipher suites. Only library primitives. Kill criterion: no interoperable handshake with reasonable effort.
2. **P1, in the app, unpaired**: `SendspinHub` connects (server-initiated mode: the player is found by `_sendspin._tcp` or typed in as `host:port`), shows the player as a receiver row, and plays the current queue to it: the PCM tap of the existing feed, converted to 48 kHz 16-bit stereo, cut into 20 ms chunks with server-clock timestamps and sent at real time with a **fixed lead** (for example 1 s, within the player's `buffer_capacity`; not a full accounting yet), `stream/start` at play, `stream/clear` at seek and track jump, `stream/end` at pause and stop. Volume and mute by `server/command`. The operator approval is the act of choosing the player in "Play on" (the spec lets a server treat starting playback on a client as implied approval); a visible list can revoke it. A player that refuses unpaired access is shown with the reason ("pairing required") and waits for P2.
3. **P2, Pairing PSK**: the player shows a token (`SP:0...`); the user pastes it; the server checks the key in the token against the connection's `client_id`, re-handshakes under the pairing PSK, runs `pair-init`/`pair-finalize`, stores the long-term PSK and re-handshakes to it. Records are listed and removable; the secrets are wrapped by an Android Keystore key.
4. **Gate**: the owner listens (30 minutes, and two players if he has two), the evidence is written to `decisions.md`, and the owner decides.

What the PoC leaves out on purpose: groups and linking, group volume, takeover display beyond an honest status text, `client/time` filter and the player role, fragmentation of large messages (the PoC sends and reads only small messages; a larger one closes the connection), FLAC, code-based pairing, client-initiated mode, the controller and metadata roles.

## Technical Approach

### Packages
`de.yaacc.sendspin.session` (WebSocket, framing, message codec, time filter, connection state machines), `.secure` (Noise `KKpsk2`, identities, pairing records, tokens, key store), `.hub` (server role: discovery, connections, groups, scheduler, controls), `.speaker` (player role: listener, engine). A package named after the protocol is what the other protocols do (`de.yaacc.fcast`, `de.yaacc.yxc`, `de.yaacc.openhome`, and `Snapcast*` classes in `de.yaacc.multiroom`); the draft's neutral name `de.yaacc.multiroom.*` is dropped because `multiroom` now holds the Snapcast code (decision in `decisions.md`, CONFIRM). Android glue in `de.yaacc.browser`, `de.yaacc.player`, `de.yaacc.settings` as for the other protocols. Pure parts have no Android imports.

### Session layer
- **WebSocket** (RFC 6455 subset, decision pending): client handshake (with `Sec-WebSocket-Key`), server handshake (rejects `Origin` header per spec for server-initiated endpoints), frame codec (masking, fragmentation, ping/pong, close), message size cap, idle timeout. One class pair shared by both roles.
- **Connection handshake** (spec "Communication"): `client/init` (cleartext, text frame) -> `server/init` + Noise message 1 -> Noise message 2 -> encrypted `server/hello`, `client/hello`, `server/activate`. The server is always the Noise initiator, whichever side opened the socket. Timeouts 30 s per step; silent failures close without a reply, as the spec defines.
- **Messages**: JSON `{type, payload}` records (platform `org.json` in production, test-only `org.json:json` in JVM tests, as `yxc`), binary IDs (0 JSON, 1 fragment, 4-7 player, 12-15 source), fragmentation for messages above 65518 bytes, ignore rules for unknown types/fields/IDs, out-of-range values close the connection. Immutable value objects per message.
- **Time filter (player role only; the server role just answers `server/time`)**: the two-dimensional Kalman filter with the spec's parameters (`process_std_dev` 0, `drift_process_std_dev` 1e-11, forget factor 2, cutoff 3, `min_samples` 100, drift threshold 2, `max_error_scale` 0.5) and the conversion formulas. Pure class with injectable microsecond clock; unit tests with simulated offset/drift/jitter and with the spec's formulas as table tests. The reference C++ filter (separate repo, license to be checked) is used only to compare outputs, not copied.
- **Clock sync bursts** (player role): at least 8 `client/time` messages per burst, each after the previous reply, a burst at least every 10 s, only the burst's lowest `max_error` measurement feeds the filter, and the first `client/state` waits until the filter's `count` is at least 1 (spec at `2cfe197`). The server role answers `server/time` with the four timestamps (server receive and transmit time taken as late/early as the spec requires).

### Secure layer
- **Noise `KKpsk2`** with `25519_ChaChaPoly_SHA256` and `25519_AESGCM_SHA256`; server = initiator, client = responder; prologue = exact bytes of `client/init` + `server/init`; message 1 payload `{psk_id, psk_category}`, message 2 payload `{}`; transport counters, re-handshake in transport mode (needed to promote a pairing session). Written as a small state machine over library primitives (decision: Bouncy Castle lightweight API), verified against the Noise test vectors and against the reference implementation on the rig (a handshake with `sendspin-python-cli`).
- **PSKs** (spec "Pre-Shared Key"): `psk_id = base64url(SHA-256("sendspin-psk-id-v1" || PSK))`; categories long-term, pairing, Sentinel (published constant); Sentinel fallback on a lookup miss; credential-mismatch signal handling.
- **Identity**: Curve25519 key pair per YAACC installation and role (server identity, player identity); `server_id`/`client_id` = base64url public key (43 chars). Private keys from `SecureRandom`; stored wrapped by a Keystore key (decision); never logged.
- **Pairing PSK flow** (stage P, step P2): the player shows a token `SP:0…` (version 0: 32-byte client key + 32-byte pairing PSK, base32 with `2->9` transliteration, QR alphanumeric alphabet); the server operator pastes it; the server checks the decoded client key against the `client_id` on the connection, re-handshakes with the pairing PSK, runs `pair-init`/`pair-finalize`, persists the long-term PSK with the `client_id`, re-handshakes to it. Pairing records on the player: at least 5, eviction rules from the spec. Token decoding is lenient with input as the spec requires and strict on malformed data.
- **Unpaired access** (stage P server side, Phase 3 player side): per-`client_id` operator approval on the server (never implied for the `source` role); on the player a setting, default off (decision).
- **Phase 4**: dynamic and static pairing codes with CPace (X25519/SHA-512, draft-irtf-cfrg-cpace-21) with the draft's test vectors, commit-and-reveal binding, wrapping, rounds; kill criterion in tasks.

### Server role ("hub")
- **Discovery**: `NsdManager` for `_sendspin._tcp` (server-initiated mode, recommended by the spec), manual `host:port` list; client-initiated mode (advertise `_sendspin-server._tcp` and accept inbound WebSocket connections) is required for conformance and is a Phase 2 stretch with its own task; a service that disappears is dropped after the live-update grace.
- **Connection manager**: one connection per player, serial worker per connection, reconnect rules from `client/goodbye` reasons (`another_server`: do not reconnect, show as available; `shutdown`/`restart`: reconnect; `concurrent_attempt`: retry later with backoff; `unauthorized`/`pairing_required`/`unpaired`: stop, ask the user), backoff on repeated handshake failures. Limit of connected players (default 32), memory caps per connection.
- **Activation and roles**: the server declares `activities: ['playback']` only while its group plays (and drops it when the purpose ends, so other servers can take the player), activates `player@v1` only when approved or paired, never activates a role the client did not list.
- **Groups**: a `HubGroup` has an id (32 random bytes, base64url, sent in `group/update`), a name, the member clients, one queue and one stream timeline. The leader is the group's controlling row in the UI; the others are members. A client is in exactly one group; `client/leave`, `available: false` and disconnects move it to a solo group per the spec; `switch` from a controller client cycles groups (Phase 4).
- **Streaming**: per player, `stream/start` with a format the player lists (PCM 16-bit 44.1/48 kHz first; FLAC and Opus later), audio chunks of 15-150 ms with server-clock timestamps; the first timestamp at least `max(min_buffer_ms + output_delay_ms)` ahead (common send-ahead = the maximum over the group); fill each player up to `buffer_capacity` using the spec's accounting rules; `stream/clear` for seek and track jump (with `from_timestamp` when possible), `stream/end` on pause/stop, `stream/start` again on resume; track changes continue the timeline (gapless). Players that join a playing group get future timestamps only.
- **Audio source**: the PCM tap of the existing feed (`FeedTapChain`, `PcmTapAudioProcessor`, `PcmFormatConverter`, `PcmResampler`) so the queue, seek, gapless and decoding of YAACC stay as they are, as for the Snapcast feed; the converted PCM is chunked and stamped. The PoC paces at real time with a fixed lead (above). The product phase adds the per-player buffer accounting of the spec, so the send-ahead follows each player's `buffer_capacity` and `min_buffer_ms`, and the common send-ahead of a group is the maximum over its members. (verify in task 4.1: how `RealTimePacer` and the slot model of the feed fit several consumers with different leads; if they do not, the Sendspin hub gets its own pacing behind the same tap.)
- **Controls**: `server/command` `volume`, `mute`, `set_output_delay` to players that list them in `supported_commands`; **group volume** with the spec's algorithm (delta, clamp, redistribute, round once, one command per player), group mute (true only when all mute-capable players are muted); state back through `client/state` and `group/update`.
- **Receiver model**: each Sendspin client is a receiver row (synthetic `Device` with id `sendspin:<client_id>`, friendly name from `client/hello`, TXT name before that), showing state (available / in use by another server / needs approval / unpaired), volume, mute, group role (leader, member, solo) like `YxcRowText`. Merging with a UPnP renderer of the same device (IP or `device_info.mac_address`) is optional and decided in Group 1.4.
- **Link UI (MusicCast pattern)**: a link picker lists candidates with disabled reasons (unavailable, taken by another server, not approved/paired, group full); "link" adds the player to this group's stream (connect, approve, `server/activate`, `stream/start` on the group's timeline); "unlink" moves it to a solo group (stream ends); "Play on" a member plays on its group (as `YxcPlayTargets`); the group slider = group volume; a member's slider = its volume; output delay in the member's detail menu.
- **Takeover**: when another server displaces a player (`client/goodbye` `another_server`), the row shows it as available/in use and the group continues without it.

### Client role ("speaker")
- **Endpoint**: one `PlayerEndpoint` per phone, with state (volume, mute, output delay, formats, buffer capacity), that exactly one "driver" controls at a time: either YAACC's own hub (through an in-process adapter, no sockets, no Noise) or a remote server (through the network listener). The spec's admission rules (`playback` activity ranking, last-playback server wins ties) decide who may displace whom; the in-process hub participates as a server with its own `server_id`. Result: a YAACC phone can lead a group with its own speaker as a member, or be taken over by Music Assistant or another YAACC, and take itself back.
- **Listener** (opt-in setting): WebSocket server on a free port (preferred 8928), `/sendspin` path, mDNS registration `_sendspin._tcp` with TXT `path` and `name` via `NsdManager`; rejects upgrade requests with an `Origin` header; admits one connection at a time (more only as the spec allows); provisional connections dropped after 30 s without `server/activate`; limits on message size, fragment buffers and time; stops advertising when disabled or when the app has no reason to run (like the UPnP server service lifecycle).
- **Hello**: roles `player@v1` (Phase 3); `supported_formats` (PCM 16-bit 44.1/48 kHz stereo first, FLAC when the decoder is verified), `buffer_capacity` (a few MB), `supported_pair_methods` (Pairing PSK), `unpaired_access` (setting), `device_info` (product "YAACC", software version, MAC only if obtainable - Android 11+ hides it; omit if not).
- **Player engine** (spike first, own gate; starts from `de.yaacc.multiroom.client`, see Context): decode chunks (PCM direct; FLAC via `MediaCodec` with the STREAMINFO from `codec_header`); schedule each chunk at `compute_client_time(timestamp) - output_delay_ms` using the converged time filter, pace into an `AudioTrack` (streaming mode) using `getTimestamp()` to map frames to the local clock; correct drift by dropping/duplicating single frames (spec: at most 0.5 % speed deviation, accuracy target +-1 ms in steady state, one-shot resync rare); send `client/state` only after the filter has converged; report `required_lead_time_ms` and `min_buffer_ms` from measurements; handle `stream/clear` (with and without `from_timestamp`) and format changes without gaps where possible. Honest limit: Android output latency varies per device, so a manual latency offset is part of the design.
- **Service**: a foreground service with wake and Wi-Fi lock only while a stream plays; notification with the group name and a stop action.
- **Pairing token display**: the player screen shows the token (copy/share); the user pastes it into Music Assistant (or any server). Pairing records can be listed and removed.

### Phase 4 extras
- Controller role (phone controls another server's group: play/pause/next/seek/volume/switch) and metadata/artwork roles (now playing in YAACC's player UI); code-based pairing with CPace; FLAC encoding (hub) and Opus (patent note from the spec); the `source` role (the phone streams a local input into a server, never played locally).

## Interfaces & Contracts
- `WsConnection` (text/binary send, listener, close, limits), `WsListener`/`WsConnector` factories injectable for tests (loopback fake peers, as the existing fake servers with `setCanonicalHostName("localhost")`).
- `SessionCodec` (JSON + binary + fragmentation), `NoiseSession` (handshake + transport, re-handshake), `TimeFilter`, `PairingStore` (keys, records, approvals; interface + file-backed implementation), `PairingToken` (encode/decode).
- `HubConnection` (state machine per player), `HubGroup`, `HubScheduler`, `GroupVolume`, `SendspinDirectory` (players, merged ids, rows), `PlayerEndpoint` with `EndpointDriver` (in-process or remote), `PlayerEngine`.
- Persistence: server/player identities (wrapped), pairing records, approvals, manual player list, settings (all in app-private storage).

## Test strategy
- Pure JVM, tests first: WebSocket framing and handshake, Noise handshake vectors, message codec and fragmentation (malformed sequences from the spec), time filter simulations, token encode/decode with the spec's reference vector, scheduler/accounting tables, group volume tables from the spec's algorithm, admission/arbitration tables ("Multiple servers"), pairing flow with a fake peer.
- Rig (opt-in, Docker): reference player(s) and a reference server (`sendspin-python-cli`/`aiosendspin`, pinned image tags); integration tests: handshake, pairing PSK, play 5 minutes of PCM, link/unlink, takeover, for both roles.
- Manual: owner listens (sync between two players and the phone, takeover, pause/seek/track change).
- Gate per group: unit tests, lint, assemble; reviewer then security-reviewer (the listener, the crypto use, the pairing store and the token handling are the focus).

## Risks (most serious first)
1. **Cryptography and pairing in Java** (Noise correctness, key handling, CPace): mitigation = library primitives only, test vectors, interoperability with the reference on the rig, security review; spike with a kill criterion before any UI.
2. **Player sync on Android** (+-1 ms target vs. device output latency, doze, Wi-Fi power save): spike with the owner's devices, manual latency offset, kill criterion for Phase 3.
3. **Receivers are Cling `Device`s in many places**: answered for this protocol, FCast and Snapcast show the pattern works with a synthetic `Device`; the cost is a handful of `instanceof` branches (task 1.3 lists them). A third and fourth protocol would justify the receiver seam of `2026-11-10-open-device-model/notes.md`; not part of this work.
4. **Ecosystem risk**: young protocol (technical preview in Music Assistant), spec may change: pin to wire `version` 1, track the spec repository, keep each phase releasable.
5. **Listening socket on a phone** (attack surface): off by default, hardened, reviewed.
6. **ExoPlayer with a capture sink** may not give seek/gapless with back pressure: spike; fallback headless decode.
