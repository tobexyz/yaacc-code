### Warning
- [yaacc/src/main/java/de/yaacc/browser/LocalPickController.java:224-252 (`readRows`, `text`)] SI-12 is weakened for folder rows. The folder query reads document id, display name and mime type with `cursor.getString` without any length cap and keeps all of them in `rows` (up to `FolderListing.MAX_ROWS + 1` = 5001 rows) before `DisplayName.clean` and the URI length check run. The existing probe (`ProviderProbe.nameOf`) cuts a name at 1024 chars exactly because of this. A hostile `DocumentsProvider` whose folder the user picks can return rows with strings of up to the cursor window size (about 2 MB each) and make the app hold gigabytes in the Java heap (OOM, the app dies). Remediation: cut every string at read time in `text()` (name 1024 as `ProviderProbe.MAX_NAME_CHARS`, mime type `SharedContentPolicy.MAX_MIME_LENGTH`, document id a few hundred chars, longer id = skip the row) and stop reading when a total character budget for the listing is used; add a test with an oversized row. Optionally also stop the loop when the 15 s call budget is over (the worker thread keeps reading up to 5001 rows after the caller gave up).
- [yaacc/src/main/java/de/yaacc/imageviewer/ImageFragment.java:174 (reached through `QueueItems.direct` -> `LocalImagePlayer.setItems` -> `ImageViewerActivity`)] SI-16 is not kept on the direct path for this phone's images. A picked `content:` uri goes into existing viewer code that logs `"Failed to load image: " + redact(uri)` at ERROR, which is the default log level; `ShareLogRedactor` only removes `/proxy/<key>`, so the picked document uri (its document id usually contains the file path and name) reaches the log (and the log viewer / exports) whenever a picked image cannot be read (grant gone, provider died, decode error). The DEBUG line 102 has the same content. Before this feature that code saw only server URLs and proxy URLs. Remediation: in `loadBitmap` and `loadImage` log the scheme and the exception class only for any `content:` uri (or extend the redaction to `content://` texts); add a unit test for the redaction of a content uri.

### Suggestion
- [LocalPickController.java / ShareService.java, functional with an availability aspect] A refusal of the provider gate is treated as a failed item. The three players of a mixed folder (music, video, images) start together, run `loadItem` on their own timer threads and bind against the SAME provider: `ProviderCallGate` lets one call per provider in (`BoundedCall.callDetailed` returns `isRefusedBusy`), so the others get "busy", `ShareService.prepare` toasts, `AbstractPlayer.skipUnsharedItem` skips the first item(s) and after 3 in a row the player stops. This is the headline scenario of the spec for remote receivers (and for local video). Recommended: in `QueueShareBinder.bind` (worker side, never the main thread) retry a busy refusal a few times with a short pause (bounded, e.g. 3 x 500 ms), or open the first items one after another in `PlayerService.createQueuePlayers`/the start loop. Not a confidentiality issue (the share is never created), so no Warning.
- [AbstractPlayer.java:365-440, `play()` / `stop()`] While a share is bound inside `loadItem(int)` (open up to 20 s, copy fallback up to 5 min, SI-13) `isProcessingCommand()` is true, so `stop()`/`pause()` calls are silently ignored for that time and the bind cannot be cancelled. `onDestroy` still closes the lease (`closeShares` never waits), so no share leaks. Consider making `stop()` remember a request that arrives during a bind and honour it at the end, or at least show the "copying" state.
- [QueueShareWindow.java Lease, AbstractPlayer.java:820-835 `moveTo` / `drop`] Narrow race: `drop()` (stop) running between `acquire(index)` returning true and `held.add(index)` leaves that share bound after the stop. It is released by the next move, `close()` on destroy, the 6 h absolute maximum of the registry, so bounded, and `stop()` normally cannot overlap a bind (see the point above). A `dropped` generation counter checked at `held.add` would close it.
- [ShareService.java:112-170 / AbstractPlayer.java:`skipUnsharedItem`] Toast volume: every failed bind toasts (`share_open_failed`/`share_busy`) and the player may fail on every second file of a 500 file queue (provider gone for some files), per player, up to 8+ players. The system caps the queue (50) but the user is flooded with LONG toasts. Consider one notice per player and queue.
- [PlayerService.java:378-411, `ShareLimits` 8 active shares] A queue needs one share per player (types x receivers). With 3 receivers x 3 types (9 players) or one dead receiver whose playback never ends (share lives until the player is destroyed, 6 h at most) the 8 registry slots are used up and the user's single file shares from other apps are refused with "registry full" (and the other way round). The failure is clean (hasRoom before any file is opened, SI-14 ownership kept) and `ShareLimits` is unchanged (SI-17), so this is by design; consider a per-queue cap (for example 6) or a visible hint, and keep the known limitation in docs/tech.md.
- [LocalPickController.java:82-84] Third static `BoundedCall` pool ("pick-provider", own `ProviderCallGate`). SI-12 "at most one call in flight per provider" now holds per pool: a hung provider can pin one thread in each of the intake probe pool, the pick pool and the share pool (3 threads, daemon, pool max 4 each, `AbortPolicy`, no unbounded growth). Document it in the SI-12 text, or share one pool/gate between the three if the thread budget matters.
- [LocalPickController.java:70-75] The single static `WORKER` thread runs the probe (up to about 23 s), the folder listing (15 s) and `initializeQueuePlayers` (`waitForPlayerServiceComeUp`, `awaitReceiverDevices` up to about 7.5 s) one after the other, with an unbounded queue (user driven, no growth risk). A slow provider delays the start of an unrelated confirmed queue. A second executor for the start would decouple them. An `Error` thrown in `work.call()` (not caught, only `Exception`) would skip `then`/`finish` and leave the flight to the `ActionFlight` watchdog and the receiver selection unrestored; catching `Throwable` there is cheap.
- [PlayerService.java:384-411] `createPlayer(...)` is called before the items are known; `built.items().isEmpty()` then `continue` leaves a created, never added player (and an exception half way leaves the already added players idle in the service without items played). Create the items first, or shut the player down on that path. Also `LocalImagePlayer.setItems` puts all picked uris into one intent extra: 500 uris of the maximum 2048 chars can exceed the 1 MB binder limit (`TransactionTooLargeException` from `startActivity`); realistic folder uris are far below, so only a robustness note.
- [PlayerService.java:392-393] "this phone" is detected by `UpnpClient.LOCAL_UID.equals(udn identifier)`. If a local device ever reports another id the audio and image players fall back to placeholder + share with loopback allowed (still safe, just not the direct path). A test on `createQueuePlayers` with the real local device would pin it.
- [docs/tech.md] Add the new points to "Security invariants" (queue: one share per player, release by `remove`, stale url answers 404, addresses fixed at player creation) and to "Known limitations" (local video app gets the proxy url; direct content uris of this phone are readable by this app only, no share).

#### Invariant check (what the new path keeps or weakens)
- SI-1/SI-2/SI-3 (keys, registry, request chain): kept, no change; `ShareRegistry.hasRoom` is read only under the registry lock. A released queue share is `registry.remove` (closed at once, not the 10 minute grace); a request for the old key gets the constant 404; keys are never reused (last 256 remembered, 128 bit), so the stale proxy url left on an item cannot reach another file.
- SI-4 (addresses): kept. Per player the set is resolved once in `createQueuePlayers` from that player's device only (singleton id), copied by the binder and passed to every later `prepareFor`; a receiver that was not chosen is not in the set, an empty set denies, the restriction default is untouched. The set is resolved after the confirm on the worker thread from the stored selection (like the browse "Play on..." path), not literally at the confirm, but always consistent with the receiver the player is created for.
- SI-11 (pending state): kept. Before the confirm only bounded type/name/listing queries run; nothing is opened, copied or registered; the picked action uses the existing flight/guard; closing the fragment drops the pick.
- SI-12 (provider calls): kept for probe (gate, 3 s per call, 20 s total, name cut at 1024) and for opens (bind uses `ShareService.PROVIDER_CALLS`, 20 s), never on the main thread; weakened for folder rows (Warning 1) and per-pool gate (Suggestion).
- SI-13 (copy fallback): kept. Copies happen just in time, one at a time, names from `SecureRandom`, budget min(512 MiB, 1 GiB minus used), deleted when the share is removed; a queue never holds N copies (one per player).
- SI-14 (ownership): kept. `prepare` registers as unclaimed, the binder claims at once; `QueueShareWindow` releases a late bind after a close; claim/release idempotent; `Lease.close` is final and never waits for a bind; the 2 minute sweeper cannot take a claimed key; `ShareLifetimeListener` releases the bound key of a removed player with the grace as a second net.
- SI-16 (logging, toasts): all new code logs fixed texts and class names; toasts are fixed resources with counts only; broken only through the existing `ImageFragment` log (Warning 2).
- SI-17 (limits): unchanged (no `ShareLimits` change in the diff). SI-18 (surfaces): no manifest, permission, dependency or preference change; no new exported component (`ImageViewerActivity` is exported already; it receives the picked uris through an explicit intent of this app).
- SI-19 (picker UI): the receiver picker title is the fixed text "Files: N" through the cleaner; no provider text reaches the screen.

#### Other points checked, no finding
- Untrusted provider text: names cleaned (`DisplayName`, 200 chars), mime type only through `SharedContentPolicy.chooseMimeType`, size is a number (<= 0 means none), non `content:` schemes, `file:`, non-ASCII/over-long uris (2048) and this app's own providers (`OwnProviders`, fail closed on exceptions) are rejected for picked files and the tree; child uris are built with `buildDocumentUriUsingTree` on the checked tree authority (id is percent-encoded, same authority), so a row cannot point at another provider; a hostile id can only name a document of its own provider.
- Direct content uris on this phone: only uris the user picked (or listed below the picked tree through the tree grant) go to ExoPlayer/`ImageFragment`; both use the app's own grant; a provider cannot redirect to another authority; no `FLAG_GRANT_*` is added; the grant is temporary (no persistable permission).
- Folder listing bounds: 5000 rows, 15 s call, no recursion, directories skipped, 500 queued files.
- Registry/DoS: at most one share per player, 8 slots, `hasRoom` before any open; executors are bounded (`BoundedCall` pool with `SynchronousQueue` + `AbortPolicy`, one daemon worker); no unbounded thread growth.
- Receiver selection (`setReceiverDeviceIds` / `afterStartHook`): same global-selection pattern and single flight as the browse and intake actions; the previous selection is read at confirm; `finish` runs exactly once on all paths (rejected worker, empty result, exception in `play()`).

### Verdict: FAIL
Two Warnings (unbounded folder row strings, picked uri in the default-level viewer log). No Critical. Re-review after both are fixed and tested.
