# Security Review: Receivers on the server page

## Cycle 1 — 2026-11-08
Reviewing: the whole change (uncommitted diff on `prepareRelease` plus the new files): `ReceiverLiveUpdates`, `AdapterPositions`, `SectionHeaderAdapter`, `SectionHintAdapter`, changes in `ServerListFragment`, `DeviceSheetAdapter`, `DeviceSheetFragment`, `BrowseDeviceAdapter`, `ServerListClickListener`, `ContentListFragment`, `fragment_server_root.xml`, strings in 7 locales.

Scope notes: "new" = introduced or made reachable by this change; "pre-existing" = already in the device sheet / Receiver tab (`ReceiverRowBinder`, `RendererStatusMonitor`, `MonitorSubscriptions`, `YxcMonitor`, `ReceiverVolumeLiveUpdater` are not in the diff).

### Critical
- none

### Warning
- [ServerListFragment.java: `deviceAdded`/`deviceRemoved`/`deviceUpdated` -> `populateDeviceList` -> `refreshReceivers`; ReceiverLiveUpdates.java `devicesChanged`; RendererStatusMonitor.java `subscribe`/`MonitorSubscriptions.java`] **Unbounded device count on an always-on landing screen (availability, hostile LAN).** NEW exposure of a PRE-EXISTING mechanism.
  - What is bounded: rows on screen (RecyclerView recycles; `ReceiverVolumeLiveUpdater` only reads visible rows, 3 pool threads, one request per receiver); YXC/group feed (`YxcMonitor.MAX_DEVICES = 64`); binder executors (shut down in `release()`).
  - What is not bounded: (a) `RendererStatusMonitor.subscribe` starts one 10 s poll chain per device in the registry; there is no cap, `polledDevices` and `statusMap` are never pruned for devices that left the registry, and all chains share one single-thread executor. A LAN host that announces many fake receivers (distinct UDNs, each with a description offering AVTransport) creates that many chains; each failing request holds the shared executor until its timeout, so status updates of real receivers starve, and the chains live as long as any listener stays subscribed. (b) every registry event (add/remove/update, no debounce) now runs `DeviceSheetAdapter.refresh()` (rebuilds and diffs all entries) and `devicesChanged()` (re-subscribes status monitor and group feed with the full list) on the UI thread, so an announce/byebye flood costs O(devices) UI-thread work per event.
  - Why new: before, these lived only while the sheet was open (short) or on the Receiver tab; the sheet did not even rebuild on device events in normal mode. Now the screen the app lands on does it for as long as it is started (until a server is opened, the view is destroyed and everything stops: verified, `showContent` uses `replace`, `onStop`/`onDestroyView` call `receiverLive.stop()`).
  - Mitigation: cap the devices passed to the status monitor (same idea and order of magnitude as `YxcMonitor.MAX_DEVICES`, e.g. in `ReceiverLiveUpdates.forApp.subscribeStatus` / `MonitorSubscriptions.subscribe`), and coalesce `refreshReceivers()` (post once on the main-thread handler with a short delay, e.g. 300 ms like `DeviceSheetFragment.PICK_REFRESH_DELAY_MS`, and remove the callback in `onDestroyView`). Optionally drop chains of devices no longer in the registry. A small unit test for the cap in `MonitorSubscriptions`/`ReceiverLiveUpdates` is enough.

### Suggestion
- [ReceiverRowBinder.java:242, 263, 266, 1162] (PRE-EXISTING, but now run on the landing screen) device-supplied strings reach the log uncleaned: the icon URL (`"Device icon uri:" + iconUri`, on every row bind), `device.getDisplayString()` (friendly name) and `e.getMessage()`. Debug/warn level only, but a friendly name with line breaks can forge log lines. Wrap in `de.yaacc.util.LogText.clean(...)` as `UpnpClient.logDevicesOnce` and `RendererStatusMonitor` already do. The new code itself logs nothing from devices.
- [RendererStatusMonitor.java] (PRE-EXISTING) prune `statusMap` and the poll chain of devices that left the registry (see the warning; also a slow leak with legitimate devices over a long session).
- [ServerListFragment.java `onResume`] (PRE-EXISTING) a new `Thread` per resume for `populateDeviceList`; not related to this change.

### Checked, no finding
1. **Untrusted LAN data to views.** New code adds no device strings to views: the headers use `setText(@StringRes)`, the hint text is fixed in `server_list_section_hint.xml` and `onBindViewHolder` does nothing; strings in all 7 locales are plain text (no markup, no format specifiers). Receiver rows are the unchanged `DeviceSheetAdapter`/`ReceiverRowBinder` rows: friendly names, track titles and session names go through plain `setText` (the cleaned/`cleanText` paths in the picker), there is no `Html`, `Linkify`, `setHtml`, `WebView` or `autoLink` in these classes or layouts (the `autoLink` hits in `device_sheet_player_session_item.xml` and `mini_player_row.xml` are comments saying there is none). Icons and album art still go through `IconDownloadTask` (unchanged).
2. **Leaks and callbacks after stop.** `ReceiverLiveUpdates.stop()` clears `running`, removes the poller, stops the volume updater, unsubscribes the status listener, stops and nulls the group feed (so `YxcRowFeed` removes its busy listener and its `YxcMonitor` subscription) and removes the player listener; every callback checks `running`, the poller does not reschedule once stopped, `start` is idempotent. The page calls `stop()` in `onStop` and again in `onDestroyView`, then `release()` (volume updater `stop()` + `ReceiverRowBinder.shutdown()` stops the single executor and `shutdownNow` on the group-volume pools) and nulls adapter and hint; `ServerListFragment` is also removed as `UpnpClientListener` there, and the `onRefreshed` lambda null-checks. `devicesChanged()` is a no-op while stopped. `ReceiverVolumeLiveUpdater` drops late answers by generation and removes the system volume listener. Calling `YxcRowFeed.start` and `subscribeStatus` repeatedly is safe: `addBusyListener` uses `addIfAbsent`, the status listener is `addIfAbsent`, `YxcMonitor.subscribe` de-duplicates listeners and caps devices. The shared `RendererStatusMonitor` is a reference-counted singleton: the page and an open sheet subscribe as separate listeners and polling stops only after the last one leaves. Battery: 2 s poll of local status plus visible-row volume reads is the same cost as the open sheet, but it runs while the landing screen is started (not in the background: stopped in `onStop`).
3. **Exported surface.** No change to `AndroidManifest.xml`, no new components, intents, permissions or receivers; no new `PendingIntent`s or file/URI handling. `ReceiverLiveUpdates.Sources.forApp` takes `UpnpClient` and a main-looper `Handler`, nothing is broadcast.
4. **Logging.** See suggestion above; the new classes log nothing. `searchDevices()` only shows a toast with a fixed string.
5. **Position handling.** `ServerListClickListener` and the `BrowseDeviceAdapter` key handler now use `ViewHolder.getBindingAdapterPosition()` via `AdapterPositions.bindingPosition`, i.e. the position in the servers adapter, not in the whole `ConcatAdapter`; `NO_POSITION` (row being removed) returns without acting, so a tap cannot select a neighbouring or stale provider (previously the plain `getChildAdapterPosition` would have selected the wrong server once the header was added; the fix closes that). `DeviceSheetAdapter` row clicks/actions resolve the entry through `holder.getBindingAdapterPosition()` (already so) or capture the row's own device at bind, and `visibleReceiverRows` now maps rows by their position in this adapter (`getBindingAdapter() == owner`), so volume/mute reads and updates target the row's device, and rows of other adapters or of other types are skipped. The remaining `getChildAdapterPosition` uses are in adapters that are not part of the `ConcatAdapter` (content list, receiver tab, player list).
6. **Other.** `TooltipCompat.setTooltipText` with a fixed string resource; the item animator tweak is cosmetic; no new dependencies, no new network endpoints, no changes to build files.

### Verdict: FAIL
One Warning (unbounded polled devices and unthrottled rebuilds on the new landing screen). Availability-only on the local network and small to fix; no Critical. After the cap and the debounce the expected verdict is PASS.

## Cycle 2 — 2026-11-08
Reviewing: the fixes for the cycle 1 Warning: `ReceiverLiveUpdates.MAX_RECEIVERS` / `watched(...)`, `Coalescer` (+ `CoalescerTest`, `ReceiverLiveUpdatesTest`), their use in `ServerListFragment`, `DeviceSheetAdapter.refresh()` and `ReceiverLiveUpdates.forApp`.

### Critical
- none

### Warning
- none (the cycle 1 Warning is resolved, see below)

### Suggestion
- [RendererStatusMonitor.java / MonitorSubscriptions.java] (PRE-EXISTING, follow-up already in decisions.md) the cap bounds the receivers polled at one time (64), not over time: `subscribe` is additive and `polledDevices`/`statusMap` are only cleared when the last listener leaves. A host that keeps rotating fake UDNs that sort into the first 64 still adds one 10 s chain per new UDN while the page is started. This needs a sustained, active attacker (each device must be announced and its description fetched), costs one request per 10 s per chain, and is slow compared with the former flood; pruning chains of devices that left the registry closes it. Worth doing soon, since the page is the landing screen.
- [ReceiverLiveUpdates.watched, ordering] the cap keeps "this phone first, then by name", so a hostile host can name fake receivers to sort before real ones and push real receivers out of the 64 (they then are not listed or polled). This is inherent in any cap, availability only, and no worse than the flood it replaces; no change needed, but it is why 64 should not be lowered.
- [Coalescer.java doc] the doc says "a little after the last of a burst"; the implementation runs 300 ms after the first trigger of a burst (a trigger while one is pending does nothing), so a continuous flood gives at most one rebuild per 300 ms rather than none until it stops. That is the better behaviour for the UI (no starvation) and the rate is bounded; only the wording is imprecise.
- [ReceiverRowBinder.java:242, 263, 266, 1162] (PRE-EXISTING, follow-up in decisions.md) uncleaned device strings in the log.

### Checked
1. **Cap applied consistently.** `watched()` is used for the status monitor subscription, the group feed (`YxcRowFeed.start`, itself capped at 64 by `YxcMonitor`) and the rows in `DeviceSheetAdapter.refresh()`, so rows, polled devices and the volume candidates (visible rows only) all come from the same first 64; the order is the registry's (local dummy device first, then by name), so this phone is never dropped. The helper copies at most 64 entries and handles a smaller or empty collection.
2. **Truncating the list in the sheet.** `DeviceSheetAdapter` serves the sheet, the picker and the page, so all three now show at most 64 receivers (before: unbounded). Players are not truncated: sessions of a device outside the cap still get a session row (the existing "device not in the list" path via `receiversById.containsKey`, grouped by `DeviceSessionGrouper`), so no session becomes unreachable and no action can target the wrong device (rows resolve their entry by binding position as before). The classic Receiver tab is unchanged and not capped (pre-existing). Realistic households have a handful of receivers, so the limit is not a usability risk.
3. **`devicesChanged()` per coalesced refresh.** It now runs at most once per 300 ms burst; with the cap it passes at most 64 devices to `subscribe` calls that de-duplicate (`addIfAbsent`, `polledDevices.add`, `YxcMonitor` known-UDN check, `addBusyListener` `addIfAbsent`), so a repeated call starts no new chain and no new listener. The UI-thread cost per rebuild is bounded by 64 entries plus the player list.
4. **Cancelled or late runnable.** `Coalescer` is main-thread only; `cancel()` clears `pending` and removes the exact runnable, and the runnable clears `pending` before running, so a late run cannot be double-scheduled. `onDestroyView` cancels it and nulls it; the action `refreshReceivers` null-guards `receiverAdapter` and `receiverLive`, so a runnable that was already dispatched cannot touch a released adapter (it runs on the same thread, in order). A `populateDeviceList` lambda queued before `onDestroyView` null-checks `receiverRefresh` and calls `refreshReceivers` only through the guard. The first build is immediate (adapter set up in `populateDeviceList`), later events only trigger the coalescer. The runnable references the fragment only until cancelled, so no leak past `onDestroyView`; a new view creates a new coalescer.
5. **No new surface.** No manifest, permission, intent, dependency or logging change in the fixes.

### Verdict: PASS
Zero Critical, zero Warning. The cycle 1 Warning is fixed: the number of receivers that are listed, polled and watched is bounded at 64 and the rebuild rate on device events is bounded at one per 300 ms. Remaining items are Suggestions (pruning of poll chains over time is the one to schedule first).
