## Cycle 1 — 2026-10-02
Reviewing: Group 2 tasks (commits `c14950a` "feat: wire sort into music and video browsers (Group 2, partial)" and `e40d279` "feat: wire sort into image, SAF, and synthetic folder browsers (Group 2)")

Confirmed Group 2 correctly builds on the Group 1 `SortSupport` API (`toMediaStoreSortOrder`, `toComparator`, `formatEpochMillisAsDate`) as shipped — no re-review of `SortSupport`'s own internals (already PASSed above).

### Critical

- **`MusicAlbumsFolderBrowser.java:104-133`, `MusicArtistsFolderBrowser.java` (same pattern), `MusicGenresFolderBrowser.java` (same pattern), and `ImagesByBucketNamesFolderBrowser.java:97-126`** — four container-listing browsers fetch cursor rows (now correctly SQL-`ORDER BY`-sorted via `SortSupport.toMediaStoreSortOrder`) but funnel every row through `Map<String, X> folderMap = new HashMap<>()` keyed by id, then iterate `folderMap.entrySet()` to build the returned `List<Container>`. `HashMap` iteration order is unspecified and derived from key hash buckets, not insertion order — it has **no relationship** to the SQL sort order the cursor was just read in. The result: a client sending `SortCriteria="-dc:title"` (or any `SortCriteria`) against the Music→Albums, Music→Artists, Music→Genres, or Images→"By bucket name" container listing gets back containers in essentially arbitrary order, not the order it asked for. This directly contradicts this spec's primary Goal ("A `Browse` request's `SortCriteria`... actually determines the order of returned containers/items...") and Success Metric ("...receives results in that order for music, images...") for four of the twenty browsers — the SQL-level sort work is real but is silently discarded one step later. This was self-reported by the implementing agent for the three music browsers per the task brief but not fixed, and the same defect exists unreported in `ImagesByBucketNamesFolderBrowser`.
  - **Fix**: replace `HashMap` with `LinkedHashMap` in all four files (insertion order == cursor iteration order == the SQL-sorted order), or sort the final `result` list directly instead of relying on map iteration. `LinkedHashMap` is the minimal, lowest-risk fix — insertion already happens in cursor order, so switching the map type alone makes `entrySet()` iteration order match the SQL sort with no other logic change.
  - Note: this does *not* violate the "unchanged when `SortCriteria` is empty" regression constraint — the default `sortOrder` passed to `toMediaStoreSortOrder` is unchanged, and the `HashMap`-scrambled iteration order was already present (and equally undefined) before this spec for the "no criteria" case, so default-order behavior is bit-for-bit identical pre/post change. The defect is specifically that the *new* sorting feature never actually reaches the client for these four content types.

### Warning

- **`SafFolderBrowser.java`** (all four `browseContainer`/`browseItem` branches) — correct sorting requires seeing the whole folder before paginating (you cannot sort a slice), so the switch from windowed iteration (`for (i = start; i < end; i++)`) to full enumeration (`for (i = 0; i < size; i++)` into `allFolders`/`allItems`, then sort, then `subList(start, end)`) is a necessary consequence of this spec's goal, not a design mistake. However, for the *items* paths specifically, "enumerate the whole folder" now means calling the full `createItem(...)` pipeline (SAF metadata cache lookup, MIME-type sniffing/guessing, `ProtocolInfo` resolution, URI construction — each with its own timing instrumentation already in the code, suggesting this was known to be non-trivial per-item work) for **every** file in the folder on **every** `Browse` call, not just the requested page window as before. `design.md`'s own non-functional constraint explicitly flags "avoid introducing N+1 query patterns or materializing entire large collections in memory" as a risk for this spec; this SAF change is exactly that pattern for folders with many files (e.g. a SAF-mounted folder with hundreds/thousands of files, especially over a slower `DocumentsProvider` such as a cloud-backed one), and there's no size-based guard or lazy/lightweight-key-first approach (e.g. sort by raw `DocumentFile.getName()`/`lastModified()` first, then only run `createItem()` on the sliced window) to cap the cost. Not blocking a correct-order requirement, but worth flagging given the explicit design-level risk callout; a follow-up could sort using cheap keys (name/lastModified read directly off `DocumentFile`, no metadata-cache/MIME lookups) and defer `createItem()` to the post-slice window.

- **`ImagesAllFolderBrowser.java` / `ImageAllItemBrowser.java`** — both are explicitly named in Group 2's "Image browsers" task file list and the task's Accept criteria requires `dc:date`/`DATE_TAKEN` wiring "where `ImageByBucketNameItemBrowser`/analogous item browsers" apply, but neither file was touched by this commit pair (confirmed: file mtimes/content unchanged since Group 1; `git show e40d279^:...ImagesAllFolderBrowser.java` and the current file are identical except Group 1 history). Concretely: `ImagesAllFolderBrowser.browseItem`'s projection never includes `MediaStore.Images.Media.DATE_TAKEN`, and its `createPhoto(...)` call still uses the old 9-arg (no-date) overload, even though its `columnMap` *does* map `PROPERTY_DATE → DATE_TAKEN` for `toMediaStoreSortOrder` purposes. Net effect: a `SortCriteria="-dc:date"` request against "All images" will still come back correctly ordered (SQL `ORDER BY` doesn't require the column to be in the `SELECT` list), but the returned `Photo` items will have no `dc:date` property at all — inconsistent with the "By bucket name" image path (which does expose it) and short of the stated Goal ("images: `DATE_TAKEN`... just unwire the gap") for this specific, heavily-used browsing path. `ImageAllItemBrowser.browseMeta` (single-item metadata lookup) has the same gap for the same reason. Not order-breaking (Critical bar not met), but a real completeness gap against the task's own file scope.
  - **Fix**: add `MediaStore.Images.Media.DATE_TAKEN` to `ImagesAllFolderBrowser`'s projection and `ImageAllItemBrowser`'s projection, parse it the same way `ImageByBucketNameItemBrowser` does (`null` fallback, not `0L`), and pass it through to the new `createPhoto(..., Long dateTaken)` overload.

### Suggestion

- `SafFolderBrowser.java` subfolder-listing branches (`browseContainer`'s "Browse subfolder" and `browseItem`'s "Browse subfolder items") — switching from "paginate-then-filter" (old: slice the raw `files[]`/path-list window, then filter to directories/non-directories within that window) to "filter-then-paginate" (new: filter the whole list first, then slice) is a side effect of enabling correct sorting, and it actually *corrects* a pre-existing pagination inconsistency (old code's page boundaries were computed over raw, unfiltered indices, so a page could return fewer entries than `maxResults` even when more matching entries existed further down the list). Worth a one-line code comment noting this intentional, independently-beneficial side effect, since a future reader diffing against "no behavior change when `orderby` is empty" might otherwise mistake it for scope creep.
- `MusicAlbumsFolderBrowser`/`MusicArtistsFolderBrowser`/`MusicGenresFolderBrowser`/`ImagesByBucketNamesFolderBrowser` — once the Critical `HashMap`→`LinkedHashMap` fix above lands, consider a short code comment at each `folderMap` declaration noting *why* map ordering matters here (ties directly to the SQL `sortOrder` just built), so a future refactor doesn't silently reintroduce a plain `HashMap`.
- `SortSupport.toComparator` callers that pass a possibly-null-producing accessor (e.g. `SafFolderBrowser`'s `item.getFirstPropertyValue(DIDLObject.Property.DC.DATE.class)` for items whose `lastModified()` was `0`/unknown) rely on `SortSupport`'s internal `Comparator.nullsFirst(...)` wrapping to avoid an NPE — confirmed correct by inspection, but it'd be worth a one-line comment at the `ITEM_ACCESSOR_MAP` declaration noting that `null` dates are expected and handled, since it's not obvious from the accessor's call site alone.

- **`SafFolderBrowser.java:343-359` / `:399-412`** (both `browseItem` branches) — the accepted trade-off the implementing agent flagged in the `0115105` commit message is real and worth recording, but doesn't rise to a blocking finding. Mechanics: `candidates` is built and sorted cheaply (no `createItem`), then sliced to `[start, end)`, and `createItem(...)` runs only on that slice; if `createItem` returns `null` for an item in the slice (SAF metadata-cache miss or unresolvable MIME type — `isPlaylist(...)` already pre-filters the one previously-unfiltered failure mode, m3u files, out of the candidate pool entirely, so this specific residual case is narrower than it looks at first), that slot is silently dropped rather than backfilled from `candidates[end]` onward, so `NumberReturned` can come back less than `maxResults` even though more valid candidates exist further down the (already-sorted) list. Traced this against both the UPnP ContentDirectory:1 spec and the pre-existing codebase baseline before concluding it's non-blocking:
  - **Spec tolerance**: `Browse`'s `RequestedCount`/`NumberReturned` contract explicitly allows `NumberReturned < RequestedCount` — a control point is expected to continue from `StartingIndex + NumberReturned`, not assume short pages mean end-of-list. This isn't a protocol violation.
  - **Not a new regression vs. the true baseline**: read `SafFolderBrowser.java` as of `c14950a^` (immediately pre-Group-2) — the original `browseItem` windowed `[start, end)` directly over raw `sortedPathes`/`files[]` indices and silently dropped `createItem`-null items from the result *without* re-indexing the window, i.e. the exact same raw-index-vs-valid-item-count mismatch existed before this entire spec touched the file. Group 2's intermediate (pre-Fix-Group-1, now superseded) full-enumeration version incidentally fixed this as a side effect of filtering nulls before slicing, but that was never the thing Cycle 1 asked to preserve — Cycle 1's Warning was specifically about the performance cost of full enumeration, and fixing that necessarily means accepting back this long-standing, pre-spec pagination characteristic rather than inventing a new one.
  - **Worked through the actual failure mode**: because `end` (next page's lower bound minus unreturned count) only ever grows by `maxResults` per request while `start` advances by `NumberReturned` (`<= maxResults`), the practical effect of a mid-page `createItem` failure is a **duplicate** item on the following page (the un-backfilled slot gets revisited), not a silently lost item — `start` never jumps past unprocessed candidates, so the loop still terminates and nothing is permanently dropped from view across a full pagination run.
  - **Trigger is narrow**: requires a SAF metadata-cache miss or unresolvable MIME type specifically on a page-boundary file, in a folder whose owner has already granted SAF access — not sorting-related, not security-related, and orthogonal to the dates/titles this spec cares about.
  - **Recommended low-cost follow-up** (does not block this PASS): advance `end` to backfill from `candidates` past the initial slice until `maxResults` valid items are collected or `candidates` is exhausted, which would close the gap entirely at near-zero added cost in the common (all-succeed) case, since it only does extra work when a failure actually occurs within the slice.
