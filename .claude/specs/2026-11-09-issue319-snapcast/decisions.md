Condensed on 2026-11-17, before the branch `feat/issue319` was squashed. The per-group, per-cycle log of the earlier versions (727 lines) is gone from the history after the squash; this file keeps every decision that still holds, grouped by topic, the newest decision winning. ## 1. Scope and product decisions (owner)

- **2026-11-09 Scope.** Phase A: YAACC feeds a snapserver and controls it. Phase B: the phone as a client (plain Java protocol, no native code). YAACC is never a snapserver. No dynamic linking: Snapcast has no way to move a client to another server (verified in the sources and again in the control/binary protocol documents on 2026-11-16). The 2026-11-09 rule "Phase B only after Phase A is released" was replaced on 2026-11-11 by the owner's request: Phase A was tested on his device (music plays on several Snapcast devices at once; not every check of the list was run), Phase B (Groups 7 to 10) started then, keeping the kill criterion of Group 8.
- **2026-11-17 Idea: a Snapcast SERVER inside the app (owner asked, not decided).** The owner asked whether YAACC could be a snapserver itself. The feasibility was answered in the conversation (the answer is not recorded in the repository files); the result is: needs its own spec first, nothing is started. It would revise the standing decision "YAACC is never a snapserver" and relates to the parked Sendspin spec (`.claude/specs/2026-11-24-issue325-sendspin/`, server role) and to `notes.md` variant V2.
- **2026-11-09 One receiver per Snapcast group** (owner's choice). A group is the receiver row, its clients are members with their own volume; group changes use `Group.SetClients` / `Group.SetStream`; a group that loses its last client disappears. The synthetic device is never in Cling's registry (never advertised); it appears in `getDevicesProvidingAvTransportService()` and resolves by `getDevice(id)` (design.md "Inventory result").
- **2026-11-09 Runtime stream creation** (owner's choice). YAACC adds one tcp stream per phone and server at runtime (`Stream.AddStream`, name `YAACC <phone name> <marker>`) and removes it when idle; it never takes a stream URI from server data. 2026-11-14: the owner chose option (d) for the old "static source fallback" hint: no fallback exists; the hint text is the true sentence "The server must allow adding a TCP stream source at run time." (7 locales, key `snapcast_feed_static_source_hint` and constant `HINT_STATIC_SOURCE` unchanged on purpose). The hint is attached to REFUSED, NO_FREE_PORT, CONFLICT and "another stream id"; for the two middle cases it is true but not the cause (the reason in brackets is). A hint-free toast there is a one-line change in `SnapcastStreams` if the owner wants it.
- **2026-11-09 Neutral names.** Package `de.yaacc.multiroom` (`protocol`, `control`, `discovery`, `feed`, `client`); "Snapcast" is a product name in strings, docs and class names `Snapcast*`, never the package. Open for veto (Snapcast is GPL software, not a brand like Yamaha). GPL: no Snapcast code copied; wording "version 3 or, at your option, any later version" everywhere.
- **2026-11-09 Authentication out of scope.** A server that requires authorization (Basic) gives a clear error row; no credentials are stored (host:port only; `@` in an entry is refused).
- **2026-11-13 Codecs deferred (owner).** The Phase A feed is codec independent (raw PCM, the server encodes). The phone's client plays `pcm` and `flac` only; `ogg` and `opus` are refused with a typed reason; Opus/Vorbis is a possible future enhancement (task 11.9) and the docs say so.
- **2026-11-14 Renderer output (owner).** The YAACC renderer (AVTransport and OpenHome) has the output *This device* (default) or *Snapcast group* (server and group chosen in the renderer settings). In group mode it ONLY feeds that group (the Phase A feed) and maps volume and mute to the group; it does not add the phone's own client to the group and does not start the Phase B client; which clients are members is the user's decision (link sheet). It makes YAACC a UPnP wrapper for a Snapcast server. This replaced the Group 8i plan to put the phone's client into the fed group.
- **2026-11-14 Discovery default ON (owner), reverses security review S19.** `settings_snapcast_discovery` is on by default; a value that cannot be read counts as off; an install that stored false keeps it. Cost accepted: mDNS queries on the network from the first screen and a control connection to every announced server; announcements are unauthenticated (S70). Text and docs say so in 7 locales.
- **2026-11-16 Play default ON (owner, 12.20).** `Play to Snapcast groups` is on by default (`SnapcastSettings.PLAY_DEFAULT`, one place in code and `preference.xml`); a stored false is kept; a damaged value counts as off. The Snapcast client option stays off by default.
- **2026-11-15 Wording (owner).** "experimental" / "not tested on a device yet" removed from user texts, README, docs and CHANGELOG (12.20); the facts stay (unencrypted audio, any device that reaches the renderer changes the group's volume and mute, PCM/FLAC only, sync depends on the device). 2026-11-17 (12.22): no "listen test", "Hörtest" or "Spike" in user-visible texts; entries are *Snapcast client* (option), *Connected to the Snapcast server* (state), *Snapcast client details* (sheet); keys, classes and layout ids unchanged. 2026-11-17 (12.23): the Hello `Version` is `<YAACC server name> <app version>` ("Yaacc 6.1.0"; generic "YAACC 6.1.0" for a public address; cleaned, at most 40 characters); `OS` Android, `Arch` unknown, `ClientName` YAACC, MAC all zeros. Old log texts keep their old wording (records).
- **2026-11-15 Logo.** The text name "Snapcast" stays on cards and in docs, with a not-affiliated notice; no logo (the Snapcast repository has no statement about logo, name or trademarks; no legal advice). A draft question to the maintainer is in `snapcast-logo-question.md`; the owner posts it himself (open).
- **2026-11-15 Process (owner).** (a) Review depth: one general and one security review per group; after a failed review the orchestrator verifies the fixes (tests, the reviewer's mutation checks, a read of the diff), no second review round unless a fix adds new logic; the review of Fix Group 9d was finished, no further security cycle for Group 9. (b) The confirmation review of Group 12A was skipped; all of Group 12 gets one general and one security review at the end (still postponed on 2026-11-17, see tasks.md). (c) Tests: agents and the orchestrator run ONLY the tests they add or change (`--tests`), never the whole suite or lint; the owner runs both. Consequence: regressions elsewhere are found by the owner's run (see tasks.md T.1 to T.5).

## 2. Control library (`multiroom.control`, Group 2)

- **Timeouts and threads (2026-11-10).** A call has an overall deadline of 10 s, a read a timeout of 5 s (idle between lines is normal, a stall inside a line drops the connection). Calls run on the caller's thread (never the main thread); the serial worker is the listener executor (notifications, lifecycle events and ordered results in line order). One reader and one writer thread per connection attempt, so a server that stops reading cannot hold a caller past its deadline. The loopback fake server uses the literal `127.0.0.1` (no resolver in tests).
- **Order of answers and notifications (W1).** The result of a model-changing call is handed to the listener executor as an event in the same queue as the notifications (`callOrdered`); `callOrdered` from a listener fails with `IllegalStateException`. The server does not notify the connection that made a change, so `SnapcastOperations` patches the model after each own call; AddStream/RemoveStream ask for a re-read.
- **Hostile input.** The JSON pre-scan matches Android's `org.json` rule (a `"` opens a string only after `{`, `[`, `,` or `:`); byte-level line cap 1 MiB, depth and token pre-scan before parsing, notifications of unknown methods are dropped at the reader and only set a re-read flag, the notification queue is bounded in count (256) and bytes (4 MiB, one notification is always accepted), `Stream.OnProperties` arrives with empty params, a silent peer (no byte since the request was written) drops the connection and starts the reconnect cycle (backoff, ceiling 5), `Config` refuses limits below 1. (The older `YxcJson.bracketDepth` has the same gap that W2 closed here; not part of this work.)
- **Exceptions and display text.** `SnapcastException.io` and JSON syntax errors keep no cause (it can hold the address); the title of a server error is printable ASCII up to 64 characters, its data has control, line/paragraph separator, bidi and C1 characters replaced (W1 of the security review). `describe()` is "error row, never a log".
- **Group volume.** The average of the connected members; every member moves by the same number of points; a muted member moves with the group and keeps its flag; a disconnected one is untouched; at 0 and 100 the points that did not fit are redistributed; a drag passes the start levels separately so steps do not add up. `setGroupClients` refuses null and an empty list (it would dissolve the group).
- **Rig switch.** The one switch is the system property `snapcast.rig` (forwarded by `yaacc/build.gradle` only when set); also `snapcast.rig.seconds` and `snapcast.rig.expectChunks` for the binary rig test.

## 3. Discovery and the receiver model (Groups 3, 11C, 11D)

- **Server key and merge (2026-11-10).** Key = canonical control endpoint `host:port` (IP literal canonical, IPv6 as eight hex groups in brackets, host names lower case); mDNS and a typed IP are one entry, a typed host name is a different endpoint (no resolution to merge). Receiver id `snapcast:<key>:<group id>` parsed from the right; a group id must be 1 to 64 characters of letters, digits, `_`, `-`. At most 16 servers, 64 groups listed (in server order), 32 remembered service names; grace for a lost service 30 s.
- **Address rules.** Discovered servers: loopback (refused for discovery since S72, a LAN host can announce 127.0.0.1), private IPv4, link-local, IPv6 unique-local, ports 1024 and up (S18); site-local fec0::/10 and 100.64/10 refused. A typed-in server is not range-filtered (the user chose it, a public address is allowed and documented) except unspecified, multicast and broadcast; no leading zeros in IPv4 parts. The parser is hand-written so no input causes a lookup; host names go through `SnapcastResolver` (helper thread, 5 s, 2 at once).
- **Connections.** Opened lazily for the listed servers while a page is visible, for a retained server (a player) and for servers of chosen groups on `wake`; closed 30 s after the last page was hidden. Nothing is scanned outside the page lifetime. A stored selection survives a cold start: the endpoint of a non-manual server that holds a selected group is stored (`snapcast_selected_servers`, plain `host:port`, at most 16) and listed as remembered; the last known state stays after a link closes (groups shown offline); a pending id is not waited for at a play (no 5 s wait with searches for a dead server). One `SnapcastGroupDevice` per id is reused while name, offline flag, stream and member count are unchanged (stable identity for the diff callbacks).
- **Closing tells the owner (Group 5b, W1).** `SnapcastSession.close()` fires `onLinkChanged` (offline) once before dropping listeners, so the feed controller of a removed server closes the feed (CONTROL_LOST). The group may stay on YAACC's idle stream until another controller moves it back (accepted). "Discovery off" ends a running feed only for a server that no selected group remembers (S43/S48 accepted: a remembered server is contacted with discovery off).
- **Why discovery missed servers (found 2026-11-13, task 11.6).** Snapcast 0.33 and newer announce the control port as `_snapcast-ctrl._tcp`; 0.26 to 0.32 as `_snapcast-tcp._tcp` / `_snapcast-jsonrpc._tcp`. The first build browsed only the new name. Now it browses `_snapcast-ctrl._tcp` and `_snapcast-tcp._tcp` (listed) and `_snapcast._tcp` (stream port, report only, never turned into a control port); types match exactly after normalising the dot and `.local`; the same name under two types is two services; a failed resolution (codes 0 and 3) is retried twice after 2 s. The Docker rig has mDNS compiled out, so it can never be found there.
- **Discovery diagnostics.** `SnapcastDiscoveryLog` (last 40 callbacks), `SnapcastDiscoveryReport` with a first-rule `Reading`, shown with *Copy report* in the server list window (marked sensitive on Android 13+, carries the phone model); while that window is open and the switch is on the scan runs, bound to the window by a lease (W1 of review 11Cb: released on dismiss, stop, destroy, detached view). A VPN is "unknown", not "no Wi-Fi". Found/remembered servers are offered in the client choice with port 1704 only; link-local IPv6 is not offered (no scope id).
- **Server choice texts (S67).** Label `host (NAME)`; the address field is never prefilled from a server that was only found.
- **Display text (S15, S66, S71).** Everything a server sends (names, ids, streams, errors) passes `SnapcastDisplayText` before display: control, bidi, format (general category Cf), zero-width, tag characters, unpaired surrogates, Hangul fillers, Braille blank, U+034F, U+17B4/5, U+2065..206F become `?`; white-space-only is empty. Known cost: a real name with a ZWNJ or joiner shows `?`. Never logged, never used as identity; the first row line is the server endpoint (S20: a hostile server cannot imitate a group), the stream name on the row is cut to 24 characters.
- **Why the ports matter (T.1 to T.4, 2026-11-16).** The feed tests open real server sockets on 127.0.0.1:4953-4962 (`SimulatedSnapcastServer`); any other process on those ports (the owner's Docker rig, a snapserver) makes 11 of those tests fail. Not a code regression. T.5 (ephemeral ports) is open.

## 4. Feed and player (`multiroom.feed`, `SnapcastPlayer`, Group 4)

- **Pacing.** One anchor plus bytes sent; the earliest write time is the end of the audio sent minus a look-ahead of 3 chunks (60 ms); a write more than 2 chunks late re-anchors (no burst). Why: the server reads in real time and resyncs when a read ends after the next chunk's deadline; a burst piled up 39 s in the rig. The feeder never underruns (pads a partial tail with zeros after a half-chunk grace, at most 50 chunks of silence, then waits and re-anchors), writes whole frames only, wakes when audio arrives, drops after 200 ms of back pressure. Zero chunks make the stream `idle` (harmless); idle cleanup is measured by our own last audio, never by the stream status.
- **Connect target.** The feed connects only to the control connection's peer address (read after the last `ensure()`, same connection generation) and a port from YAACC's range 4953 to 4962; never to a host or port from a server reply; wildcard and multicast refused; connect failures carry no address (the log line is `connect failed: <exception simple class name> (port <n>)`). Why a feed can fail with CONNECT_FAILED: a server firewall (ufw) blocking 1704, 1705, 4953-4962 (docs have the ufw example).
- **Streams.** The phone name is sanitised (letters/digits of any script, space, `-`, `_`, 32 code points) and percent-encoded; adopt only an exact name, tcp, `mode=server`, `48000:16:2`, host `0.0.0.0`, port 4953-4962; the AddStream answer must name exactly the id asked for; only -32603 tries the next port; leftovers (marker in the name, tcp, no group on them) removed, at most 8 per run; previous group streams restored only for groups still on our stream and only to a stream that still exists; a failed restore keeps the stream and the records; `useFor` keeps the previous-stream record when `setGroupStream` fails (S27). The marker is 8 hex characters made once with `SecureRandom` (private preferences, atomic load-or-create, an identifier, not a secret). Removal at release or after 10 idle minutes (back-off up to 10 minutes while an unrecorded group stays on it).
- **Converter.** Always 16 bit stereo at the stream rate (Sonic converts the rate); mono duplicated; 3 to 8 channels folded with Media3's channel order (7 = FL FR FC LFE BL BR BC, not the WAV layout), LFE dropped, each side normalised so the sum cannot clip. The Media3 `ChannelMixingAudioProcessor` is not used (stops at 6 channels, needs `SparseArray`).
- **Tap and pass-through.** `SnapcastPlayer` extends `LocalMediaSessionPlayer` (protected factory `createExoPlayer()`); the tap sits behind the sink's trimming/channel map/16-bit conversion. `DefaultAudioSink.Builder.setAudioCapabilities` does nothing with `Builder(Context)` in Media3 1.11.1 (verified with `javap`), so the sink is wrapped in `PcmOnlyAudioSink` (refuses every non-`audio/raw` format, so AC-3/E-AC-3/DTS are decoded to PCM); offload is never enabled. A phone without a decoder for a format plays that item silently for its length, no message (documented).
- **Player behaviour.** Discard on `onPlayWhenReadyChanged(false)`; a pause during the start is honoured; stop drains 250 ms + 60 ms and closes on the controller's worker, never the main thread; a typed `FeedError` (cleaned reason, at most 80 characters, format characters removed) is a toast and stops the player; volume and mute are the group's, on an executor of their own with a 5 s gesture budget; one feed per server from this phone (a second group hears BUSY after 3 s); `getId()` random above 100, `getDeviceId()` the receiver id; the media sessions are a list, the last registered is active; `stop()` is retried every 50 ms while a command runs (20 times) and a flag marks a stop that still did not go through.
- **Playlist files and unreadable tracks (2026-11-13, owner).** `PlayableCheck` filters `.m3u/.pls/.asx` (type or extension, HLS `.m3u8` stays) at queue build for receivers that read on this phone (the phone and Snapcast groups); the OpenHome renderer's own queue is NOT filtered (its `playerIds` list is parallel to the player's list), the skip policy copes. `TrackFailurePolicy`: an unreadable track is skipped with a toast naming it (never an address: "Track N"), after three failures in a row or a failing last item the player stops; a manual next/previous resets the count; the local player had the same gap and is fixed too. Known limit: a track that reaches READY and fails again can loop in a repeat list.
- **Receiver picker (2026-11-13).** A Snapcast group is not listed in "Play on..." when the content holds an image or video (`PickedAction.content()`); unknown content offers everything, the start-time check and toast stay as safety net.
- **Static source fallback (history).** Found while writing the docs (6.1): the old hint promised a fallback that the code did not deliver (a matching static source is adopted once, removed at release or idle, the marker is shown nowhere). Resolved by option (d), see section 1.

## 5. UI, volume keys, link sheet (Groups 5, 11B)

- **Row.** Reuses the MusicCast row: first line the server endpoint (S20), second the facts (stream, clients connected n of m, volume, muted); "server unreachable" (stale flags are not shown) and "stream unavailable" (not in the status or `disabled`) markers; slider and mute are the group's; play/pause/stop act on the group's `SnapcastPlayer`. Members ordered by name then id, equal names numbered, never an id (a MAC) as label.
- **Controls.** Two executors (volume gestures, everything else), the latest slider value wins, start levels at the gesture start (or after a 2 s gap), 5 s budget, typed failures (`REJECTED` carries server text, cleaned and cut to 80), one toast per 3 s; group mute coalesced per group like the volume (W1 of review 9), shared by the card and the renderer.
- **Mute symbol (11.1).** The group sheet's switch/checkbox became `snapcast_mute_toggle` (the symbol of the other cards) with description and state text in 7 locales.
- **Link sheet (11.3).** The link icon of the card opens `SnapcastLinkSheet` on `YxcLinkSheet` (new `Options`); rows from `SnapcastLinkChoices` (every client of THAT server, members checked, the only member checked and disabled, "(in group X, which then ends)", offline clients linkable); OK is one `changeMembers` = `Group.SetClients` with the exact list computed on a fresh status (`freshStatusOrModel`, 1/s and 10/min, else the model: a client added meanwhile normally stays, S36). "Add client" and "Remove from group" were removed from the group sheet.
- **Volume keys (11.4).** No routing to a focused receiver existed. The focused Snapcast group is the row with input focus, else the row touched last, only while it is on screen (receivers page of the default layout, Receiver tab of the classic layout, device sheet); steps of 5 points through `setGroupVolume`; up on a muted group unmutes, down on a muted group changes nothing; nothing touched means the system's keys; the picker takes none. `BrowserActivity` (the default layout) needed its own routing (W1 of review 11B); a source guard pins every activity that can show receiver rows. Other receivers are not controlled by the keys; in renderer group mode the keys still change the phone's volume.
- **Settings.** Discovery and play checkboxes, the server list dialog (host[:port], `@` refused, duplicates merged, 16 at most; removing a server also clears its selection, remembered flag and stored endpoint; an announced server cannot be removed).
- **Open (not built).** S44: a hostile server can make the group sheet redraw about every 250 ms with up to 256 members (throttle and in-place slider updates not built).

## 6. Phase B protocol (`multiroom.protocol`, Group 7)

- **Codec.** Types 1 to 5, 7, 8 (0, 6 and others skipped by size); payload caps 8 MiB for chunks, 64 KiB + 64 for a CodecHeader (tightened by S56: a chunk above the connection's backlog budget of 4 MiB is refused at its header), 64 KiB otherwise; lengths checked against what is left before anything is reserved; the body buffer grows with the arriving bytes. Codec allow-list `pcm`/`flac` applied while decoding. PCM: integer only, 1 to 8 channels, 8000-192000 Hz, 16/24/32 bit, `data` length not trusted; FLAC: "fLaC", STREAMINFO of exactly 34 bytes first, 16 or 24 bit.
- **Time sync.** Offset = (c2s - s2c)/2; `ClockOffsetFilter` takes the last 16 samples, the median of the half with the shortest round trips, refuses round trips below 0 or above 500 ms, holds back jumps above 1 s until three candidates agree (epoch +1, window restart); 16 requests 100 ms apart after the settings, then one per second; an answer whose network time exceeds the measured one by more than 1 ms, or whose `refersTo` is not outstanding (16 at most), is ignored.
- **Scheduler.** "Too far ahead" = timestamp more than 5 s after the corrected clock (independent of the client latency, else a latency of -10 s drops everything); `DROP_QUEUE_FULL` at 512 chunks / 4 MiB; nothing is released before the header or without a synchronised clock.
- **Connection.** One reader per attempt, a writer thread with a queue of 32 (a full queue = the server does not read = TIMEOUT; the writer is published after the Hello is queued; it catches `Throwable`); messages must complete within 10 s of their first byte; a frame budget of 2000 per second of the injected clock (the 2001st ends the connection; a real server sends 50 chunks plus one Time answer per second), an unsolicited Time answer counts as unexpected, Hello/ClientInfo frames are skipped by size; settings and offset updates are latest-wins, at most 8 codec headers wait (a ninth drops the connection); 401/403, unsupported codec and `UNSUPPORTED_FORMAT` are permanent; other losses retry like the control client (5 failures, 1 s doubling to 30 s). `forAddress` refuses null, wildcard and multicast; `MicroClock.fromNanoSource(SystemClock::elapsedRealtimeNanos)` is the Android clock (counts in deep sleep). A stall inside a frame is bounded by the message deadline, not by the time-sync wake-up timer (W1 of review 7).
- **Hello.** `ID` = `yaacc-` + 16 hex of SHA-256(install secret, 0x00, fixed label) for EVERY server (see section 9, supersedes the per-server id and the idea of deriving it from the device UDN); `HostName` = the UPnP server name, generic `YAACC` when the resolved address is outside the local ranges (decided in `connect()` from the resolved address, S18); no `Auth`.

## 7. Phase B audio engine (`multiroom.client`, Group 8)

- **Architecture.** `SnapcastClientEngine` is a single-threaded deterministic core behind `AudioSink`, `DecoderFactory`, `OffsetSource`, `MicroClock`; `EngineHost` gives it one thread (`THREAD_PRIORITY_URGENT_AUDIO`), a bounded event queue (1024 events and 16 MiB, chunks only while three quarters empty so settings, headers and a loss find room, a round bounded to 50 ms, every polled event is run), a watchdog and sticky stop/abandon. Not built: a second decode thread, Opus/Ogg, more than two channels (`UNSUPPORTED_CHANNELS`); 24/32 bit PCM is converted to 16 bit.
- **Time model.** The output reports `frame f presented at t`; the engine extrapolates to the frame about to be written; play time = `anchor + s/rate + bufferMs - (server latency + manual latency) - offset`. The output is always fed (silence when nothing is due). Exact alignment (pad/skip to 1 ms) at the start, after a gap and after a step above 30 ms (needs the median of at least three reports, done to the end as one unit); while playing single frames are dropped or repeated (at most 1 per 400, smooth-interpolated over 32 frames in the service, dead band 2 ms); lateness above 300 ms flushes (3 consecutive fresh reports, at most one flush per 500 ms), a flush keeps the decoded audio and the anchor; aligning waits for a settled clock estimate (half the filter window).
- **No time bounds.** The 10-minute bound was a Critical bug (healthy playback cut every 10 minutes): continuity is judged by the gap between consecutive chunks (a gap above 3 s starts the timeline anew), the anchor moves in place by whole seconds every 2^34 frames, all frame counters are 64 bit, wall-clock windows use the engine clock.
- **Start threshold and deep buffer (owner's "peep....peep" test, Nothing A142 / Android 16).** Cause 1: a streaming track plays only when its buffer holds a device minimum, the old engine waited for a position that never came and then flushed. Fix: the sink asks for a 40 ms start threshold (Android 12+), the engine writes at least that much, keeps queueing silence when no position comes after 200 ms. Cause 2: the phone's output is deep-buffer (`mFlags 0x8`, mixer latency 128 ms, period 2048 frames); the platform's underrun counter rose every period while the engine kept only 120 ms queued. Rule: the counter is real evidence of a thin cushion. Default write-ahead 250 ms (40 to 350 in the details, adaptive raise by 40 ms after a rise the position does not turn into a dry-out, never lowered in a session), track created with `PERFORMANCE_MODE_POWER_SAVING`. The "spurious/unreliable counter" logic of Group 8g is superseded by this.
- **Position robustness.** Outlier gate (a report 150 ms off the extrapolation waits for confirmation), persistence for hard resyncs, plausibility of the timestamp clock base (age above 2 s or in the future counts as a failed poll), head-position fallback only once it moved and kept across flushes (retry of the timestamp every 5 s), a position stall path (`position_stall`) for a frozen output; `StreamingSink` is the pure position code behind a thin `AudioTrackSink`.
- **Restart after a pause of the source.** flac chunks are placed by counting frames, so a pause was invisible and the engine believed it was late by the pause and skipped everything; fixed (timestamp jump drops the timeline, skip bound 1 s, pcm timestamps going back re-anchor). Why a restarted client got no chunk (owner's status, Group 8i): the server puts a (re)connecting client in a group of its own on the default stream; nothing was wrong in the client protocol. The details show `server says` and a hint and offer *Move my group to a stream* (`Group.SetStream` after a confirmation, fresh status check, `MoveDecision`).
- **flac holes and the stall guard.** A chunk lost before the decoder (scheduler drop, decode failure, host queue overflow) leaves a hole; holes are a sorted bounded set (64, overflow range), recovery re-anchors by the next chunk's timestamp (known limit S10: it discards the decoded audio waiting; a lossy link is much worse than pcm). The server stamps flac chunks with a running clock advanced by the encoded duration (contiguous with the encoder's frames; 20/20/20/20/40 ms is only the arrival spacing; an earlier claim and its "owner trace" were wrong). A source stall shifted the stream for good; the first guard measured against decoded frames and was harmful on the owner's phone (four fills of about 26 ms in 15 minutes, his A/B by ear preferred the build without it). Root fix: the position of a chunk is read from the FLAC frame header (`FlacFrameHeader`, longest header 16 bytes), the guard works only with header positions (three refusals in a row fall back to counting and switch the guard off), thresholds pinned by literal tests, check box "FLAC stall guard" (default on). Unverified without a capture from a real server: that every chunk starts with a frame header, the stamps being contiguous, the arrival jitter.
- **Hostile input.** Chunk timestamps are never trusted (saturating maths, gaps above 3 s restart); decoded audio waiting is bounded to 3 s; sizes come only from the validated format (`maxFramesPerChunk` = rate x 2 s), never from FLAC block sizes; a partial trailing PCM frame is dropped; decoder restarts at most 12 per minute (`HEADER_FLOOD`), decoder failures at most 12 per minute plus 8 in a row (`DECODER_FAILED`); the FLAC decoder (`MediaCodec`, `csd-0` = the header) drains through the pure `CodecDrain` (first over-limit buffer ends it, 64 buffers, 150 ms, input above 128 KiB refused, codec made anew); the native decoder is a residual risk; hole marks are ignored while unsynchronised and clamped to corrected time + 5 s (S15); a settings flood is one rebuild per second at most (`NotificationPolicy`).
- **Service and power.** `SnapcastClientService`: foreground service type `mediaPlayback` (no timeout), not exported, `START_NOT_STICKY`, notification with Stop, started only by the app; permission `FOREGROUND_SERVICE_MEDIA_PLAYBACK` added (needed for target 34+). Wake lock (8 h safety, renewed every 30 minutes) and Wi-Fi lock only while the engine plays, plus 60 s grace; audio must have played 5 s in a row to count (S17); a session with no audio for 15 minutes ends (`NO_AUDIO`); locks released before the ending is recorded (S25). Wi-Fi mode `FULL_HIGH_PERF` up to API 33, `FULL_LOW_LATENCY` from 34, which is active only with the screen on and the app in the foreground: from Android 14 NO screen-off Wi-Fi lock exists and the app does nothing more. Residual (S23): audio of 5 s or more every minute keeps the locks and the session for ever. The session never ends silently (reason and time stored, `Stopped: <reason>` notification, trace line); YAACC's own shutdown timer is recorded as `app_exit`. Known limits, not built: audio focus, `ACTION_AUDIO_BECOMING_NOISY`, gain ramp (it has to be done on the samples).
- **Owner's evidence.** 2026-11-13: with write-ahead 250 ms the tone is continuous ("looks good now"); an album played from the app to the server and streamed to three clients, one of them the app, was stable for 30 minutes (the 8i build); an A/B of 8i against 8j (three devices, 15+ minutes) showed a very small latency between devices. No capture of a real server's chunks and no measurement against a reference clock exist. The owner's kill criterion (sync cannot be held) was not raised.

## 8. Renderer output, OpenHome sources, power buttons (Groups 9, 12B)

- **Stored value (Group 9).** One string, the receiver id `snapcast:<key>:<group id>` (names never stored); keys `settings_renderer_output` (`device`/`group`) and `settings_renderer_output_group`; read at every use and validated; a damaged value falls back to this device and says so at the next play; group mode without a group is an error, never a local play. No experimental option gates it (the renderer's choice is explicit); the disclosure (unencrypted, any device that reaches the receiver can change the whole group's volume and mute) is the first sentences of the summary text.
- **Behaviour.** One factory `PlayerService.createLocalPlayer`; content judged as the picker does (music only; no type is refused with its own message); a play that makes no player ends STOPPED; every problem is a message and never a local play; switching the output stops only the renderer players of the other output; a stale player (output changed during the up to 4 s wait) is shut down; a server that does not answer is remembered as unreachable for 5 s (`UnreachableMemory`, S75); toasts through a 3 s gate (S76); an interrupt is a cancel (S78); one content-type rule `ContentTypes.normalize` for the gate and the lookup (W2: `Audio/Mpeg` made a feed no controller could stop).
- **Volume path.** `OutputRoutedVolume` decides per call; reads come from the model (last known level per group); a controller's own Get call or the first subscription wakes the connection at most every 20 s (`peek*` reads never wake); the OpenHome poll reads with `peek*` and wakes once at the start (S16); the cost is that an OpenHome control point sees the last level the model knows until the next play or start. The row of YAACC's own renderer is routed through `UpnpClient.volumeOf`; hardware keys are not routed in this mode.
- **Test infrastructure (W6).** `ServiceHarness` records events by their SEQ number (`OrderedEvents`), as a GENA control point does; the 1-in-20 failures under load came from out-of-order recording.
- **Power model (12.4, 12B).** `RendererPower` / `RendererPowerToggle.Source` / `RendererPowerGate` / `RendererPowerLook` / `RendererPowerButton` are kind-free; button in the title row between badge and check box, Material `power_settings_new`; MusicCast: `power` in the main zone's `func_list`, state from the monitor, `main/setPower` with an explicit target after a `getStatus`; OpenHome (remote): Product actions `Standby`/`SetStandby`, state read every 10 s by `OpenHomePowerMonitor`; MusicCast wins if both. 12.13: the app's own OpenHome card uses the Product `Standby` state variable that the settings sheet's Power switch writes (`OhRendererCore.setStandby` is the one writer), not `settings_local_server_receiver_chkbx`. For a Snapcast card the power button exists only for the phone's own client (section 9).
- **Snapcast groups as OpenHome sources (12.5).** `SnapcastRendererSources`: index 0 "this device" exactly as before, then at most 16 groups by cleaned name, all of type `Playlist`; the group id never appears in a visible text (`SystemName` = `snapcast-` + 16 hex of SHA-256 of the receiver id); a chosen group that is gone shows one placeholder source; choosing writes the same two keys as the settings screen; the list shows what the app has read since it started and never wakes a server; `OhRemote.prepare()` keeps the current source when it is a Playlist source. Cling turns a negative `ui4` into 0 (`SetSourceIndex -1` = this device).
- **Removing a client (12.8).** `Server.DeleteClient`; the app enforces its own rule on a REAL fresh `Server.GetStatus`: not found = gone, connected = refused, the own client = refused (only an offline own entry may go while no session runs); one removal per client per 2 s. Why two YAACC entries existed: see section 9.

## 9. Client identity, merged lists, power on the own card (Group 12C, owner 2026-11-15/16)

- **One client id for all servers (12.11, owner).** The Hello id is derived from the install secret only (no endpoint), also for public addresses; reverses the per-server id (security review S61) and the idea of the device UDN. Accepted cost: any server and controller can tell it is the same phone. `SnapcastClientIdentities.ownId` never creates the secret. Why the old per-server ids were a problem: the id was derived from the endpoint text the user typed for the client (`host:1704`), so an IP versus a name, another port, a DHCP change or a reinstall made a second client entry ("ghost") on the server.
- **Old ids are the phone (12.19).** The old derivation is recomputed (`SnapcastLegacyClientIds`: `host:1704`, `host:1705`, `host:<entry port>` for every known server and the details' last address, at most 64) and merged into the phone: shown once, connected > latest `lastSeen`; the menu *Remove old entries of this phone* removes offline legacy entries of the FULL status (current id, connected entries and other installs' ids are never touched). Display only. An old entry that cannot be reproduced (a host name typed for a server the list knows by number, another port, a reinstall) stays an ordinary offline client (*Remove from server*).
- **Merged lists as a FILTER (12.12, owner, small).** `SnapcastMergedClients` over the statuses of all known servers (display only): a client id is shown once, on the server where it is connected, else where it was last seen (`lastSeen`, tie: first server); a server whose link is down counts as not connected; offline copies elsewhere are left out of cards, sheets, link pickers and counts; a card whose members are all shown elsewhere is not listed. Group keys, stored selections and OpenHome sources are unchanged (`findGroup` still resolves a fully hidden group). Nothing that changes a server knows the filter (`Group.SetClients` is built from the fresh full status, so a hidden member stays; guard test). The link picker lists only clients of the sheet's server (the cross-server link and transparent server switch of 2026-11-16 were dropped by the owner's second round).
- **Power on the own card (12.4 part 2, 12.16).** The button is on a Snapcast group card only when the phone's own client (recognised by id) is the group's first member or its only member, and on the own row of the group sheet (also for an offline entry); a tap = `SnapcastClientPowers.setOn`; off = stop of the session = the disconnect; no other client has one (the protocol has no way to disconnect or wake another device's client). State: on while a session starts, runs or reconnects (or a restart waits, or a start was handed over less than 5 s ago).
- **One stored state and restore (12.6, 12.17).** `settings_snapcast_client_switched_on` is written only by `SnapcastClientPower.setOn` (first-page switch, settings checkbox, card button, details Start/Stop); writes first, then re-checks option and server; a refusal is a toast and a recorded ending (`DISABLED`, `BAD_ADDRESS`, `START_NOT_ALLOWED`), no retry loop; only the user's off clears it. `SnapcastClientRestore` restores at app start (and once more at the first screen after a start the system refused, never a third time) when switched on, option on, a valid server known, no exit hold-back, no session, and the last ending is not an unseen failure (the row, the details or the off switch count as seeing it). A refused foreground start (`ForegroundServiceStartNotAllowedException`, recognised by class name) is the ending `START_NOT_ALLOWED`, appended last in the enum. First-page row: label, switch and gear like the UPnP row, no subtitle (owner), state in the switch's state description; shown when the option is on and at least one server is known.
- **Which server (owner 2026-11-16).** The client connects to the server it was last connected to (`snapcast_client_last_server`, written when a session first reaches RUNNING, on a choice on the own row and on Start with an address), else the first known server (order of `SnapcastServerChoices`: last used, typed, remembered, found); it is "associated" with all known servers as choices but connected to one; no automatic failover; a switch while on restarts the session (bounded poll 200 ms up to 8 s for the old service instance to end, `SnapcastClientServerSwitch`); only the host is used, stream port 1704.
- **Superseded intermediate decisions.** Client-centric cards and re-keying everything by client id (2026-11-16 first answers), cross-server links, "restore at app start but not after a reboot" (2026-11-15), and a separate "This phone" card were all replaced by the small solution above (filter, own card power button, startup route).

## 10. App behaviour decisions made during the work (owner)

- **Back (12.1).** The last back puts the app in the background (`moveTaskToBack`), never `Yaacc.exit()`; the idle timer (`BackgroundIdleTimer`), the exit button, `ExitBroadcastReceiver` and the shutdown timer still exit. `TabBrowserActivity` uses an `OnBackPressedCallback` (predictive back).
- **Exit and restart (12.2, 12.9).** The sticky-restart hypothesis is not proven (`stopService` clears the started state synchronously); found instead: `Yaacc.onCreate` starts and binds the server service at every process creation, the server service stayed bound by `UpnpClient`, and releases posted to the main thread never ran because the process ended in the same message. Defence in depth: `ExitRestartGuard` mark (file `yaacc_exit_guard`, 120 s window, fails open, a boot and a user start never blocked); a system start with no intent stops itself (minimal notification up and down); `onCreate` within the window starts nothing, the first screen clears the mark; restored screens within the window finish; `ExitSequence` (mark, shares, client ending, players each ended on a thread of its own with a 4 s hand-over (`ExitHandoff`), services, notifications, tasks, then a posted poll up to 3 s for services and open feed controllers). Known old bug not changed: the inverted wait of `AVTransportPlayer.doExit()`. Only the owner's phone shows whether the app still comes back (log lines "Restarted by the system right after an exit..." / "Process created right after an exit...").
- **Permissions (12.3).** The old "all granted" check was never true (install-time permissions, write storage on API 29+, all-files access in the list), so the request ran at every start; the battery-optimisation request ran at every `onCreate`: very likely the dialog the owner saw. `PermissionRequestPlan`: only requestable permissions per API level (23-29 read+write storage, 30-32 read, 33 media + notifications, 34+ selected photos), each asked once (stored before the dialog), once per process; battery once per install. Android 10 keeps write storage (`requestLegacyExternalStorage`, `FileDownloader`). `requestPermissionsOnUserAction` is built, not wired to a screen.
- **Idle close and autostart (12.14, 12.15, 12.18, owner).** The UPnP service itself is no blocker for the automatic close; blockers: a player, a Snapcast feed or client session, the master switch *UPnP Server*, and (new) a ticked autostart setting (`Keep.AUTOSTART`, last in the order so the log names a running thing first). Facts: the idle timer was armed only when a browser stopped, so a process created without a screen (boot, system restart) never closed: now `BackgroundIdleTimer.processStarted` arms it at the end of `Yaacc.onCreate`. 12.15 (owner's log `staying open: RENDERER` with the master switch off): the renderer and proxy sub-switches count only with the master switch (`IdleFacts`); the provider checkbox is not a parameter. Autostart: the setting is always selectable; it enables/disables the `ServerAutostart` receiver component (manifest default disabled, applied in `Yaacc.onCreate` and on preference change, `DONT_KILL_APP`); the boot case is the normal startup route (process creation runs `Yaacc.onCreate`, which starts what is switched on and restores the Snapcast client); a force-stopped app gets no boot broadcast (accepted); after the update an install with the setting ticked has no boot start until the app was opened once; targetSdk 33 allows the foreground start from `BOOT_COMPLETED`, Android 15+ targets may not. The Android 15 restriction is not verified on a device.
- **Shared-link proxy (12.21, owner "proxy vs sharing").** The proxy is the SSL offload during sharing and needs the master switch *UPnP Server* AND the proxy checkbox (`ProxyAvailability`: proxy ticked + master off = refuse with `share_link_needs_server`, proxy not ticked = direct); normal sharing of files and links with the short-lived URL works WITHOUT the master switch. The HTTP server can run with the master switch off (the service is bound for the life of the process), so `ServerRequestGate` answers 403 for a proxied link and for the content paths while the switch is off; a shared file is always served. Narrow edge not fixed: a process created in the background whose `startService` was refused has no HTTP server until the switch is on, so a file shared then is dropped (`share_open_failed`); smallest fix: start the service in `Yaacc.userStarted()` when the server probe is false.
- **Unfixed notes from 12.15.** `NetworkDeviceListener.shouldHoldWifiLock` has the same sub-switch mistake but lives inside the service that stops with the master switch (no effect); the first-page status icons show the configured state; the content handler's provider/proxy flags without the master switch are covered by the other handlers' checks (not verified for every path).

## 11. Security decisions and accepted risks

Phase A / B rules are in `design.md` ("Security rules", "Security rules for Phase B"). Decisions and residuals:
- **Trust model.** LAN only: control (1705), feed (4953-4962) and client stream (1704) are plain TCP, unauthenticated; announcements are the whole trust (S70); no credentials stored; the stream's tcp port listens on all server interfaces so any host can inject audio (a property of Snapcast's tcp source); the audio goes to whoever answers at the chosen address (a manual host name may resolve anywhere, also public, S24; nothing warns); the stream name discloses the phone name to every fed server and controller (S31/S40); the marker is an identifier, not a secret; a hostile server can name a group like a legitimate one (S20, endpoint first on the row).
- **Rig.** Pinned by commit hash and image tag, ports published on 127.0.0.1, HTTP/WebSocket control disabled in the rig (a browser page can reach a loopback websocket), `process://` is refused by the server outside its sandbox directory (owner's probe), only `tcp` sources are ever created by YAACC. `adb reverse` exposes the rig to every app on the phone while active.
- **Accepted residuals.** S1/S2 (byte budget counts line bytes, no rate budget for valid lines on the LAN control channel), S4 (host-name lookup without our timeout on the reader thread), S5-S8, S10, S43, S44 (not built), S23, S36, S65 (4000 frames at a window edge), the native FLAC decoder, Snapcast's own lack of TLS on 1704/1705, the group staying on YAACC's idle stream after a lost connection/removed server.
- **Documentation duties taken.** README, `docs/index.md`, `docs/settings.md`, CHANGELOG, `THIRD_PARTY.md` say: unencrypted and unauthenticated, discovery spoofable, the phone name in the stream name, the stored data (typed-in servers, selected receivers, remembered servers, marker, client state, last server, secret; `allowBackup=false`), the same id on all servers, any device reaching the renderer changes the group's volume and mute, the ports table and firewall notes, GPL wording, not-affiliated notice, no logo.
- **Findings that explain code.** Ghost ids and the per-server id (section 9); `_snapcast-tcp._tcp` (section 3); the ports T.1-T.4 (section 3); the boot receiver ran after `onCreate` (it only changed a log line) so the setting did not control the boot start, and the idle timer was never armed without a screen (section 10); the deep-buffer output and start threshold (section 7); the old 6.1 docs claimed "never removes a stream it did not create" and a working fallback, both false (fixed in review cycles 1 to 3 of Group 6).

## Idea: a Snapcast SERVER in the app (owner asked 2026-11-17; feasibility only, no decision, no spec yet)
Answer given: feasible, medium to large; a minimal useful server (one stream from the app's own playback, PCM only, a JSON-RPC subset, mDNS, a switch) is roughly comparable to Phase B, parity with snapserver is much larger. Reusable: the binary protocol codec (both directions), FrameReader, FLAC header parser, PcmFormat and clocks, the Phase A PCM tap (the source), the JSON model (parse -> build), the fake servers in the tests and the Docker rig with real snapclients. New: TCP listeners 1704/1705, per-client sessions (Hello, ServerSettings, write queues with back-pressure), time-sync responder, chunk pipeline (20 ms chunks, server clock + buffer, PCM or FLAC via MediaCodec), server state and a JSON-RPC server with snapserver semantics (groups, clients, streams, notifications, persistence), mDNS announcement, foreground service, UI. Risks: Android background limits and battery, Wi-Fi client isolation, a new unauthenticated listener surface (needs its own security rules), compatibility details only partly documented (read the snapserver source). Staged path: spec and rules, binary core against a real snapclient, JSON-RPC subset, service and UI, later FLAC, more streams, Snapweb, authentication. Overlaps the parked Sendspin spec. Next step if wanted: write a spec after the postponed review of Group 12.
