# Decisions: Snapcast support (#319)

## 2026-11-09 - Scope: target + controls first, client second, no linking, no server role
**Context**: Snapcast clients take their server from their own command line; the server has no method to move a client (`notes.md`, Discussion 3). The owner wants a maintained Android option (Snapdroid is stale) but not the dynamic linking.
**Decision**: Phase A = YAACC feeds a snapserver and controls it. Phase B = the phone as a client (plain Java protocol). YAACC is never a snapserver. Phase B starts only after Phase A is released and used (own gate).
**Rationale**: Phase A is small, useful alone and testable with the rig; Phase B carries the real risk (sync on Android) and gets kill criteria.

## 2026-11-09 - One receiver per Snapcast group
**Context**: UPnP receivers are devices; a Snapcast group is the unit that has one stream and a set of clients.
**Decision**: A group is the receiver row; clients are members with own volume. Group changes use `Group.SetClients` / `Group.SetStream`. A group that disappears (all clients gone) disappears from the list.
**Rationale**: owner's choice (recommended option).

## 2026-11-09 - Runtime stream creation
**Context**: The documentation says `Stream.AddStream` accepts only pipe, file, tcp, alsa, jack, meta (a security restriction), but no such check was found in the sources (`docs/tech.md`); until the rig shows otherwise assume the server accepts any scheme. YAACC only ever creates `tcp` sources and never takes a stream URI from server data.
**Decision**: YAACC creates a tcp stream per phone (name "YAACC <device name>") on demand and removes it when idle for a while; fallback = documented `snapserver.conf` line when the server answers an error.
**Rationale**: owner's choice; no manual server setup.

## 2026-11-09 - Neutral package name
**Context**: MusicCast rule: respect trademarks, nominative use only, neutral code names.
**Decision**: Package `de.yaacc.multiroom` (sub-packages `protocol`, `control`, `discovery`, `feed`, `client`); "Snapcast" appears only as the product name in strings, docs and a README notice. Open for veto: Snapcast is GPL software by its author, not a brand like Yamaha, so `de.yaacc.snapcast` is acceptable if the owner prefers.
**Rationale**: consistent with `de.yaacc.yxc`, cheap to change now, costly later.

## 2026-11-09 - Authentication out of scope
**Context**: Snapcast 0.35 can require authorization (Basic) for control and for the Hello message of clients.
**Decision**: Not supported in Phase A/B; a server that demands it gives a clear error row. Revisit when a user needs it.
**Rationale**: no credential storage design yet; keeps the first release small.

## 2026-11-10 - Group 2 (control library): choices made while building it
**Context**: Group 2 (`de.yaacc.multiroom.control`) deviated from the wording of `tasks.md` in a few places, and the review of cycle 1 asked to record them.
**Decision**:
- *Fake server address*: the loopback fake server (`FakeSnapcastServer`) binds and is addressed by the literal `127.0.0.1`, not by `setCanonicalHostName("localhost")` as in the HTTP fake servers of other tests. A literal needs no name lookup, so no test depends on the resolver.
- *Timeouts*: a call has an **overall deadline of 10 s** (the figure of `design.md` "Security rules"), and a read has a **timeout of 5 s** (idle between two lines is normal; a stall inside a line drops the connection). The "5 s timeout" in the title of task 2.2 and in `design.md` "Control: JSON-RPC" meant the read timeout; task 2.2 is aligned, the design sentence is left as it is.
- *"Serial worker"*: calls run on the caller's thread (the blocking API is for the worker of a server, never the main thread). The **serial worker is the listener executor**: one task at a time, in the order of the lines, for notifications, lifecycle events and the ordered results of `callOrdered`. Besides that there is one reader thread per connection attempt and one writer thread (so a server that stops reading cannot hold a caller beyond its deadline).
- *Group volume*: the group volume is the average of the **connected** members; every member moves by the same number of points; a **muted member moves with the group and keeps its mute flag**; a disconnected member is not touched. At 0 and 100 the points that did not fit are **redistributed** among the members that still have room (the MusicCast version only clamps), so the average reaches the wanted value where the scale allows. A drag passes the levels from its start separately from the current levels (`GroupVolume.changes`), so steps do not add up.
- *Names*: the classes in the neutral package carry "Snapcast" in their names (`SnapcastRpc`, `SnapcastGroup`, ...) because `tasks.md` prescribes them. This is the one place where the word is used outside strings and docs, and the package name stays neutral. Open for veto together with the package decision above; renaming later is mechanical.
**Rationale**: each point was the simplest thing that satisfies the security rules and the tests; recording them stops the reviewer from finding them again as deviations.

## 2026-11-10 - Group 2 fixes (review cycle 1): how the findings were solved
**Context**: Review cycle 1 of Group 2 found six warnings (W1 to W6) and a list of suggestions.
**Decision**:
- *W1, order*: the result of a call that changes the model is handed to the listener executor **as an event in the same queue as the notifications** (`SnapcastCaller.callOrdered`, implemented by `SnapcastRpc`); the caller waits until the handler has run. `SnapcastOperations(caller, updater)` uses it for the status and for every change of our own. Alternative rejected: numbering the lines and letting `setStatus(status, line)` keep newer notifications, because a notification that is applied before the status arrives would have to be kept somewhere. `callOrdered` from a listener fails at once with `IllegalStateException` (it would wait for its own thread).
- *W2, scan*: a `"` outside a string is accepted only directly after `{`, `[`, `,` or `:` (white space aside), as Android's `JSONTokener` decides where a string starts. `de.yaacc.yxc.YxcJson.bracketDepth` has the same gap; it is older code and out of scope here (reported to the orchestrator).
- *W3, queue*: notifications of methods outside `SnapcastModelUpdater.isKnown` are dropped at the reader and only set the "read again" flag. The queue has a byte budget (4 MiB of lines, `SnapcastLimits.MAX_QUEUED_NOTIFICATION_BYTES`) besides the count (256); a notification is always taken into an empty queue, so the memory bound is the budget plus one line (1 MiB). A batch shares the size of its line between its notifications.
- *W4, silent peer*: a call that ends at its deadline closes the connection when its request is not out yet, **or** when no byte at all was received since the request was written. Any traffic (a notification, a part of an answer) shows that the peer is alive. The reconnect cycle (backoff, ceiling of 5) takes over. `reconnect()` replaces a connection from any state except CONNECTING and CLOSED.
- *W5, rig switch*: the one switch is the system property `snapcast.rig`, forwarded in `yaacc/build.gradle` only when it is set. The environment variable `SNAPCAST_RIG` was removed so that there is one documented way.
- *Own changes*: the server does not notify the connection that made a change (`server/server.cpp`), so `SnapcastOperations` patches the model after each successful call with the notification the others get; `Stream.AddStream` and `Stream.RemoveStream` cannot be patched and ask for a re-read.
- *Exceptions*: `SnapcastException.io` and the JSON syntax errors keep **no cause** (the text of a network exception or of an `org.json` error can hold the address or the server's text). `INTERNAL` keeps its cause: it comes from our own code or an `Error`. `toString()` of stream and server info prints fixed words and numbers only.
- *`setGroupClients`*: `null` and an empty list are caller errors (`IllegalArgumentException`, as documented for a wrong argument); an empty list would dissolve the group.
**Rationale**: smallest change that closes each finding without a second mechanism; the ordering fix also gives the own-change patch its ordering for free.

## 2026-11-10 - Stream.OnProperties arrives without params
**Context**: the model ignores the stream metadata; keeping 1 MB payloads in the notification queue only costs memory.
**Decision**: `Stream.OnProperties` is delivered to listeners with empty params and weight 1. A later group that needs track metadata must add the params for that method deliberately.
**Rationale**: security review rule "unknown or unused notifications are not queued with their payload"; found in review cycle 2/3 of Group 2.

## 2026-11-10 - Group 3 (discovery and the receiver model): choices made while building it
**Context**: Group 3 (`de.yaacc.multiroom.discovery`, `SnapcastSession`, `SnapcastGroupDevice`, `SnapcastReceivers`, the live source) left a few points open in `design.md`.
**Decision**:
- *Server key and merge*: the key is the canonical text of the control endpoint (`host:port`; an IP literal in one canonical form, IPv6 as eight hex groups in brackets; a host name in lower case). A server found by mDNS and typed in **as an IP address** is one entry. A manual entry written as a **host name** is a different endpoint from the address mDNS reports and is not merged with it (it would need a lookup to know; the user can type the address). Alternative rejected: resolving manual names to merge, because it adds a lookup path for little gain.
- *Address ranges*: discovered servers: loopback, IPv4 10/8 172.16/12 192.168/16, link-local (169.254/16, fe80::/10) and IPv6 unique-local fc00::/7. The deprecated IPv6 site-local range fec0::/10 and the carrier-grade NAT range 100.64/10 (Tailscale and the like) are **refused**; a manual entry is not range-filtered (the user chose it) except that unspecified, multicast and broadcast literals are refused. The strict parser is hand-written for IP literals so that no input can cause a name lookup.
- *Cap and grace*: 16 servers in total; a lost entry makes room first, a manual entry may also take the place of a discovered one, never the other way round; at most 32 service names are remembered. The grace for a lost service is 30 s (`SnapcastDirectory.DEFAULT_GRACE_MILLIS`); a restart of the discovery gives every discovered entry that is not seen again the grace period.
- *Connections*: opened lazily by `SnapcastReceivers` for the **listed** servers while a page is visible (`pageStarted`), for a **retained** server (a player, Group 4) and for the servers of **chosen** groups on `wake` (called by `awaitReceiverDevices` on its look-ups); closed 30 s after the last page was hidden, except retained ones. `wake` does not start the discovery (nothing is scanned outside the page lifetime), so a selected group of a server that was only discovered (not typed in) is not known after an app restart until the receivers page has been shown; manual servers are known at once. Known limitation, see the report of Group 3.
- *Last known state*: the last status of a server stays after its link is closed or down, and its groups stay in the lists marked as offline, so a stored selection survives a hidden page; they disappear with the server (grace over, manual servers never) or when a fresh status lacks them.
- *Group ids*: a group id from the server must be 1 to 64 characters of letters, digits, `_` and `-` to become a receiver; the id `snapcast:<key>:<group id>` is parsed from the right and the key must be in canonical form. A group with another id is not listed (an ambiguous id could not be forged).
- *Names*: the name of a row is the group name, else the first member's set name, else its host name (never its id, which is a MAC), else the label "Snapcast group", cut at 64 characters and cleaned with `SnapcastDisplayText`, plus " (Snapcast)"; offline: " (Snapcast, offline)". Snapcast is the product name and not translated; "Snapcast group" and "offline" are strings in the 7 locales.
- *Session*: three own threads (listener, worker, timer) besides the reader and writer of the RPC; a failed read is repeated up to 5 times in a row, only for timeouts, I/O errors and malformed answers (not for an error the server answered, such as 401); a one-second tick delivers held-back re-reads and runs only while the connection is up; `retry()` (page visible) is the only caller of `SnapcastRpc.retry()`.
- *Transport*: `SocketTransport` got a constructor for an `InetAddress` (nothing is looked up); host names go through `SnapcastResolver` (helper thread, 5 s, at most 2 lookups at once) in `ResolvingTransport`.
- *Live source*: `ReceiverLiveUpdates.Sources` got two default methods (`startSnapcast`, `stopSnapcast`); a change of the groups is one `Target.refresh()` after a 300 ms coalescing window. The classic receivers tab (`ReceiverListFragment`) starts the same source between `onResume` and `onPause`.
- *Playing before Group 4*: a Snapcast group can be chosen and listed, but `PlayerService` is not touched, so starting playback to it before Group 4 would make an `AVTransportPlayer` for a device without services. Group 4 adds the branch.
**Rationale**: each point is the smallest thing that satisfies the security rules and the tests; recorded so the review does not find them again as deviations.

## 2026-11-10 - Fix Group 3 (review cycle 1 of Group 3): choices made while fixing it
**Context**: `review.md` "Cycle 1 (Group 3)", warnings W1 to W3 and the suggestions; `tasks.md` "Fix Group 3" (F3.1 to F3.4). This supersedes the "Known limitation" in the Connections bullet of the Group 3 entry above (a selected group of a discovered server is now kept across a restart) and the "Playing before Group 4" bullet (there is a guard now).
**Decision**:
- *F3.1 guard*: `PlayerService.createPlayer` returns null with a toast ("Playing to Snapcast groups is not available yet", string `snapcast_play_not_available` in the 7 locales) for a `SnapcastGroupDevice`; the decision is the static `PlayerService.isNotPlayableYet(Device)`. The toast is posted to the main looper (the callers run on workers). Both callers skip a null player, `createQueuePlayers` before it builds the share lease, so no share is registered. Group 4 (task 4.4) replaces the guard with the real branch.
- *F3.2 selection survives a cold start*: `SnapcastGroupSource.isPending(id)` is true when the id parses, its server is listed in the directory and the server has delivered no status yet; `UpnpClient.getReceiverDevices()` does not drop such an id (it is still not returned as a device, and `countMissingReceivers` still counts it as missing, so `awaitReceiverDevices` still wakes the connection). A server that answered without the group is not pending (the id is dropped as before), and neither is one that left the directory. The page start already connects to every listed server, so the status arrives there.
- *Discovered-only servers*: `SnapcastSelectedServers` (in `de.yaacc.multiroom`) stores the endpoint of every non-manual server that holds a selected group in the preference `snapcast_selected_servers` (plain `host:port` lines, no name, no group id, no credentials; strict parse on load, address literals only that pass the range filter again, at most 16; same storage style as the manual list). `UpnpClient.setReceiverDeviceIds` tells the source (`selectionChanged`), which writes only when the list changed, and the server is forgotten as soon as no selected group refers to it. The hub restores the list at construction into the directory as **remembered** servers (`SnapcastDirectory.setRememberedServers`): listed without being announced, not aged out by time, never taking the room of another server. When the discovery starts (a page is shown) a remembered server that is not seen gets the normal 30 s grace and then leaves, which drops the id from the selection through the normal path and the store through `selectionChanged`. So a selection of a server that is switched off is dropped after one page view of 30 s, like any discovered server; a manual server stays for ever (remove it in the settings, or clear the selection). Nothing is scanned outside the page lifetime (`wake` still does not start the discovery).
- *F3.3 stable identity*: `SnapcastReceivers` keeps the last `SnapcastGroupDevice` per group id and returns it while name, offline flag, stream and member count are unchanged (`SnapcastGroupDevice.showsSame`); a changed group gets a new instance, a vanished one is evicted at the next `groups()`, `shutdown()` clears all. `findGroup` uses the same cache, so a selected device and a listed device are one object. The name is part of the comparison, so a change of the language gives new instances. `DeviceDiffCallback` and `DeviceSheetAdapter` are unchanged (they compare by identity, which now holds).
- *Cut at 64*: `groups()` builds at most 64 devices **in server order** (servers sorted by key, groups in the order of the server), then sorts those by name. Before, the 1024 possible groups were sorted by name and the first 64 kept. With more than 64 groups in total the choice of which are shown is different (deterministic either way); it only matters for a very large setup.
- *F3.4 taken* (each with a test that was seen to fail without the change): leading zeros in an IPv4 part of a manual entry are refused (`010.0.0.1`, also inside `::ffff:`); `SnapcastJson.displayText` (and with it `SnapcastDisplayText`) does not cut inside a surrogate pair; `SnapcastSessionTest.sessionThreadsAlive` ignores the threads that existed before the test; the **tick after a reconnect**: the bookkeeping moved into the pure `SnapcastTickGate` (the running flag is cleared before the connection is looked at, so a start that lands in between schedules its own chain); the **directory snapshot outside the lock**: `pageStarted`, `retain`, `wake` and `onServersChanged` now read the list inside the lock through the new quiet `SnapcastDirectory.snapshot()` (expired entries left out, no listener called), after a `directory.expire()` outside the lock; the **old resolve clearing a new queue's entry**: `SnapcastResolveQueue.done(Pending)` clears only the entry that is active now (identity), `SnapcastNsd` uses it; **`SnapcastNsd` stop right after start**: the per-call state moved into the pure `SnapcastBrowseHandle`, a stop before `onDiscoveryStarted` is held back and made when the platform confirms the start; listeners of an earlier browse whose stop is still waiting are ignored (generation check).
- *F3.4 not taken*: (a) `SnapcastDirectory.serviceFound` reviving a lost server announced under a new name when 32 service names are known, and the Javadoc line about a second host announcing the same service name: not named in the fix task, no regression, left for a later cycle; (b) the 64-receiver cut of `ReceiverLiveUpdates.watched`: only matters with a very large setup and changes the feed order, outside the files of this fix; (c) a cache of the sorted list per status version: not needed any more (the cache per group removes the allocation, and the build stops at 64).
- *Not verifiable here*: the changes in `SnapcastNsd` and `SnapcastHub` (Android classes, no JVM test); the pure parts they delegate to are tested. The interleavings of the two threads are not forced in a test: the stale-snapshot case is reproduced deterministically with a directory listener that changes the list while `servers()` is still returning (the same stale answer), the tick case with a start from inside the gate's check.
**Rationale**: the smallest changes that make the review's cases impossible, each with a failing test first; the remembered-server store reuses the manual list's style and limits so that no new kind of input is trusted.

## 2026-11-11 - Fix Group 3b (review cycle 2 of Group 3): choices made while fixing it
**Context**: `review.md` "Cycle 2 (Group 3)", warnings W4 and W5 and the cheap suggestions; `tasks.md` "Fix Group 3b" (F3.5 to F3.7).
**Decision**:
- *F3.5 flaky test (W4)*: `SnapcastSessionTest.aFailedReadIsRepeated` waits (`await`) for `getLastErrorKind() == null` after the status shows up instead of asserting at once; the worker publishes the status inside `operations.getStatus()` and clears the error one statement later. Test only: the order in `readStatus` is not changed (clearing the error before the status is published would hide a failure of the read that is still in progress). The other assertions of the class were checked: `itReadsAFreshStatusWhenTheConnectionComesUp` asserts a null kind that was never set, `aServerErrorIsNotRepeated` waits for the code first (the kind is set before the code), `aFailedReadIsRepeatedWithinTheRateLimitAndNotForever` expects a kind that is set and never cleared.
- *F3.6 pending id and the wait (W5)*: the simpler rule, **a pending Snapcast id is not waited for**. `countMissingReceivers` does not count an id for which `isPending` is true, and `awaitReceiverDevices` calls `snapcastGroups.wake(...)` once up front (non-blocking) instead of in every look. So a server that never answers costs no wait and no search at a play; the other selected receivers wait as before and are not slowed by the group. The pending id stays in the selection, is not a ready receiver and is not played; a user who selected only such a group gets the existing "no receiver selected" message at once. Rejected: "first look only" (still a 2.5 s wait with a search at every play with a dead server). Group 4 can decide again whether a play should wait for the first connection of a group once there is a player for it.
- *F3.7 cheap suggestions taken*: one toast per call of `createPlayerFor` / `createQueuePlayers` (`PlayerService.withoutNotPlayableYet` takes the Snapcast groups out of the list first and posts one toast via the package-private `notifyNotPlayableYet`; `createPlayer` keeps the guard and returns null silently as a second line of defence), which also means no group reaches `YxcPlayTargets.resolve`; the `setRememberedServers` Javadoc says that a lost entry may be evicted when the list is full (code unchanged, test added); `SnapcastNsd.start` calls `directory.discoveryRestarted()` before it returns on a missing NSD service (Android class, not testable here); tests of the wiring with a spied `PlayerService` and a mocked `UpnpClient` (no player, one toast, nothing for an empty call).
- *F3.7 not taken*: (a) pruning the remembered servers at `restore()` against the stored selection (the hub has no access to it; a stale endpoint is listed and connected to for 30 s per page view and then goes, and any change of the selection rewrites the store); (b) a stored manual entry with leading zeros (`192.168.001.010`) is dropped at the next read: unlikely, to be noted in the Group 6 documentation (manual addresses are written without leading zeros).
**Rationale**: no wait and no repeated cost for a server that is down; the rest are one-line corrections with tests where a test is possible without a device.


## 2026-11-11 - Group 4, the pure parts (4.2, 4.3 and the code draft of 4.1): choices made while building them
**Context**: `de.yaacc.multiroom.feed` (pacer, feeder, converter, stream handling, Media3 tap draft). The player (4.4) and the device spike (4.1) wait for the owner; these classes are plain Java except `PcmTapAudioProcessor` and `FeedTapChain` (Media3). Facts used: `docs/tech.md` "Feeding a server with a TCP stream source" and "Rig run and feed spike".
**Decision**:
- *Pacing (`RealTimePacer`)*: one anchor time plus the bytes sent since; the earliest time to write `n` bytes is the end of the audio sent so far (including those `n` bytes) minus the look-ahead of 3 chunks, so the first three chunks go out at once and the lead never exceeds 60 ms. The anchor moves forward by whole seconds as bytes are counted (no overflow, exact at 44.1 kHz). A write that comes more than 2 chunks after the time the audio sent so far ran out **re-anchors to now** (no burst, no debt); one chunk late counts as a late chunk. The unit of lateness is "how long the stream had nothing", so a write much larger than the look-ahead is an underrun by construction (not a use case: the feeder writes whole chunks).
- *Feeder behavior (`PcmFeeder`)*: the writer **never underruns**: when the queue has no full chunk at the time the next audio is due it pads a partial tail with zeros, or writes an all-zero chunk, for at most 50 chunks (1 s, `silenceFillChunks`); then it waits without writing and the pacer is reset, so the first audio after a pause anchors the clock again (no late-chunk count for a pause). It starts in that waiting state, so no silence goes out before the first audio. Silence is written at the due time, not early. The queue is a byte ring of at most 8 chunks; `write` waits at most 200 ms for room and then drops the rest and counts it (a partial acceptance is possible and reported as `false`). The watchdog is a thread of its own that looks every 250 ms (real time) and compares the injected clock against the start of the running write (10 s). `close()` and a failure both end both threads and the socket; the listener hears of a failure once, never of a close.
- *Connect target (`PcmFeeder.connect`)*: takes an `InetAddress` and a port, never a string; refuses null, the wildcard (`0.0.0.0` is what a server reports as `uri.host`; connecting to it reaches the phone itself) and multicast addresses, and ports outside 1 to 65535, before anything is opened. A failed connect is an `IOException` with a fixed text and no cause (socket exceptions carry the address). Nothing in these classes logs. Group 4.4 must read `SnapcastRpc.getPeerAddress()` after the last `ensure()`, abort when it is null, and pass it straight to `connect` (security review S11).
- *Converter (`PcmFormatConverter`)*: always 16 bit stereo, rate untouched. 16 bit stereo is copied; mono is duplicated; 3 to 8 channels use a documented table (Android channel order, centre and surrounds at 0.7071, LFE dropped, each side divided by the sum of its weights so the sum can not clip; about 7.7 dB quieter for a front-only signal at 5.1, like FFmpeg's default). 8, 24, 32 bit and float round half up and clip; NaN is silence; infinity is limited before the mix so it can not become NaN.
- *Streams (`SnapcastStreams`)*: the phone name keeps letters and digits of any script plus space, `-` and `_` (everything else becomes `_`, 32 code points), so a name like `a&mode=client` is sanitised before it is encoded and the encoder (`percentEncode`, unreserved characters only, UTF-8) is tested on its own with the raw name. An existing stream is **adopted** only with our exact name, `tcp`, `query.name` equal to the name, `mode=server`, the sample format, host `0.0.0.0` and a port of our range (4953 to 4962). A stream with our exact name and another shape is **replaced** (remove, then add) unless a group plays it (result `CONFLICT`, nothing changed). The port candidates are the ten ports of the range minus every port that any stream URI of the status names; only the error -32603 (a taken port or a duplicate name) tries the next port, any other server error stops at once. The answer of `Stream.AddStream` is accepted only if it names exactly the id we asked for; another id is `REFUSED` and nothing is recorded or touched (a hostile server could name a stream of the user). Typed results: `READY`, `REFUSED` (reason = the server's text, cleaned and cut at 200, hint key `snapcast_feed_static_source_hint`), `UNAUTHORIZED` (hint key `snapcast_feed_authorization_hint`), `NO_FREE_PORT`, `CONFLICT`, `FAILED`; the strings for the two hint keys are added in Group 5. Leftovers (marker in the name, `tcp`, no group on them, not the one we hold) are removed by `ensure()` and `removeLeftovers()`, at most 8 per run. `useFor` records the previous stream per group (pruned against every fresh status); `release` restores only a group that is still on our stream, only to a previous stream that still exists. `removeIfIdle()` is driven by `noteAudio()` (our own last audio), the stream status `idle` is not read anywhere. `shutdown()` restores every recorded group, then removes our stream only if it still carries the marker and is `tcp`; on a failed call it keeps the records so a second call continues.
- *Tap draft (4.1)*: the chain is `ToInt16PcmAudioProcessor`, `SonicAudioProcessor` (rate), `PcmTapAudioProcessor` (channels, hand-over, silence or pass-through on the speaker). Media3's `ChannelMixingAudioProcessor` is not used: its constant-power matrices stop at 6 channels and it needs `SparseArray`. The questions for the device are in `docs/tech.md` "Snapcast feed tap (draft)". 4.1 is **not ticked**, nothing in `PlayerService` or the player package was touched.
- *Tests*: the pacing and the feeder run on a clock the test moves (`ManualFeedClock`: `sleepNanos` blocks until the test advances it; no sleeping for pacing), so the feeder tests need real time only for thread hand-offs and bounded waits (the longest single wait is 2 s; the back-pressure failure test waits 300 ms). `SnapcastStreamsTest` uses a simulated snapserver (`SimulatedSnapcastServer`: status, AddStream with the real error codes, RemoveStream, SetStream); `FakeSnapcastServer` and `RpcTestSupport` are package-private in the control tests, so `SnapcastFeedIntegrationTest` serves the same simulation over a loopback socket to a real `SnapcastRpc` and feeds a real listener through the real socket.
**Rationale**: smallest design that satisfies the pacing facts of the spike (deadline pacing, small buffers, no burst, silence is cheap and keeps the server's clock steady), and the trust rules of the security review (the feed target is the control peer, nothing from a server reply is identity, connect target or removal target unless it carries the marker).
**Not verified here**: any audio, the Android classes (`SocketFeedConnection` runs on the JVM socket, `PcmTapAudioProcessor` against the Media3 classes on the JVM, but not inside ExoPlayer), Sonic's audible quality, and everything in the list of `docs/tech.md` "Snapcast feed tap (draft)".

## 2026-11-11 - Fix Group 4 (review cycle 1 of Group 4, pure parts): choices made while fixing it
**Context**: `review.md` "Cycle 1 (Group 4, pure parts)", W1 to W3 and the suggestions; `tasks.md` "Fix Group 4" (F4.1 to F4.4). Each finding was reproduced by a failing test first.
**Decision**:
- *F4.1 (W1)*: the writer no longer pads a partial chunk at once. A chunk with fewer bytes than a chunk is waited for; it is padded with zeros only when it is due **and** its first bytes have been queued for half a chunk (10 ms, `partialGraceNanos`). Half a chunk and not a whole one, because the server resyncs when a read ends after the next chunk's deadline (one chunk after the due time): the pad then still leaves half a chunk of margin. A start after dormancy therefore waits for the rest of its chunk instead of padding the first few bytes. The writer **wakes when audio arrives** (`FeedClock.wake`, with the permit semantics of `LockSupport.unpark`; `sleepNanos` may now return early and every caller looks again): the producer wakes it only while the writer waits for data (`needsData`, set before the queue is looked at again, so no write is missed), so a producer that delivers in real time uses the look-ahead and the lead no longer sits at zero. `write` refuses a length that is not whole frames (`IllegalArgumentException`; the tap and the converter produce whole frames). The test of the review (`everyByteArrivesInOrderInWholeChunksAndATailIsPaddedWithZeros`) is deterministic now: the clock does not move before all three pieces are queued, and the new tests assert the rule itself (first write smaller than a chunk, partial chunk at the due time, padding after the grace, wake on data).
- *F4.2 (W2)*: `shutdown()` (and so `removeIfIdle()`) removes the stream only when every restore succeeded **and** a fresh status shows no group on it; a group that somebody else moved there keeps it alive (result `false`, records kept, the next call tries again). A stream that vanished or no longer looks like ours is dropped from the records without a removal. `ensure()` reads the status again (`removeLeftovers()`) before it removes leftovers, so a group put on a leftover in the meantime is respected.
- *F4.3 (W3)*: 7 channels are FL FR FC LFE BL BR BC (BL left, BR right, BC both sides), as Media3 1.11.1 maps them; the class comment and `docs/tech.md` say so. A test places each channel of 3, 4, 5, 6, 7 and 8 channels alone and checks the side and the level from a layout table written in the test (not from the implementation's indexes).
- *F4.4*: pacer tests with a clock at 0, one that starts negative and crosses 0, and ones that wrap around `Long.MAX_VALUE`/`Long.MIN_VALUE` (the arithmetic is difference based, so no change was needed). **Not done**: one all-zero chunk when leaving dormancy; the source (`asio_stream.hpp`) was read for the resync rule but does not show that the clients would drop a late first chunk, so it is a rig check (`docs/tech.md` "Snapcast feed tap (draft)", item 10). The writer priority is a task of the app side (4.4), item 11 there.
**Rationale**: the zero-insertion defect was real (a producer that hands over small buffers after a pause), not only a flaky test; the other changes keep a failed call from taking a stream away from a group.

## 2026-11-11 - Group 7 (Phase B: binary protocol and time sync, tasks 7.1 to 7.3): choices made while building it
**Context**: `design.md` "Phase B" and "Security rules for Phase B", `docs/tech.md` "Binary protocol" and "Phase B protocol: implementation notes". Pure Java in `de.yaacc.multiroom.protocol`; tests were written before the classes; the key safety rules were mutation-checked afterwards (twelve one-line mutations, each caught by at least one test; two tests had to be made stricter to catch the mutation: the unsolicited Time answer and the message deadline of the connection).
**Decision**:
- *Shared code.* `SnapcastJson` (control) became `public` with four public entry points (`parseObject`, `string`, `integer`, `bool`; the text cleaning is reached through the already public `SnapcastDisplayText`), so the binary JSON messages go through the same depth/token pre-scan; the rest stays package-private. `RetryScheduler` and `SnapcastTransport`/`SocketTransport` are reused as they are (the port 1704 is passed by the caller). `yaacc/build.gradle` also hands `snapcast.rig.seconds` and `snapcast.rig.expectChunks` to the test JVM.
- *Codec.* Types 1 to 5, 7, 8; type 0 and 6 and every other number are "unknown" and skipped by size (at most 64 KiB). Bytes after the fields inside a message are ignored (forward compatibility); a whole-frame `decode` with bytes after the frame is MALFORMED. A length inside a message is compared with what is left before anything is reserved (BAD_LENGTH); a field that does not fit is TRUNCATED. The reader's body buffer starts at 64 KiB and grows with the bytes that arrive. The allow-list (`pcm`, `flac`, exact match) is applied while decoding the CodecHeader, so a `CodecHeaderMessage` always holds a validated header; the codec name appears only cleaned and cut to 32 characters in the text of the error.
- *Headers.* PCM: integer PCM only (tag 1), 1 to 8 channels, 8000 to 192000 Hz, 16/24/32 bit, block align must match; chunk walk of at most 16 chunks, a `data` chunk header must follow (other chunks in between are skipped, at most 16 chunks in all); RIFF size and data length are ignored. FLAC: "fLaC", the first block must be STREAMINFO of exactly 34 bytes, 16 or 24 bit (the engine range chosen here; FLAC itself allows more), block type 127 refused, later blocks (at most 32) must fit, bytes after a last-block flag refused; a chain that ends exactly at the end of the header without the flag is accepted (lenient on purpose, because the real header of the server is not seen yet, **rig**).
- *Time sync.* Sample = (c2s - s2c) / 2 as in `tech.md`; filter parameters and the proven bound are in `ClockOffsetFilter` and `docs/tech.md`. The jump limit (1 s) is chosen so that network noise cannot reach it: accepted samples have a round trip of at most 500 ms, so two of them differ by at most 500 ms. Three agreeing candidates (within 100 ms) restart the window and raise `epoch()`; the scheduler empties its queue on a new epoch. Beyond the stated sample checks the connection refuses an answer whose network time (c2s + s2c) is more than 1 ms longer than its own clock measured for that request, and ignores an answer whose `refersTo` is not an outstanding request (at most 16 outstanding). Schedule: 16 requests 100 ms apart after the ServerSettings, then one per second (the reference client does 50 quick ones and then one per second; 16 fills our window).
- *Scheduler.* "Too far ahead" means the timestamp is more than 5 s after the corrected clock, i.e. the play time is more than `bufferMs + 5 s` away without the client latency (otherwise a latency of -10 s would drop every fresh chunk). A fifth action `DROP_QUEUE_FULL` was added for the bounded queue (512 chunks, 4 MiB, the new chunk is dropped). Late tolerance 0, release lead 250 ms (both configurable); chunks wait while the header is not accepted or the clock is not synchronised.
- *Connection.* One reader thread per attempt (also sends the Hello and the Time requests, so there is no second thread on the socket); listeners on a serial executor; chunk backlog bounded to 256 chunks / 4 MiB, beyond that the chunk is dropped and counted; a message must be complete 10 s after its first byte, settings and header within 10 s of the Hello, nothing at all for 10 s drops the connection; more than 100 frames in a row of unknown or client-only types drop it. Error 401/403 and an unsupported codec are permanent (no retry), every other loss is retried like the control client. `onLost` once per outage, ended by a complete handshake. `sendClientInfo(volume, muted)` was added (the renderer mapping of Group 9 needs it); `forAddress` is a convenience. Package-private test hooks: `awaitTimeSamples`, `awaitFramesRead`, `isReaderRunning`.
- *Tests and the rig test.* No sleeps for synchronisation (latches, event queues, a manual clock); the only sleeps are the pacing of a hostile fake sender. The fake server ends a script with a FIN and drains the client's input, because a plain close with unread input sends a reset that can wipe data the client has not read yet (this made the flood test fail at first). `SnapcastBinaryRigTest` is skipped without `-Dsnapcast.rig=<host>`.
**Rationale**: the server is untrusted; every number from it is bounded before use; the pure parts have JVM tests and the unsure ones are named for the rig.
**Not done / unsure**: nothing was run against a real snapserver (no Docker here): the FLAC header the server really sends, whether an idle stream sends chunks, and the offset over 10 minutes are for the owner's rig run. The audio engine is Group 8.

## 2026-11-11 - Fix Group 7c (security review of Group 7: W1, S56, S57, S60, S62; S10 of the general review): choices made while fixing it
**Context**: `security-review.md` "Cycle 1 (Group 7)"; `tasks.md` "Fix Group 7c". New tests were written first; 11 of them failed against the code of Group 7b (the flood, Hello-skip, chunk-cap, codec-header-cap, stalled-write, `sendClientInfo` and `forAddress` cases); the legitimate-rate test, the header-counter test and the clock test pin behaviour that was right and are mutation-checked instead.
**Decision**:
- *W1, frame budget.* Every frame the server sends (chunks, Time answers, settings, unknown ones) counts in a window of one second of the injected `MicroClock`; the 2001st frame in a window ends the connection as PROTOCOL_ERROR (`Config.maxFramesPerSecond`, default 2000). Why 2000: a real server sends one chunk per `chunk_ms` (20 ms by default, so 50 a second; even 5 ms gives 200) plus one Time answer per request (one a second after the burst of 16), so 2000 a second is a chunk every half millisecond, ten times the rate of a 5 ms chunk and 40 times the default; a flood at the reviewer's measured 1 million frames a second is cut off after 2000 frames, that is about 2 ms of reader time. A fixed window allows a burst of up to 4000 across a window edge, which is still bounded. The window restarts on the clock, so the tests use a manual clock (all frames in one window) and need no CPU measurement. The 3000-frame flood tests raise the budget on purpose.
- *W1, strange frames.* An unsolicited Time answer counts as an unexpected frame and no longer resets the run of unknown frames (99 unknown + 1 unsolicited Time repeated now ends at the 101st frame). Only an answer to an outstanding request (at most 16) is "expected". Hello and ClientInfo frames (client-only types) are skipped by size in the reader of the connection (`FrameReader.forClient`), never parsed; the plain reader still decodes them, because the fake server and the codec tests read them.
- *S56.* The size cap of a CodecHeader is now 64 KiB + 64 bytes (a name of at most 32 bytes, the header of at most 64 KiB, two lengths) instead of 8 MiB: tighter than the design's "8 MiB for WireChunk or CodecHeader", and the real headers are 44 and about 42 bytes. A WireChunk above the connection's own backlog budget (`maxPendingChunkBytes`, default 4 MiB) is refused at its header (the connection is dropped as PROTOCOL_ERROR) instead of being read in full and then dropped; the codec itself still allows 8 MiB. The payload of a chunk is copied once less (the message takes over the array cut out of the body).
- *S57.* A writer thread per connection attempt (`snapcast-bin-writer`) is the only code that writes to the socket; the reader and `sendClientInfo` hand bytes to a queue of 32. `sendClientInfo` keeps only the latest value (one queued marker), so it can be called as often as a slider moves; it returns false when not connected or when the queue is full. A full queue means the server does not read (a socket write has no timeout): the connection ends as TIMEOUT ("the server does not read"). A failed write closes the socket and so ends the reader. `close()` still ends everything.
- *S60.* `forAddress` refuses null, the wildcard and multicast addresses (IllegalArgumentException; bad ports were refused already by `SocketTransport`) and its javadoc says to pass a resolved address. *S62.* `MicroClock.fromNanoSource(LongSupplier)` is the seam; the javadoc says Android must use `elapsedRealtimeNanos` (Group 8). *S10.* A test delivers 21 headers one by one to a listener that keeps up.
- *Hand-offs (tasks.md, Groups 8 and 9).* S58 (identical-header ignore, decoder restart limit, no `AudioTrack` re-creation on an epoch change), S59 (buffers sized from validated rate/channels/bits only, FLAC block sizes not trusted, drop a partial frame), S13 (coalesced settings can overtake an earlier codec header), S62 (the Android clock), S60 (pass a resolved address), S61 (per-server Hello ID, generic OS/arch/version strings, disclosure text).

## 2026-11-12 - Group 8 (Phase B: audio engine, task 8.1 spike built and 8.2 pure parts): choices made while building it
**Context**: `design.md` "Phase B" and "Security rules for Phase B", the hand-offs S58, S59, S13, S62 in `tasks.md`, `docs/tech.md` "Snapcast client engine" (new, with the Android guesses) and "How to try the Snapcast client (device spike)" (new). Package `de.yaacc.multiroom.client`. The pure core was built against a simulated output (`SimulatedSink`, manual clock, markers in every frame); **the sandbox cannot play audio, so the listening test (kill criterion of 8.1) is the owner's.** Tests: 101 new (96 in `de.yaacc.multiroom.client`, 5 in `SnapcastClientResourcesTest`); 13 one-line mutations of the engine, drift controller and tracker were run, 12 were caught at once, the thirteenth (the engine's own size check of decoder output) led to the test `theEngineChecksTheSizeOfWhatAnyDecoderReturns`.
**Decision**:
- *Architecture.* `SnapcastClientEngine` is a single-threaded, deterministic core behind four interfaces (`AudioSink`, `DecoderFactory`/`FrameDecoder`, `OffsetSource`, `MicroClock`). `EngineHost` gives it one thread and a bounded queue (1024 events, chunks only while it is three quarters empty, so settings, headers and a loss always find room), is the listener of `SnapcastConnection`, and has a watchdog (`isStalled`/`abandon`). The service owns the connection and the host. Deliberately **not** done: a second thread for decoding (the decoder calls have short timeouts instead), Opus/Ogg (out of Phase B), channel counts above two (typed refusal `UNSUPPORTED_CHANNELS`), 24/32 bit integer PCM is converted to 16 bit (`PcmConverter`), not refused.
- *Time model.* The output reports `frame f presented at t` (engine clock); the engine extrapolates it to the frame it is about to write and compares with the play time `anchor + s/rate + bufferMs - (server latency + manual latency) - offset`. This avoids a history of what was written (only the writer's frame count and the stream index matter, and corrections adjust the drift at once). The output is fed continuously (silence when nothing is due), so it never runs dry and always has a position. Alignment before the first audio, after a gap and after a step above 30 ms is exact (silence or skipping, to 1 ms); while playing, single frames are dropped or repeated, at most one per 400 frames, on the median of 7 measurements with a dead band of 2 ms and hysteresis; the correction shifts the stored measurements so the median does not overshoot. A drift of more than 300 ms late flushes the output (the queued audio is old); flushes because of lateness or underruns are rate limited to one per 500 ms. Numbers are in `ClientEngineConfig` (defaults) and were chosen without a device: **they are the first things to adjust after the owner's report.**
- *S58.* An identical codec header is ignored (counted). A different one restarts the decoder at most 12 times in 60 s of the engine clock (config `maxDecoderRestartsPerMinute`); the 13th ends the session with `HEADER_FLOOD` and frees the output (tests: 1000 headers in one second with alternating formats; 30 headers six seconds apart are all accepted). An epoch change empties the engine's queues and the anchor (the scheduler empties its own) but neither flushes nor re-creates the output (tests: one change; 400 changes in 6 s: one `open`, zero flushes). A new sample rate or channel count re-opens the output once per accepted header; the same format keeps it.
- *S59.* `maxFramesPerChunk` is `rate x 2 s` from the validated rate and is the only size passed to a decoder (a test passes FLAC headers with block sizes 65535 and 16 and sees 96000 both times); PCM chunks lose a trailing partial frame (counted); a chunk that would decode to more than 2 s is dropped before conversion (PCM) or when the decoded size is seen (the engine checks every decoder's result; the platform FLAC decoder also caps what it copies out of MediaCodec); the engine's own buffers are sized from the format only (one block of 20 ms of silence).
- *S13.* Server settings are global state: bufferMs, latency, volume and mute apply whenever they arrive and are never paired with a header; a settings value that arrives before the first header is kept (test).
- *S62.* The service builds one `MicroClock.fromNanoSource(SystemClock::elapsedRealtimeNanos)` and gives it to the connection and the engine (the offset is relative to that clock). `AudioTrack.getTimestamp()` is on `CLOCK_MONOTONIC`, so `AudioTrackSink` converts a report by its age (`System.nanoTime()` minus the timestamp's time), which stays right across deep sleep.
- *Hostile input.* Chunk timestamps are never trusted: the scheduler's saturating maths plus a limit of 10 minutes (and 2^38 frames) from the anchor, beyond which the timeline starts anew; a gap in PCM timestamps up to 3 s is filled with the same amount of silence, a longer one starts anew, an overlap is trimmed (the repeated chunk test); the decoded audio that waits is bounded to 3 s; decode failures drop the chunk, 8 in a row end the session; a sink that rejects writes or a position that never comes (5 s) end it with a typed reason. A seeded fuzz test (200 sequences of 400 random events: headers of all kinds, settings, epoch jumps, losses, underruns, random chunks) checks that nothing throws and the bounds hold.
- *Hello.* Per server derived id (`yaacc-` and 16 hex characters of SHA-256 over a random per-installation secret and the server's endpoint text), never a hardware id; the secret is a new preference (`snapcast_client_spike_secret`); host name = the UPnP server name preference; program "YAACC", OS "Android", arch "unknown", version "spike" (S61 asked for generic strings); MAC placeholder. Group 9 replaces the secret with the YAACC device UDN; the derivation stays.
- *Spike entry point.* Settings > Snapcast (experimental) > "Snapcast client spike (listen test)", a checkbox, **default off** (a test pins the default and the key); only while it is on the entry "Snapcast client listen test" is visible; it opens an `AlertDialog` (host[:port] with default port 1704, manual latency in ms clamped to -2000..2000, Start, Stop, Apply latency, a selectable monospace status text read from `SnapcastClientRuntime`, so closing the dialog or switching the screen off loses nothing). Switching the option off ends a running session. `SnapcastEndpoint.parse(text, defaultPort)` was added (the one-argument form is unchanged) so the strict host check is reused. The field is filled from the first server of the Snapcast server list when nothing is remembered (the host only; the port stays 1704). The status text is English and diagnostic on purpose; dialog texts, the notification and the settings texts are in the 7 locales (`SnapcastClientResourcesTest`).
- *Service and resources.* `SnapcastClientService`: foreground service of type `mediaPlayback`, `exported=false`, `START_NOT_STICKY`, started only by the dialog (startForegroundService; the notification is posted before anything else), standard notification with a Stop action on the app's channel. Partial wake lock (with a safety timeout of 8 hours) and Wi-Fi lock (`FULL_LOW_LATENCY` from API 29, else `FULL_HIGH_PERF`) are taken when a session begins and released on **every** end: Stop, connection gave up, engine failure, watchdog, `onDestroy` (the locks are released before the blocking teardown, which runs on its own thread). The name is resolved once on a worker (`SnapcastResolver`, bounded) and the connection gets the address (S60). No listener socket. No server text is logged (the classes log nothing). A permanent loss (authorization, codec/format) ends the session; other losses use the connection's retry rules (5 failures), then the session ends with `CONNECTION_GAVE_UP`. The notification is removed at the end; the final state stays readable in the dialog. Not done: audio focus handling and the `MediaSession` (the spike keeps playing through a call), a restart after the process dies.
- *Manifest.* Added `FOREGROUND_SERVICE_MEDIA_PLAYBACK` and the service. Reasons: with `targetSdk 33` Android does not enforce the new permission (the type attribute exists since API 29), but a target of 34 or higher requires it for `mediaPlayback`, it is a normal permission granted at install, and the owner listed it; nothing else was added because everything else the service needs is declared already: `INTERNET`, `ACCESS_WIFI_STATE` (not strictly needed for the Wi-Fi lock, already there), `CHANGE_WIFI_STATE` (Wi-Fi lock), `WAKE_LOCK` (both locks), `FOREGROUND_SERVICE`, `POST_NOTIFICATIONS` (the notification is not shown if the user denied it; the service still runs). `RECORD_AUDIO` and others are not used.
- *FLAC.* Done with `MediaCodec` (`audio/flac`, synchronous mode, `csd-0` = the server's header as is, decoder found through `MediaCodecList.findDecoderForFormat`, output 16 bit or float converted), no new dependency. Not unit tested (platform classes). If a device has no decoder the session ends with the typed reason `DECODER_UNAVAILABLE` and the text says so.

## 2026-11-13 - Fix Group 8j (general review cycle 4: flac stall, mutation survivors, stale statements)
**Context**: cycle 4 showed that a source stall of 40 to 300 ms leaves the flac stream shifted for good or silent (PCM fine). The owner is running long stability tests of the 8i build, so behaviour changes were kept to the flac placement and the skip path.
**Decision**:
