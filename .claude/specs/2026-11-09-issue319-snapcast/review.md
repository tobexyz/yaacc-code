### Warning
- [docs/tech.md "Feeding a server with a TCP stream source", state bullet; design.md:62] Wrong claim about silence: "default 0 = every chunk counts as audio, so the stream stays `playing` while data flows". `PcmStream::isSilent` (`server/streamreader/pcm_stream.cpp:278-281`) with threshold 0 does a `memcmp` against an all-zero chunk, so a chunk of digital silence IS silent; `AsioStream::do_read` (`asio_stream.hpp:210-219`) then sets `kIdle` after `idle_threshold` (100 ms) of such chunks, while chunks keep flowing. Consequence: a feeder that pads track gaps or pauses with zero bytes flips the stream to `idle` after 100 ms; design item 6 ("silence between tracks keeps the stream alive") holds for the connection and clock only, not for the status that Group 4 uses for idle cleanup and that the spike uses as a pass criterion. Fix: correct the bullet (idle = 100 ms of all-zero chunks, chunks still sent), and amend design.md:62 and the idle-cleanup rule in 4.3 to say that status `idle` does not mean no data.
- [tools/snapcast-rig/spike/FeedSpike.java:588-616 (RpcException), 329-337, 339-341] The spike throws away the JSON-RPC `error.data`. Snapcast puts the real reason there and only "Internal error" in `message` (`server/jsonrpcpp.hpp:1018-1019`, fixture `error_internal.json`). So `lastError.contains("already exists")` can never be true, the "leftover of an earlier run" hint is dead code, and a leftover `YAACC spike` stream makes the spike try all 10 ports and fail with "last error: JSON-RPC error -32603: Internal error" (reproduced with the fake server). A bind failure and a name clash are also indistinguishable. Fix: keep `data` in `RpcException` (message and data), test the check against it, and stop the port loop on a name error.
- [tools/snapcast-rig/README.md "Reading the result" and FeedSpike.java:301-302] The pass criterion for task 1.5 "`grep -c "No chunks available"` prints 0 for both clients" cannot hold. The client logs that line at info level once per second whenever its buffer is empty (`client/stream.cpp:271-279`), which is every second while its stream has no data (the `Default` pipe has no writer; before and after the feed). Also `moveFirstGroup` moves only ONE group (the rig starts with one group per client), so the other client never receives the spike's stream and logs the line continuously. Fix: count only inside the feed window (note the time before and use `docker compose logs --since`, or compare counts at start and end), and move both clients into one group (`Group.SetClients`, or move both groups) so that "both rig clients" really receive the feed as the task's Accept line says.
- [yaacc/src/test/resources/snapcast/ (task 1.3 Accept)] Fixture for "an unauthorized error" is missing: there is `error_internal`, `error_invalid_params`, `error_method_not_found` but no 401/403 document. The source gives the exact shape: `Server::onMessageReceived` answers `jsonrpcpp::Error("Unauthorized", 401)` and `Error("Forbidden", 403)` (`server/server.cpp:146-152`), not a -32xxx code. The README of the fixtures and tech.md also say nothing about it ("answers requests with an error"). Fix: add `error_unauthorized.json` (code 401, message "Unauthorized", id echoed) and `error_forbidden.json`, and note both codes in tech.md. Task 1.3 is ticked, so either add it or untick with a note.
- [yaacc/src/test/resources/snapcast/status_three_groups.json:215,224] The `YAACC test phone` stream has `"host": "0.0.0.0"` while `raw` is `tcp://0.0.0.0:4953?...`. The server's `StreamUri::toJson` puts host AND port into `host` (`common/stream_uri.cpp:173-179`), so a real status shows `"host": "0.0.0.0:4953"`. Group 4 reads the used ports of existing tcp streams from these URIs (design.md:59 "free-port choice"); a model tested on this fixture would be wrong. Fix: `"host": "0.0.0.0:4953"` and mention the host:port shape in tech.md.
- [tasks.md 1.1 (ticked) vs its Accept/Verify; design.md lines 4, 32, 34, 59, 62, 73] Task 1.1 is ticked but Accept and Verify are not met, and the status text only excuses the `(rig)` items.
