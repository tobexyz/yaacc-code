# Review: Snapcast support (#319)

The detailed per-cycle text of this file (1456 lines: per-line analysis, probes, mutation tables, "verified, no action" lists) was condensed on 2026-11-17 before the branch `feat/issue319` was squashed. What is kept: the verdict of every cycle, the findings that mattered with the fix in one line, the suggestions that stayed open (numbered as in the originals so references in `tasks.md`, `decisions.md` and `docs/tech.md` still work; **numbering restarts per group and collides with `security-review.md`: read the cycle heading**), and the remaining accepted risks. Verdict rule: FAIL if any Critical or Warning exists or tests do not pass.

**Not reviewed yet (postponed by the owner until he says so):** Group 12 as a whole (12A to 12C, tasks 12.12 to 12.23, Fix Group 12Ab) and everything of Group 11D / 12.x after the last reviews listed below. The only review of Group 12 is cycle 1 of 12A (FAIL); its fix (12Ab) was not re-reviewed; no security review of Group 12 exists.

## Group 1 (research, rig, fixtures) - cycles 1 to 3, 2026-11-10: FAIL, FAIL, PASS
- W: a silence claim in `docs/tech.md`/`design.md` was wrong (an all-zero chunk is silent even with threshold 0, so the stream goes `idle` while data flows); the spike dropped `error.data` (the real reason is there, `message` is only "Internal error"); the pass criterion "0 lines `No chunks available`" cannot hold (logged once a second when a client has nothing to play: it is a time window); missing 401/403 fixtures; `uri.host` is `host:port`; task 1.1 ticked without the binary layouts; wrong counts in the inventory (app code under `de/` only). All fixed (cycle 2 added two README/marker warnings, fixed in cycle 3).
- Suggestions taken: TXT records closed from the source (none), version note (notes read on `develop` `ea981ec`, the rig builds that commit), id `snapcast:<key>:<gid>` parsed from the right. Open and harmless: `feedEnd` taken after `cleanup()` in the spike, windows of runs shorter than 6 s are empty.

## Group 2 (control library) - cycles 1 to 3, 2026-11-10: FAIL, FAIL, PASS
- W1 answers and notifications handed out on different threads (stale model) - fixed by `callOrdered` (same queue as the notifications). W2 the JSON scan and Android's `org.json` disagree about where a string starts (depth/token limits bypassable) - fixed (a `"` opens a string only after `{ [ , :`). W3 unknown notifications queued with full params, queue bounded by count only - dropped at the reader, byte budget 4 MiB. W4 a vanished peer was never noticed - a call that times out with no byte received drops the connection. W5 the rig switch did not work as documented - `snapcast.rig` forwarded by Gradle. W6 test gap for a server that stops reading - added. W7 (cycle 2) lifecycle events of `reconnect()`/`sessionEnded()` out of order - enqueued inside the lock; Javadoc for Group 3 added.
- Suggestions taken in 2b/2c (own-change patching, `setGroupVolume` start levels, peer address accessor, `OnProperties` without params, the Javadoc usage notes). Open (cycle 3): none blocking.

## Group 3 (discovery, receiver model) - cycles 1 to 3, 2026-11-10/11: FAIL, FAIL, PASS
- W1 playing to a group made an AVTransport player for a device without services - guard + one toast until Group 4. W2 a stored selection did not survive a cold start - pending ids, remembered servers (`snapcast_selected_servers`). W3 `areItemsTheSame` compares UDN objects, a new device per call made every row "new" - one instance per id while unchanged. W4 flaky `aFailedReadIsRepeated` - awaits the cleared error. W5 a pending id cost three looks at every play start - a pending id is not waited for.
- Suggestions taken: leading zeros refused, surrogate pairs, tick race (`SnapcastTickGate`), snapshot inside the lock, NSD stop before start (`SnapcastBrowseHandle`). Open (cycle 3, harmless): a test with one group plus one plain device in `withoutNotPlayableYet`; `snapcastGroups.wake` runs at every play; wording of the "not available" message.

## Group 4 pure parts (feed) - cycles 1, 2, 2026-11-11: FAIL, PASS
- W1 zeros inserted in the audio when a start after dormancy was smaller than a chunk - wait for a full chunk, half-chunk grace, wake on data, frame alignment. W2 the stream was removed after a failed restore - `shutdown`/`removeIfIdle` keep it, re-read before removing. W3 7-channel order wrong for Android - FL FR FC LFE BL BR BC, per-channel tests.
- Open (cycle 2, S1 to S6): the half-chunk grace after dormancy is shorter than needed there, `partialSince` is measured from the first look, `close()` drops the queue (the app waits about one chunk first), one assertion `>= CHUNK_NANOS / 2`, `removeIfIdle` costs two status reads per tick while a foreign group stays on the stream, mention the whole-frame rule in `PcmSink.write`.

## Group 4, task 4.4 (player) - cycles 1, 2, 2026-11-11: FAIL, PASS
- W1 compressed pass-through bypasses the tap - `PcmOnlyAudioSink` (the proposed `setAudioCapabilities` is dead with `Builder(Context)`, verified with `javap`). W2 a pause during the start was not honoured - `onReady` checks `isPaused()`.
- Suggestions of cycle 1 taken (always `controller.start`, stop retry, volatile `bound`, ExoPlayer error stops the player, media-session list). **Open (cycle 2): S1** a format without a decoder plays silently with no toast; **S2** resuming from the notification during a deferred start shows "playing" but starts nothing; S3 `mediaSession` field read twice (race with `onDestroy`); **S4** `PcmOnlyAudioSink` could also refuse a non-raw `configure`; S5 the delay toast can appear for a held-back start; **S6** device checklist: a device without an AC-3 decoder.

## Group 7 (binary protocol, time sync) - cycles 1, 2, 2026-11-11: FAIL, PASS
- W1 a stall inside a frame was cut by the time-sync wake-up timer - the receive timeout inside a frame is the time left of the message deadline. W2 unbounded listener events for settings, offsets and headers - latest-wins slots, at most 8 headers (a ninth drops the connection). W3 the shortest-round-trip rule was untested - two tests.
- Suggestions S1 to S8 taken (permanent `UNSUPPORTED_FORMAT`, `SnapcastJson` four public methods, close() javadoc, tests). **Open: S9** the owner's 10-minute rig run before relying on the filter, S10 the `pendingHeaders` decrement mutant, S11 a stale Javadoc of `readTimeoutMs`, **S12** a test of the candidates' own round trips, **S13** a coalesced settings value can be heard before an earlier header (never pair a settings value with a header).

## Group 8 (audio engine) - cycles 1 to 7, 2026-11-12/13: FAIL, FAIL, PASS, FAIL, FAIL, FAIL, PASS
- Cycle 1: **C1** healthy playback was cut every 10 minutes (anchor-difference bound) - gap-based continuity, in-place rebase every 2^34 frames, 3 h tests. W1 a flac chunk that never reaches the decoder shifted the stream for good - hole recovery. W2 `EngineHost.stop()` not sticky. W3 Wi-Fi lock mode (the low-latency lock is active only with the screen on) - `FULL_HIGH_PERF` up to API 33, `FULL_LOW_LATENCY` from 34, honest text.
- Cycle 2: **W4** only one flac hole was remembered - sorted bounded set (64) with an overflow range. Cycle 3 PASS (S15 hole marks from absurd timestamps never expire - clamped in 8d; S16 two overflow mutants; S17 dangling Javadoc; S18 `holeOverflows` not in the status).
- Cycle 4 (after the owner's trace rounds 8f to 8i): **C1** a flac stream does not survive a source stall below 300 ms (permanent offset or silence) - time guard, `flacGapMs` 3 s. W1 the rules of 8f to 8i were not pinned by mutation-killing tests. W2 stale statements (numbers, "spurious" logic). W3 raw stream ids shown in the move-group dialog - display name only. Cycle 5: **W1** the guard turned a decoder hold into a permanent shift (+24/+48/+85 ms) - exact position from the FLAC frame header (`FlacFrameHeader`), guard only with header positions. W2 wrong server model in docs (flac chunks are stamped by a running clock advanced by the encoded duration). W3 mutation gaps. Cycle 6: W1 longest frame header is 16 bytes, not 14; W2 thresholds pinned by literal values; W3 stale Javadoc. Cycle 7 PASS (S39: mutant `sorted[1]` of the median of five survives).
- Open: S12 (a stuck engine thread can still publish after `abandoned`), S13 (test hooks `debugAdvanceFrameCounts`, `PlaybackTracker.debugShift` in production classes), S16, S18 (harmless), S33 (the move group re-checks the group, not the stream; the client count may be 30 s old), S39. S19 to S28 and S29 to S32, S34 to S38 were taken (baseline at open, poll in flight at session end, stale move-group id, stale "Stopped" notification, write-ahead shown clamped, Hello id without the owner's real id, "and N more" streams, decoder reset at epoch change, mono and 44.1 kHz in the rig, backward stamp jumps, hedge in Javadoc, status prints flac lines only for flac, `engineConfig` seam). **S36 is backlog (L8.5).**
- Known and accepted: the 3 h tests use a perfect simulation; real devices add timestamp jitter; no capture of a real server's FLAC chunks exists; the decoded audio waiting is discarded at a flac hole (a lossy link is much worse than pcm).

## Remaining accepted risks (general review)
Everything the app shows or stores from a server is display text; the untested Android glue (`SnapcastNsd`, `AudioTrackSink`, `MediaCodecFlacDecoder` adapter, services, dialogs) rests on reading and on the owner's device runs; no sync measurement against a reference clock exists; flac behaviour on a real server is inferred from the source of Snapcast 0.35.0 and from one phone.
