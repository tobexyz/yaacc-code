### Warning
- W1 [SnapcastRpc.java:567-583 and 555-559, SnapcastModelUpdater.java:51-55 and 90-93] The answer of a call and the notifications are handed out on different threads without any order between them: `route()` wakes the caller on its own thread, notifications go to the listener executor. `setStatus()` replaces the model without knowing which notifications are already older or newer than the status. A notification that the server sends right after the `Server.GetStatus` answer can therefore be applied to the old model first and then be overwritten by the older status; the model stays wrong until that value changes again. Probe (fake server answers GetStatus with volume 70 and sends `Client.OnVolumeChanged` 74 in the same write; the client does `updater.setStatus(operations.getStatus())` as the Javadoc of the updater suggests): after 3000 rounds the model held the stale 70 in 1732 rounds. The same holds for the status that `Group.SetClients` answers. Fix in this group, because the API decides it: deliver the answer in line order with the notifications (for example a call variant whose result is handed to a callback on the listener executor, so `setStatus` runs between the notifications in wire order), or number the received lines and let `setStatus(status, line)` keep notifications that are newer. Add a test like the probe.
- W2 [SnapcastJson.java:110-116 and 149-153] The pre-scan and the platform parser disagree about where a string starts, so both the depth limit and the token limit can be passed on Android. The scan opens a string at every `"` outside a string. Android's `JSONTokener.readLiteral()` reads an unquoted literal up to one of `{}[]/\:,=;#`, space, tab, form feed or a line end; a quote is not in that set, so `a"` is one literal and no string begins. For the line `[a",` + 100 000 × `[` + `"]` the scan sees one string and passes it with depth 1 (probe: "SCAN PASSES"), while Android would recurse 100 000 levels; `[a",[],[], ... ,b"]` with 300 000 elements passes the scan with one token and is valid for Android. What then remains is the `StackOverflowError` handler (which the design calls the last line of defense, not the guard) and no token limit at all. The JVM tests cannot show it: the test-only `org.json:json` ends a literal at a quote and refuses these lines itself. Not run on Android (no runtime in the sandbox); derived from the AOSP source of `org.json`. Fix: make the scan strict about quotes (a `"` outside a string is accepted only directly after `{`, `[`, `,` or `:`, whitespace aside; otherwise MALFORMED), or refuse unquoted literals other than numbers, `true`, `false`, `null`. Add scan-level tests with the two lines above (`SnapcastJson.scan` is pure, so the JVM can test it). `de.yaacc.yxc.YxcJson.bracketDepth` has the same gap (older code, not part of this group).
- W3 [SnapcastRpc.java:555-559 and 745-765, SnapcastLimits.java:50] Design, "Security rules": "unknown notifications are ignored, not queued". Every notification is queued with its whole `params`, whatever the method, and the queue is bounded by count only (256), not by size. ### Suggestion
- [`SnapcastEndpoint.parseIpv4`] `010.0.0.1` is read as decimal 10.0.0.1, while `inet_aton` and many tools read it as octal 8.0.0.1. Harmless inside YAACC (the canonical text is what is used and shown), but a user who types octal gets another host. Refuse a part with a leading zero (and `0` alone stays valid) and add the probe to the test.
- [`SnapcastSession.scheduleTick` / `onConnected`] A narrow race: the tick sees `!online`, the link reconnects and `startTick` finds `tickRunning == true`, then the tick sets it false and ends. The connection is then up without a tick, and a held-back re-read is not delivered until the next connect. Re-check `online` after clearing `tickRunning` (and reschedule if it is true again).
- [`SnapcastReceivers.pageStarted/retain/wake`] The directory snapshot is taken before the lock is taken; a server that leaves in between still gets a link until the next reconcile (`onServersChanged` of the other thread may already have run). Take the snapshot inside the lock (the directory has its own lock and never calls back under it) or reconcile once more after `work.run()`.
- [`SnapcastDirectory.serviceFound`] When 32 service names are known, a known but lost server that is announced under a new name is reported as listed but is not revived (its grace runs on). Revive `lostAt` in that branch too. Also: another host that announces the same service name with another address takes the name from the real server, which then goes into its grace; mDNS name uniqueness is the real defence, a line in the Javadoc is enough.
- [`SnapcastNsd.stop`] `stopServiceDiscovery` right after `discoverServices` (a page that is shown and hidden within a moment) may answer `onStopDiscoveryFailed` on some releases and leave the browse running; the log line is at debug level only. Retry the stop once from `onDiscoveryStarted` when `started` is false. Also `queue.done(name)` of an old resolve can clear the active mark of a new queue with the same name after a quick stop/start; guard with the generation.
- [`SnapcastDisplayText.of` / `SnapcastJson.displayText`] The cut at `max` can split a surrogate pair and leave a lone surrogate in a row name (shown as a replacement glyph). Cut before a high surrogate at the end.
- [`SnapcastReceivers.groups()`] With 16 servers of up to 64 groups the method builds up to 1024 `Device`s per call before it cuts to 64; `getDevicesProvidingAvTransportService()` is called on the main thread by polls. Cheap now, but a cache of the sorted list per status version (which also solves W3) would remove the work.
- [`ReceiverLiveUpdates.watched`] The watched list is cut at 64 receivers; 64 groups listed first by name can push registry devices out of the live feed. Only matters with a very large setup.
- [`SnapcastSessionTest.sessionThreadsAlive`] It scans all threads of the JVM for the prefix `snapcast-session-`; any other test that leaves a real session open would make it flaky. All sessions of the suite are closed today. Match the threads of this test's session (a thread-name suffix or a baseline set taken in `setUp`).
