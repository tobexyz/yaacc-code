### Warning
- W1 [SnapcastRpc.java:567-583 and 555-559, SnapcastModelUpdater.java:51-55 and 90-93] The answer of a call and the notifications are handed out on different threads without any order between them: `route()` wakes the caller on its own thread, notifications go to the listener executor. `setStatus()` replaces the model without knowing which notifications are already older or newer than the status. A notification that the server sends right after the `Server.GetStatus` answer can therefore be applied to the old model first and then be overwritten by the older status; the model stays wrong until that value changes again. Probe (fake server answers GetStatus with volume 70 and sends `Client.OnVolumeChanged` 74 in the same write; the client does `updater.setStatus(operations.getStatus())` as the Javadoc of the updater suggests): after 3000 rounds the model held the stale 70 in 1732 rounds. The same holds for the status that `Group.SetClients` answers. Fix in this group, because the API decides it: deliver the answer in line order with the notifications (for example a call variant whose result is handed to a callback on the listener executor, so `setStatus` runs between the notifications in wire order), or number the received lines and let `setStatus(status, line)` keep notifications that are newer. Add a test like the probe.
- W2 [SnapcastJson.java:110-116 and 149-153] The pre-scan and the platform parser disagree about where a string starts, so both the depth limit and the token limit can be passed on Android. The scan opens a string at every `"` outside a string. Android's `JSONTokener.readLiteral()` reads an unquoted literal up to one of `{}[]/\:,=;#`, space, tab, form feed or a line end; a quote is not in that set, so `a"` is one literal and no string begins. For the line `[a",` + 100 000 × `[` + `"]` the scan sees one string and passes it with depth 1 (probe: "SCAN PASSES"), while Android would recurse 100 000 levels; `[a",[],[], ... ,b"]` with 300 000 elements passes the scan with one token and is valid for Android. What then remains is the `StackOverflowError` handler (which the design calls the last line of defense, not the guard) and no token limit at all. The JVM tests cannot show it: the test-only `org.json:json` ends a literal at a quote and refuses these lines itself. Not run on Android (no runtime in the sandbox); derived from the AOSP source of `org.json`. Fix: make the scan strict about quotes (a `"` outside a string is accepted only directly after `{`, `[`, `,` or `:`, whitespace aside; otherwise MALFORMED), or refuse unquoted literals other than numbers, `true`, `false`, `null`. Add scan-level tests with the two lines above (`SnapcastJson.scan` is pure, so the JVM can test it). `de.yaacc.yxc.YxcJson.bracketDepth` has the same gap (older code, not part of this group).
- W3 [SnapcastRpc.java:555-559 and 745-765, SnapcastLimits.java:50] Design, "Security rules": "unknown notifications are ignored, not queued". Every notification is queued with its whole `params`, whatever the method, and the queue is bounded by count only (256), not by size.
