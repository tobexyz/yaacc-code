## Group 1 (rig, spike, design) - cycles 1, 2, 2026-11-10: FAIL, PASS
- W1 the rig built third-party code from a mutable git tag with the integrity check off - pinned by commit hash and image tag. W2 "unauthenticated, acceptable because loopback only" was incomplete and unverified (the HTTP/WebSocket listener is reachable from a browser page) - the rig disables it, ports published on 127.0.0.1 only. W3 the control client design could not meet "no exception escapes on malformed JSON" - design rules added (byte-level cap, depth and token pre-scan, `StackOverflowError`/`OutOfMemoryError` boundary, bounded batches). W4 the design did not say which host and port the feeder may connect to - control peer only, own port range, marker, percent-encoding.
- Suggestions: spike hardening (cleaned server strings, a host guard, bounded reads), base image digest, tmpfs options and a healthcheck note for the rig, "`adb reverse --remove-all` afterwards", a threat-model paragraph (done in Group 6 docs), no raw `Server.GetStatus` persisted. Open and harmless: a few spike strings still unfiltered, no overall deadline for a dripping server in the spike.

## Group 2 (control library) - cycles 1, 2, 2026-11-10: FAIL, PASS
- W1 server text reached `getMessage()`, `getData()`, `describe()` unfiltered - title printable ASCII up to 64, data cleaned.
- Open: **S1** the byte budget counts line bytes, not the parsed tree; **S2** no rate budget for valid lines (a LAN host can keep the reader busy); S3 taken (`Config` limits positive; S13 the second half, clamping each limit to its constant, is not done); **S4** a host name is resolved without our timeout on the reader thread (Group 3 resolves itself); **S5** a reader of a replaced connection can route one answer late; **S6** `setGroupVolume` up to 256 sequential calls (bounded since by the 5 s gesture budget); **S7** `internal(Throwable)` keeps the cause; **S8** raw `JSONObject` handed out untruncated to listeners; **S9** `addStream` accepts any scheme (Javadoc says callers build only tcp; the server restricts `process://` to its sandbox directory); **S10** tests parse with the reference `org.json`, not Android's; S11 taken in Group 4 (read the peer address and connect in one step, never log it); S12 a flaky test; S14, S15 (display filter classes, done in Group 5/11D), S16 Javadoc order.

## Group 7 (binary protocol) - cycles 1, 2, 2026-11-11: FAIL, PASS
- W1 a flood of tiny frames (bypassed by one unsolicited Time frame) pinned the reader at 100 percent of a core - a frame budget of 2000 per second of the injected clock, the unsolicited Time answer counts as unexpected, Hello/ClientInfo frames skipped by size.
- S56 taken (header-level caps, one copy less), S57 taken (writer thread with a bounded queue), S58 taken in Group 8 (identical header ignored, decoder restart limit, no `AudioTrack` re-creation on an epoch change), S59 taken in Group 8 (buffers sized from the validated format only), S60 taken (`forAddress` refuses wildcard and multicast), **S61 superseded** by the owner's decision of 2026-11-15 (one client id for all servers; the old advice was a per-server id and generic strings), S62 taken (`fromNanoSource(elapsedRealtimeNanos)`), S63, S64 taken (writer publication, `Throwable` boundary). **Open: S65** (a fixed window allows 4000 frames at a window edge, a cap on unsolicited Time answers in total was not taken).

## Group 8 (audio engine, service) - cycles 1 to 4, 2026-11-12/13: FAIL, FAIL, PASS, PASS
- Cycle 1: W1 a hostile FLAC chunk could pin the engine thread with no bound, and it kept working after Stop - `CodecDrain`, rounds of 50 ms, byte-bounded host queue (16 MiB), decoder closed on exit. W2 a main-thread flood of notification rebuilds per ServerSettings message - `NotificationPolicy`. W3 wake and Wi-Fi lock held for the whole session - `SessionPowerPolicy` (60 s grace, 15 minutes without audio ends the session). Cycle 2: W4 an event dropped at every 256th position of a round left phantom bytes in the 16 MiB cap - every polled event is run, bytes come off when polled, queue discarded on exit. W5 the codec was re-created for every over-limit chunk without a limit - 12 decoder failures per minute end the engine.
- Taken: S15 (hole marks clamped and ignored while unsynchronised), S16 (a refused chunk does not use the reserved queue room), S17 (only 5 s of audio in a row re-arms the grace), S18 (the public-address decision uses the resolved address), S19 (watchdog in `SafeRun`), S20 (a rejected Start leaves the notification alone), S25 (locks released before the ending is recorded), the `ACTION_START` enabled re-check.
- **Open (backlog B8.x): S21** `EngineHost.abandon()` keeps the queue until the thread leaves; **S22** `offeredAny`/`lastOfferedMicros` not reset by a new header or a lost connection; **S23** audio of 5 s or more every minute keeps session and locks for ever (accepted, documented); **S24** ServerSettings are not coalesced in the host; the connect worker catches `IOException`/`RuntimeException` but not `Error` (B8.5); **S26** the confirmation of the move-group dialog shows a client count that can be 30 s old and the move re-checks only the group id; **S27** the report is formatted on the UI thread under the trace monitor; **S28** the clipboard report contains server stream names and the start of a group id (a note under the button); **S29** a server can fill the 100-entry important ring (see L8.5). Native FLAC decoding stays the residual risk. Known limits accepted: gain ramp, audio focus, noisy-headphones pause.

## Remaining accepted risks (summary)
Plain TCP, no login, announcements are the whole trust; any LAN host can inject audio into YAACC's tcp stream port while it exists, feed audio is sent to whoever answers at the chosen address (also a public one for a typed host name); the stream name discloses the phone name; the same client id on all servers lets servers and controllers recognise the phone; any device that reaches the renderer in group mode can change the group's volume and mute; the native FLAC decoder parses server bytes; the group may stay on YAACC's idle stream after a lost connection or a removed server; remembered servers are contacted with discovery off; the sheet redraw rate (S44).
