### Warning
- [W1: `tools/snapcast-rig/Dockerfile:17-19,44-48`, `docker-compose.yml:29-35`, `README.md:35-37`] The only third-party code that is compiled and run is fetched by a mutable git tag, and the integrity check is off by default and cannot be reached through the documented flow. `SNAPCAST_COMMIT` defaults to empty (check skipped), `docker-compose.yml` passes only `SNAPCAST_REF` as a build arg, and the README says to add `--build-arg SNAPCAST_COMMIT=...` while starting with `docker compose up --build` (`up` has no `--build-arg`; only `docker compose build --build-arg` does, and an arg that the compose file does not list is not passed by `up`). A moved or hijacked tag would therefore be built and run without any check. Also not verified: the clone is shallow without `--recurse-submodules`, and whether the CMake configure step downloads further sources (submodules or FetchContent) is unknown; the commit pin would not cover those. Remediation: (1) add `SNAPCAST_COMMIT: ${SNAPCAST_COMMIT:-}` (and `BUILD_JOBS`) to `build.args` in the compose file; (2) make the build fail when `SNAPCAST_COMMIT` is empty, or default it to the full hash the owner records at the first build (the existing "pin after the first rig build" note in `docs/tech.md:3628` becomes a hard rule); (3) README: show how to get the hash (`git ls-remote https://github.com/snapcast/snapcast 'v0.35.0^{}'`, use the peeled `^{}` line for an annotated tag) and use `docker compose build` for the arg; (4) record at the first build whether anything else is fetched during configure, and pin or vendor that too.
- [W2: `tools/snapcast-rig/snapserver.conf:22-27`, `docker-compose.yml:49-50`, `decisions.md:14`, `docs/tech.md:3594`] "Unauthenticated, acceptable because loopback only" is incomplete, and the claim that makes it safe is unverified. Loopback is reachable by every local process and, for a text protocol, by any web page open in the developer's browser: a WebSocket to `ws://127.0.0.1:1780` is not subject to CORS, and a form POST with a `text/plain` body to `http://127.0.0.1:1780/jsonrpc` (or, cross-protocol, to the line-based port 1705, whose body line is a valid JSON-RPC request) can issue control calls blind. Not tested here (no Docker), but it is the well-known cross-protocol pattern. The HTTP/WebSocket listener on 1780 is not used by anything in the design or the tests (control is the raw TCP socket, `design.md:25`), so it is attack surface for no benefit. Impact is bounded by the container hardening, but `docs/tech.md:3594` says no scheme check on `Stream.AddStream` was found in the sources and marks it "rig", while `decisions.md:14` states "accepts only pipe, file, tcp, alsa, jack, meta (security restriction)" as fact. If a `process://` source is accepted, an unauthenticated request means command execution in the container (which has outbound network). Remediation: (1) set `[http] enabled = false` and do not publish 1780 by default (a commented override or a second compose file for the day a test needs HTTP); (2) README and `snapserver.conf`: add one sentence that loopback does not protect against local processes and web pages, so stop the rig when not testing; (3) add a rig check to the README ("`Stream.AddStream` with a `process://` URI must be refused; if it is accepted, record it in `docs/tech.md` and keep the rig down when idle"); (4) reword `decisions.md:14` to "documented as accepting only ...; the code check is not confirmed (see docs/tech.md)".
- [W3: `design.md:28`, `design.md:27` (re-read on doubt), `tasks.md` 2.1/2.2] The control-client design cannot meet "no exception escapes on malformed JSON" with the planned parser, and the limits are incomplete. Models are parsed with the platform `org.json`, which has no nesting limit; a line of about 1 MiB of `[` (within the planned 1 MiB cap) overflows the stack, and `StackOverflowError` is an `Error`, so a catch of `Exception`/`JSONException` does not stop it and the worker thread or the app dies. Any host the app talks to can send it, including a rogue mDNS responder on the LAN. The spike's own parser caps depth at 64, but it is not what production uses. Further gaps, all reachable by a hostile server: the 1 MiB cap is only a line cap (a `BufferedReader.readLine()` buffers the whole line before any cap can act, and a dripping sender defeats a per-read timeout); "after any doubt re-read the full status" lets a server loop the client by sending unknown notifications, each answered by a request for up to 1 MiB (amplification, battery drain); reconnect has backoff but no ceiling or stop rule; no bounds on batch size, number of groups/clients/streams, string length or numeric ranges. Remediation (add to `design.md` as a "Security requirements" subsection and to the Constraints of tasks 2.1/2.2): (1) byte-level line reader with a hard cap (1 MiB) and an overall deadline per call; (2) depth pre-scan (string and escape aware, reject above 32 levels) before `org.json`, and catch `StackOverflowError`/`OutOfMemoryError` at the worker boundary as a typed "bad server" error that closes the connection; (3) caps: batch array size, groups/clients/streams count, name length (strip control characters), volume 0-100, latency to a sane range; (4) at most one forced re-read per few seconds, coalesced; unknown notifications are logged once, not acted on repeatedly; (5) reconnect: capped backoff, stop while the page is hidden, give up after N failures until the user retries; (6) bounded pending map, request ids never taken from the server; (7) Group 2 tests with hostile fixtures built in the test (deep nesting, oversize line without newline, dripping reader, control characters in names, wrong types, out-of-range numbers, flood of notifications).
- [W4: `design.md:32-34`, `design.md:63`, `design.md:65`, `tasks.md` 3.1/4.2/4.3] The design does not say which host and port the feeder may connect to, and several steps take input from the network. Step 1 derives the free port "from the existing streams' URIs" (server-supplied) and the stream URI binds `0.0.0.0`; the server reports `uri.host` as `0.0.0.0:4953`. If the connect target is ever read from a server reply or status (or discovery data), a hostile or spoofed server can steer the user's audio, and the phone's connection attempts, to arbitrary LAN or loopback endpoints (SSRF-like; the audio goes to whoever answered). mDNS has no authentication and no TXT records (`docs/tech.md:3585`), so any LAN host can advertise `_snapcast-ctrl._tcp` with any host and port, and a spoofed entry can look like "Living room". Adoption of an existing stream by name alone, and crash cleanup "by name prefix + marker" (`design.md:70`) with a guessable marker, are also exploitable by a foreign stream or by another YAACC phone with the same device name. Remediation (add to design.md and the tasks): (1) the feed host is the peer `InetAddress` of the established control connection (keep the object, do not re-resolve a name, do not rebuild it from a string); (2) the feed port is the one YAACC requested; if the echoed or observed port differs, fail; never use `uri.host` or any server-supplied host as a connect target; `0.0.0.0` is a bind address, never a connect target; ports parsed strictly and range-checked; (3) adopt an existing `YAACC ...` stream only if scheme is `tcp`, mode `server` and the format matches, otherwise use a new name or report an error; (4) the stream name carries a random per-install marker (for example `YAACC <name> [6 hex chars]`), and removal or crash cleanup only touches ids YAACC itself recorded (the persisted list in `design.md:83`), never "everything with the prefix"; before restoring a group's previous stream, check that the group is still on YAACC's stream; (5) discovered endpoints: accept only unicast addresses of the phone's local network (site-local, link-local, ULA, plus loopback and 10.0.2.2 for the emulator), nonzero port, cap the number of discovered servers, connect lazily (not to every advertised service), and never feed to or auto-resume on a server the user has not picked in this session; manual entries may be anything; (6) strict validation of manual `host[:port]` (no scheme, userinfo, path or whitespace; IPv6 only in brackets; keep `InetAddress` for link-local IPv6 with scope instead of string concatenation); (7) names and ids from the server are untrusted display text: never identity (the server key is the endpoint only, never merged on `host.name`/`mac`), never rendered as HTML, length-capped, control characters removed.

### Suggestion
- [FeedSpike.java:525-537,342] Server-supplied strings (group, client and stream names, ids, error `data`) are printed to the terminal unfiltered; the JSON reader decodes `\u001b`, so a hostile server can inject terminal escape sequences (spoofed `RESULT: OK`, title changes). Replace characters below 0x20 and 0x7f in everything printed. The same rule applies to production logging.
- [FeedSpike.java:616,612-645] `readLine()` is unbounded, and the 10 s deadline is only checked after a line has arrived, so a server that sends a never-ending line or one byte every 9 s exhausts memory or hangs the run (Ctrl-C then leaves the stream behind after the 10 s join in the shutdown hook). Documented as a spike limit in the header; either read bounded or add "point only at your own rig" to the README. Production requirements are in W3.
- [FeedSpike.java:330-337,412] The stream id from the AddStream reply is used unchecked for `Group.SetStream` and `Stream.RemoveStream`. The id of a stream named `YAACC spike` is that name, so accept the reply only if it equals `STREAM_NAME`, otherwise a deviating server can make cleanup remove another stream. Production must build its own ids and compare (W4 item 4).
- [FeedSpike.java:97-133,359-384] On any host the spike moves every group with a connected client to a 440 Hz tone at about -10 dBFS for up to 86400 s. Pointed at a real home snapserver (no authentication) it takes over every room. Add a guard: refuse a host that is not loopback, `10.0.2.2` or a private address unless `--allow-remote` is given, and cap the duration (for example 1 h).
- [FeedSpike.java:234-259,449-495] `out.write` has no timeout and the monitor loop ends only when the feeder ends, so a server that accepts the connection and stops reading keeps the run alive until Ctrl-C. End the loop at `seconds` plus a grace period and close the feed socket. For the production feeder (task 4.2): a write watchdog that closes the socket after a bounded stall, a bounded queue, and a typed "stalled" state.
- [Dockerfile:12,27-42,75-85] Pin the base image by digest as well (`debian:12.12-slim@sha256:...`, recorded at the first build). Debian packages follow the 12.x security updates, which is acceptable for a local rig; say so in the README. Add a `.dockerignore` (the build context is the rig directory; nothing in it is needed by the build). Optional: run `hadolint`/`docker build --check` and `trivy image` once on the built image and note the result.
- [docker-compose.yml:40-42] State the tmpfs options explicitly (`noexec,nosuid,nodev`) instead of relying on the daemon defaults. Note that the snapclient services have no healthcheck and restart on failure without a limit (harmless on a rig).
- [README.md:172-184] `adb reverse` makes the rig reachable from every app on the connected phone while it is active; add "run `adb reverse --remove-all` afterwards".
- [design.md:63-65, docs/tech.md] Document the residual risk of the feed: the tcp source listens on `0.0.0.0` of the server host without authentication and accepts one producer at a time, so any LAN host can inject audio or occupy the producer slot while the stream exists; keep the stream short-lived, remove it at the end of playback, and use a randomized port from the configured range. Binding to the peer address is not an option on NAT setups such as the rig.
- [design.md:32] Multicast lock and discovery (Group 3): acquire and release in `try/finally`, reference counted, released on every pause/destroy path; stop NSD discovery and cancel pending resolves when the page is hidden; resolve one service at a time; ignore the phone's own addresses and multicast or unspecified results.
- [design.md, docs/tech.md] Add a short threat-model paragraph (Group 6 docs, README): Snapcast is unauthenticated and unencrypted by default, YAACC assumes a trusted LAN, stores no credentials, and refuses the things listed in W3/W4. `Server.GetStatus` contains MACs, IPs and host names of other devices: do not log response bodies at default levels, do not persist raw status, keep them out of crash reports.
- [yaacc/src/test/resources/snapcast/README.md] When the derived fixtures are replaced by real captures, capture only from the rig and rerun the IPv4/MAC grep before committing (a capture from a real home server contains real MACs, IPs and host names). Add the hostile cases from W3 as generated test inputs, not as files, to keep the fixture folder clean.
- [design.md:63, stream URI building] When Group 4 builds the stream URI from the phone's device name, percent-encode every reserved character (`& = ? # % /` and non-ASCII), cap the length, and unit-test names such as `a&mode=client&b=c` and `x#y`; the spike encodes only a constant. A name with `&` otherwise injects URI parameters into the source definition (the server only accepts `controlscript` inside its plug-in directory, but the injected `mode`, `sampleformat` or `codec` would break the feed).

### Rule by rule (enforced in production code and tested)
- 1 MiB byte-level line cap: `SnapcastLineReader.append:91-106` checks before copying, `SnapcastLimits.MAX_LINE_BYTES`; tests `aLongerLineIsRefusedWithoutReadingAllOfIt`, `lineOf2MiBWithNewlineIsRefused`, `aLineOverOneMiBDropsTheConnectionAndFailsPendingCalls`, exact-cap case. No int overflow (`lineLength <= 1 MiB`, `count <= 8192`).
- Per-call deadline + read timeout + line deadline: `SnapcastRpc.execute:872-917`, `setSoTimeout` in `runSession:662`, `SnapcastLineReader.readLine:85` and `fill:113-117`. Tests `aDrippingSenderHitsTheCallDeadlineAndTheLineDeadline`, `aSenderThatStallsInTheMiddleOfALineLosesTheConnection`, `aSlowLineHitsTheDeadlineOnAFakeClock`. A write that never returns ends at the deadline and closes the socket (`aWriteThatNeverReturnsEndsAtTheDeadlineAndDropsTheConnection`, `aServerThatStopsReadingCostsTheConnectionNotTheCallers`); at most 32 queued writes of at most 256 KiB because the first timeout closes the connection.
- Depth pre-scan (32), token cap (10 000), no lenient forms: `SnapcastJson.scan:94-177`. The quote rule (a quote opens a string only after `{ [ , :`) matches Android's `nextValue` start positions; `\u` desync cannot hide a structural character (the four hex digits cannot be `" { } [ ] , :`; a bad escape throws and is caught as `RuntimeException`); BOM, comments, `'`, `=`, `;`, `#`, data after the value are refused; the `StackOverflowError` catch stays as the backstop. Numbers: Android returns `Double` for huge literals, `clamp` handles NaN/Infinity/BigInteger without `intValue()`.
- Throwable backstop at the worker boundary: `runSession:669-671` (also `StackOverflowError`, `OutOfMemoryError`), `PendingCall.runHandler:389`, `write:956`, `deliverAll` (listener faults swallowed); tests for SOE, OOM and RuntimeException.
- Caps: batch 64 (`SnapcastMessage.parseLine:84-89`), groups 64 / clients 256 per group / streams 64 / query entries 32 (`SnapcastServerStatus`, `SnapcastGroup`, `SnapcastStream`, also in the public constructors), strings 1 KiB with surrogate-safe cut (`SnapcastJson.truncate`), volume 0..100, latency 0..10 000, port 1..65535, protocol versions, error code. Unique group, client and stream ids (a client id is found in one place only). All covered in `SnapcastHostileInputTest` and `SnapcastModelTest`.
- Notification queue: count 256 and bytes 4 MiB, one always accepted into an empty queue, unknown methods never queued (only `lost`), `Stream.OnProperties` params dropped at the reader, drops reported once through `onNotificationsLost`; tests `aFloodOfNotificationsDoesNotGrowTheQueueAndTellsThatSomeWereLost`, `largeKnownNotificationsAreBoundedByBytesNotOnlyByCount`, `largeNotificationsOfUnknownMethodsAreDroppedAtTheReader`. ### Attack scenarios walked
- *LAN host advertises many `_snapcast-ctrl._tcp` services*: bounded at the queue (32), the name table (32) and the directory (16); no thread or memory growth; each resolution has a 10 s ceiling. Control characters, bidi and huge names are cleaned and cut (64) or refused (> 256). Services at public IPs are refused; the phone's own loopback is allowed by the rule (see S18); `fe80::` with a zone id keeps its scope, the zone is not in the key. TXT records are never read.
- *Spoofed server with a hostile status*: groups capped at 64 per server and 64 in all (`groups()` stops building), group ids filtered, names cleaned, 256 members per group; ids that collide with another server's key or contain separators produce no device; status updates are coalesced to one UI refresh per 300 ms.
- *Hostile preference* (`snapcast_manual_servers`, `snapcast_selected_servers`, the receiver selection set): every line is re-parsed strictly, filtered again (selected servers), capped at 16; a forged `snapcast:` id for an unlisted server opens nothing and is dropped.
- *DNS-rebinding style manual host name*: allowed by design (the user typed it); a name is re-resolved on every attempt on a helper thread, the connection goes to the resolved address, the only payload is the fixed JSON-RPC read (see S24).
- *Connection storms*: page start / `wake` retry only links that are down, at most one attempt at a time per server, no loop; hostile servers that accept and drop are handled by the Group 2 ceiling.
- *Leaks*: NsdManager listener per browse with handle and generation, stop is held until the start is confirmed; the lock is released on every exit; all executors and the socket are closed in `SnapcastSession.close`; `SnapcastHub` holds only the application context.

### Suggestion
- [S17: `SnapcastDirectory.serviceFound:173-216`, `SnapcastResolveQueue`, `SnapcastNsd.onServiceFound`] Availability under an mDNS flood or name spoofing. A LAN host that announces 16 servers, or 32 names, fills the directory/name table/queue so that a legitimate server with a new name is refused (`listed = false`) until the fake ones have been lost; a host that announces the legitimate instance name moves that name to its own endpoint, the real entry becomes lost and expires after 30 s (taking an un-remembered selected group with it). Memory, threads and sockets stay bounded, nothing leaks, and a typed-in server is the fallback and can never be evicted by discovery. Say so in the README (Group 6) and let the Group 5 UI show "server not found" instead of a silent gap.
- [S18: `SnapcastDirectory.serviceFound`, `SnapcastNsd.onServiceResolved`] The port of a discovered service is taken as announced (1..65535). A LAN host (or an app on the phone, since NSD registration needs no permission) can therefore make the phone open a TCP connection to any private/loopback `host:port` and send the fixed JSON-RPC read (`Server.GetStatus` and the like; no attacker-controlled bytes, no credentials) while the receivers page is visible. That is a blind probe, not a data leak, and the same applies to the UPnP stack; accepted. If a rule is wanted: refuse a discovered port below 1024. Write calls (Group 4: `Stream.AddStream`, the feed) must stay limited to the server the user picked.
- [S19: `SnapcastHub.pageStarted:107-117`, `ReceiverListFragment.onResume:75-85`] Discovery, the multicast lock and connections to every announced private server now start for every user who opens the receivers tab, with no opt-in and no switch (the "enable discovery" setting is task 5.2). It must land in the same release as Group 3 (or the hub must default to "manual servers only"), because a user without a snapserver otherwise opens control connections to whatever announces `_snapcast-ctrl._tcp` on a shared Wi-Fi.
- [S20: Group 4/5 hand-off, `SnapcastGroupDevice.nameOf`] Names are cleaned but not unique and not tied to a server: a hostile server can name its group like a legitimate one, the row shows only the name, and Group 4 will send the user's audio (and Group 5 volume changes) to the server behind the chosen row. Group 5 should show the server (endpoint) in the row or sheet and mark two groups with the same name as different. S15 of cycle 2 (zero-width and other format characters are not replaced) makes identical-looking names easier; replacing `Character.getType` CONTROL/FORMAT/unpaired SURROGATE in `displayText` closes it.
- [S21: `ReceiverRowBinder.java:263-266`, `BrowseReceiverDeviceClickListener.java:51,56`] These debug lines log `device.getDisplayString()`. For a Snapcast group that is server-supplied text (cleaned, 64 chars), and `nameOf` falls back to the first member's host name when the group has no name, which the design says is not to be logged. The default log level is ERROR, so it needs the user's debug setting; log nothing for a `SnapcastGroupDevice` (or the class name only).
- [S22: `SnapcastResolver.MAX_HELPERS = 2`, `ResolvingTransport`, `SnapcastReceivers.reconcileLocked`] With three or more manual servers given as host names, a page start opens all links at once; the third and later lookups are refused at once ("name lookup busy") and count as connection failures toward the 5-failure ceiling of Group 2, so such a server can end in GAVE_UP although the network is fine (until the next page start). Reliability, not a vulnerability: queue the lookups behind the two helpers (a bounded wait) or do not count "busy" as a failure.
- [S23: `SnapcastDirectory.setManualServers:295-301`, `SnapcastSelectedServers.selectionChanged:91`] A server that is both in the remembered store (an earlier discovery, a selected group) and added and then removed by hand stays listed as remembered, and is connected to on page start and `wake`, until the selection changes (tested on purpose: `aServerThatLeavesTheManualListStaysWhileItIsRemembered`). It cannot outlive the selection that refers to it, and any edit of the selection drops it, but a "remove server" in the Group 5 settings should also clear the remembered flag and the store entry of that server so that "removed" means removed.
- [S24: `SnapcastResolver.resolve`, `ResolvingTransport`] A manual host name is not range-checked after resolution (the user chose the name, so the rule for discovered servers does not apply): whoever controls that DNS name can point the phone at any host:port, again with only the fixed JSON-RPC read as payload. Accepted. If wanted, Group 5 can show a one-time hint when a typed name resolves outside the local ranges.
- [S25: Group 4 hand-off] The receiver id `snapcast:<key>:<gid>` contains `:` and, for IPv6, brackets. Downstream code that builds `/proxy/<deviceId>/<key>`, the preference key `manage_external_seeking_<deviceId>`, or leases from a device id (`RendererIdPolicy` accepts `:` but not `[`/`]`) is safe today only because of the three `isNotPlayableYet` guards. When Group 4 replaces them it should key players, leases and preferences by an opaque handle (not the receiver id), and must not let a Snapcast id into `ShareService`/`QueueShareBinder`. `SnapcastSession.getPeerAddress` must not be logged (S11 of cycle 1).
- [S26: tests] `SnapcastNsd` has no test (it cannot run on the JVM); the order of calls (lock after the service check, release on failure, stop held until `onDiscoveryStarted`) rests on this review and on the pure `SnapcastBrowseHandleTest`. Cover it on the device with the receivers page opened and closed quickly several times and `adb shell dumpsys wifi | grep -i multicast` (no lock held after the page is hidden). `SnapcastAddressFilter` has no test of its own (it lives in `SnapcastEndpointTest`) and none for an IPv4-mapped address such as `::ffff:8.8.8.8`; add the case so a future change of the folding is noticed.

### Verdict: PASS
No Critical and no Warning. Every rule of "Discovery and servers" in `design.md` and of the Group 3 security constraints in `tasks.md` is enforced in production code and has a test that fails without it (address ranges, 16-server cap, lazy connect, strict manual validation, no stored credentials, display-only names, no logging of addresses, bounded DNS); the only item that rests on the device is the NSD/multicast-lock sequencing (S26). S17 to S26 do not block; S19 (opt-in/switch for discovery before a release) and S20 (show the server behind a group) are the ones to take with Group 5.
