### Warning
- [W1: `tools/snapcast-rig/Dockerfile:17-19,44-48`, `docker-compose.yml:29-35`, `README.md:35-37`] The only third-party code that is compiled and run is fetched by a mutable git tag, and the integrity check is off by default and cannot be reached through the documented flow. `SNAPCAST_COMMIT` defaults to empty (check skipped), `docker-compose.yml` passes only `SNAPCAST_REF` as a build arg, and the README says to add `--build-arg SNAPCAST_COMMIT=...` while starting with `docker compose up --build` (`up` has no `--build-arg`; only `docker compose build --build-arg` does, and an arg that the compose file does not list is not passed by `up`). A moved or hijacked tag would therefore be built and run without any check. Also not verified: the clone is shallow without `--recurse-submodules`, and whether the CMake configure step downloads further sources (submodules or FetchContent) is unknown; the commit pin would not cover those. Remediation: (1) add `SNAPCAST_COMMIT: ${SNAPCAST_COMMIT:-}` (and `BUILD_JOBS`) to `build.args` in the compose file; (2) make the build fail when `SNAPCAST_COMMIT` is empty, or default it to the full hash the owner records at the first build (the existing "pin after the first rig build" note in `docs/tech.md:3628` becomes a hard rule); (3) README: show how to get the hash (`git ls-remote https://github.com/snapcast/snapcast 'v0.35.0^{}'`, use the peeled `^{}` line for an annotated tag) and use `docker compose build` for the arg; (4) record at the first build whether anything else is fetched during configure, and pin or vendor that too.
- [W2: `tools/snapcast-rig/snapserver.conf:22-27`, `docker-compose.yml:49-50`, `decisions.md:14`, `docs/tech.md:3594`] "Unauthenticated, acceptable because loopback only" is incomplete, and the claim that makes it safe is unverified. Loopback is reachable by every local process and, for a text protocol, by any web page open in the developer's browser: a WebSocket to `ws://127.0.0.1:1780` is not subject to CORS, and a form POST with a `text/plain` body to `http://127.0.0.1:1780/jsonrpc` (or, cross-protocol, to the line-based port 1705, whose body line is a valid JSON-RPC request) can issue control calls blind. Not tested here (no Docker), but it is the well-known cross-protocol pattern. The HTTP/WebSocket listener on 1780 is not used by anything in the design or the tests (control is the raw TCP socket, `design.md:25`), so it is attack surface for no benefit. Impact is bounded by the container hardening, but `docs/tech.md:3594` says no scheme check on `Stream.AddStream` was found in the sources and marks it "rig", while `decisions.md:14` states "accepts only pipe, file, tcp, alsa, jack, meta (security restriction)" as fact. If a `process://` source is accepted, an unauthenticated request means command execution in the container (which has outbound network). Remediation: (1) set `[http] enabled = false` and do not publish 1780 by default (a commented override or a second compose file for the day a test needs HTTP); (2) README and `snapserver.conf`: add one sentence that loopback does not protect against local processes and web pages, so stop the rig when not testing; (3) add a rig check to the README ("`Stream.AddStream` with a `process://` URI must be refused; if it is accepted, record it in `docs/tech.md` and keep the rig down when idle"); (4) reword `decisions.md:14` to "documented as accepting only ...; the code check is not confirmed (see docs/tech.md)".
- [W3: `design.md:28`, `design.md:27` (re-read on doubt), `tasks.md` 2.1/2.2] The control-client design cannot meet "no exception escapes on malformed JSON" with the planned parser, and the limits are incomplete. Models are parsed with the platform `org.json`, which has no nesting limit; a line of about 1 MiB of `[` (within the planned 1 MiB cap) overflows the stack, and `StackOverflowError` is an `Error`, so a catch of `Exception`/`JSONException` does not stop it and the worker thread or the app dies. Any host the app talks to can send it, including a rogue mDNS responder on the LAN. The spike's own parser caps depth at 64, but it is not what production uses. Further gaps, all reachable by a hostile server: the 1 MiB cap is only a line cap (a `BufferedReader.readLine()` buffers the whole line before any cap can act, and a dripping sender defeats a per-read timeout); "after any doubt re-read the full status" lets a server loop the client by sending unknown notifications, each answered by a request for up to 1 MiB (amplification, battery drain); reconnect has backoff but no ceiling or stop rule; no bounds on batch size, number of groups/clients/streams, string length or numeric ranges. Remediation (add to `design.md` as a "Security requirements" subsection and to the Constraints of tasks 2.1/2.2): (1) byte-level line reader with a hard cap (1 MiB) and an overall deadline per call; (2) depth pre-scan (string and escape aware, reject above 32 levels) before `org.json`, and catch `StackOverflowError`/`OutOfMemoryError` at the worker boundary as a typed "bad server" error that closes the connection; (3) caps: batch array size, groups/clients/streams count, name length (strip control characters), volume 0-100, latency to a sane range; (4) at most one forced re-read per few seconds, coalesced; unknown notifications are logged once, not acted on repeatedly; (5) reconnect: capped backoff, stop while the page is hidden, give up after N failures until the user retries; (6) bounded pending map, request ids never taken from the server; (7) Group 2 tests with hostile fixtures built in the test (deep nesting, oversize line without newline, dripping reader, control characters in names, wrong types, out-of-range numbers, flood of notifications).
- [W4: `design.md:32-34`, `design.md:63`, `design.md:65`, `tasks.md` 3.1/4.2/4.3] The design does not say which host and port the feeder may connect to, and several steps take input from the network. Step 1 derives the free port "from the existing streams' URIs" (server-supplied) and the stream URI binds `0.0.0.0`; the server reports `uri.host` as `0.0.0.0:4953`. If the connect target is ever read from a server reply or status (or discovery data), a hostile or spoofed server can steer the user's audio, and the phone's connection attempts, to arbitrary LAN or loopback endpoints (SSRF-like; the audio goes to whoever answered). mDNS has no authentication and no TXT records (`docs/tech.md:3585`), so any LAN host can advertise `_snapcast-ctrl._tcp` with any host and port, and a spoofed entry can look like "Living room". Adoption of an existing stream by name alone, and crash cleanup "by name prefix + marker" (`design.md:70`) with a guessable marker, are also exploitable by a foreign stream or by another YAACC phone with the same device name. Remediation (add to design.md and the tasks): (1) the feed host is the peer `InetAddress` of the established control connection (keep the object, do not re-resolve a name, do not rebuild it from a string); (2) the feed port is the one YAACC requested; if the echoed or observed port differs, fail; never use `uri.host` or any server-supplied host as a connect target; `0.0.0.0` is a bind address, never a connect target; ports parsed strictly and range-checked; (3) adopt an existing `YAACC ...` stream only if scheme is `tcp`, mode `server` and the format matches, otherwise use a new name or report an error; (4) the stream name carries a random per-install marker (for example `YAACC <name> [6 hex chars]`), and removal or crash cleanup only touches ids YAACC itself recorded (the persisted list in `design.md:83`), never "everything with the prefix"; before restoring a group's previous stream, check that the group is still on YAACC's stream; (5) discovered endpoints: accept only unicast addresses of the phone's local network (site-local, link-local, ULA, plus loopback and 10.0.2.2 for the emulator), nonzero port, cap the number of discovered servers, connect lazily (not to every advertised service), and never feed to or auto-resume on a server the user has not picked in this session; manual entries may be anything; (6) strict validation of manual `host[:port]` (no scheme, userinfo, path or whitespace; IPv6 only in brackets; keep `InetAddress` for link-local IPv6 with scope instead of string concatenation); (7) names and ids from the server are untrusted display text: never identity (the server key is the endpoint only, never merged on `host.name`/`mac`), never rendered as HTML, length-capped, control characters removed.

### Suggestion
- [FeedSpike.java:525-537,342] Server-supplied strings (group, client and stream names, ids, error `data`) are printed to the terminal unfiltered; the JSON reader decodes `\u001b`, so a hostile server can inject terminal escape sequences (spoofed `RESULT: OK`, title changes). Replace characters below 0x20 and 0x7f in everything printed. The same rule applies to production logging.
- [FeedSpike.java:616,612-645] `readLine()` is unbounded, and the 10 s deadline is only checked after a line has arrived, so a server that sends a never-ending line or one byte every 9 s exhausts memory or hangs the run (Ctrl-C then leaves the stream behind after the 10 s join in the shutdown hook). Documented as a spike limit in the header; either read bounded or add "point only at your own rig" to the README. Production requirements are in W3.
- [FeedSpike.java:330-337,412] The stream id from the AddStream reply is used unchecked for `Group.SetStream` and `Stream.RemoveStream`. The id of a stream named `YAACC spike` is that name, so accept the reply only if it equals `STREAM_NAME`, otherwise a deviating server can make cleanup remove another stream. Production must build its own ids and compare (W4 item 4).
- [FeedSpike.java:97-133,359-384] On any host the spike moves every group with a connected client to a 440 Hz tone at about -10 dBFS for up to 86400 s. Pointed at a real home snapserver (no authentication) it takes over every room. Add a guard: refuse a host that is not loopback, `10.0.2.2` or a private address unless `--allow-remote` is given, and cap the duration (for example 1 h).
- [FeedSpike.java:234-259,449-495] `out.write` has no timeout and the monitor loop ends only when the feeder ends, so a server that accepts the connection and stops reading keeps the run alive until Ctrl-C. End the loop at `seconds` plus a grace period and close the feed socket. For the production feeder (task 4.2): a write watchdog that closes the socket after a bounded stall, a bounded queue, and a typed "stalled" state.
- [Dockerfile:12,27-42,75-85] Pin the base image by digest as well (`debian:12.12-slim@sha256:...`, recorded at the first build). Debian packages follow the 12.x security updates, which is acceptable for a local rig; say so in the README. Add a `.dockerignore` (the build context is the rig directory; nothing in it is needed by the build). Optional: run `hadolint`/`docker build --check` and `trivy image` once on the built image and note the result.
- [docker-compose.yml:40-42] State the tmpfs options explicitly (`noexec,nosuid,nodev`) instead of relying on the daemon defaults. Note that the snapclient services have no healthcheck and restart on failure without a limit (harmless on a rig).
- [README.md:172-184] `adb reverse` makes the rig reachable from every app on the connected phone while it is active; add "run `adb reverse --remove-all` afterwards".
- [design.md:63-65, docs/tech.md] Document the residual risk of the feed: the tcp source listens on `0.0.0.0` of the server host without authentication and accepts one producer at a time, so any LAN host can inject audio or occupy the producer slot while the stream exists; keep the stream short-lived, remove it at the end of playback, and use a randomized port from the configured range. Binding to the peer address is not an option on NAT setups such as the rig.
- [design.md:32] Multicast lock and discovery (Group 3): acquire and release in `try/finally`, reference counted, released on every pause/destroy path; stop NSD discovery and cancel pending resolves when the page is hidden; resolve one service at a time; ignore the phone's own addresses and multicast or unspecified results.
- [design.md, docs/tech.md] Add a short threat-model paragraph (Group 6 docs, README): Snapcast is unauthenticated and unencrypted by default, YAACC assumes a trusted LAN, stores no credentials, and refuses the things listed in W3/W4. `Server.GetStatus` contains MACs, IPs and host names of other devices: do not log response bodies at default levels, do not persist raw status, keep them out of crash reports.
- [yaacc/src/test/resources/snapcast/README.md] When the derived fixtures are replaced by real captures, capture only from the rig and rerun the IPv4/MAC grep before committing (a capture from a real home server contains real MACs, IPs and host names). Add the hostile cases from W3 as generated test inputs, not as files, to keep the fixture folder clean.
- [design.md:63, stream URI building] When Group 4 builds the stream URI from the phone's device name, percent-encode every reserved character (`& = ? # % /` and non-ASCII), cap the length, and unit-test names such as `a&mode=client&b=c` and `x#y`; the spike encodes only a constant. A name with `&` otherwise injects URI parameters into the source definition (the server only accepts `controlscript` inside its plug-in directory, but the injected `mode`, `sampleformat` or `codec` would break the feed).

### Rule by rule (enforced in production code and tested)
- 1 MiB byte-level line cap: `SnapcastLineReader.append:91-106` checks before copying, `SnapcastLimits.MAX_LINE_BYTES`; tests `aLongerLineIsRefusedWithoutReadingAllOfIt`, `lineOf2MiBWithNewlineIsRefused`, `aLineOverOneMiBDropsTheConnectionAndFailsPendingCalls`, exact-cap case. No int overflow (`lineLength <= 1 MiB`, `count <= 8192`).
- Per-call deadline + read timeout + line deadline: `SnapcastRpc.execute:872-917`, `setSoTimeout` in `runSession:662`, `SnapcastLineReader.readLine:85` and `fill:113-117`. Tests `aDrippingSenderHitsTheCallDeadlineAndTheLineDeadline`, `aSenderThatStallsInTheMiddleOfALineLosesTheConnection`, `aSlowLineHitsTheDeadlineOnAFakeClock`. A write that never returns ends at the deadline and closes the socket (`aWriteThatNeverReturnsEndsAtTheDeadlineAndDropsTheConnection`, `aServerThatStopsReadingCostsTheConnectionNotTheCallers`); at most 32 queued writes of at most 256 KiB because the first timeout closes the connection.
- Depth pre-scan (32), token cap (10 000), no lenient forms: `SnapcastJson.scan:94-177`. The quote rule (a quote opens a string only after `{ [ , :`) matches Android's `nextValue` start positions; `\u` desync cannot hide a structural character (the four hex digits cannot be `" { } [ ] , :`; a bad escape throws and is caught as `RuntimeException`); BOM, comments, `'`, `=`, `;`, `#`, data after the value are refused; the `StackOverflowError` catch stays as the backstop. Numbers: Android returns `Double` for huge literals, `clamp` handles NaN/Infinity/BigInteger without `intValue()`.
- Throwable backstop at the worker boundary: `runSession:669-671` (also `StackOverflowError`, `OutOfMemoryError`), `PendingCall.runHandler:389`, `write:956`, `deliverAll` (listener faults swallowed); tests for SOE, OOM and RuntimeException.
- Caps: batch 64 (`SnapcastMessage.parseLine:84-89`), groups 64 / clients 256 per group / streams 64 / query entries 32 (`SnapcastServerStatus`, `SnapcastGroup`, `SnapcastStream`, also in the public constructors), strings 1 KiB with surrogate-safe cut (`SnapcastJson.truncate`), volume 0..100, latency 0..10 000, port 1..65535, protocol versions, error code. Unique group, client and stream ids (a client id is found in one place only). All covered in `SnapcastHostileInputTest` and `SnapcastModelTest`.
- Notification queue: count 256 and bytes 4 MiB, one always accepted into an empty queue, unknown methods never queued (only `lost`), `Stream.OnProperties` params dropped at the reader, drops reported once through `onNotificationsLost`; tests `aFloodOfNotificationsDoesNotGrowTheQueueAndTellsThatSomeWereLost`, `largeKnownNotificationsAreBoundedByBytesNotOnlyByCount`, `largeNotificationsOfUnknownMethodsAreDroppedAtTheReader`. ### Attack scenarios walked
- *LAN host advertises many `_snapcast-ctrl._tcp` services*: bounded at the queue (32), the name table (32) and the directory (16); no thread or memory growth; each resolution has a 10 s ceiling. Control characters, bidi and huge names are cleaned and cut (64) or refused (> 256). Services at public IPs are refused; the phone's own loopback is allowed by the rule (see S18); `fe80::` with a zone id keeps its scope, the zone is not in the key. TXT records are never read.

- *Hostile preference* (`snapcast_manual_servers`, `snapcast_selected_servers`, the receiver selection set): every line is re-parsed strictly, filtered again (selected servers), capped at 16; a forged `snapcast:` id for an unlisted server opens nothing and is dropped.
- *DNS-rebinding style manual host name*: allowed by design (the user typed it); a name is re-resolved on every attempt on a helper thread, the connection goes to the resolved address, the only payload is the fixed JSON-RPC read (see S24).
- *Connection storms*: page start / `wake` retry only links that are down, at most one attempt at a time per server, no loop; hostile servers that accept and drop are handled by the Group 2 ceiling.
- *Leaks*: NsdManager listener per browse with handle and generation, stop is held until the start is confirmed; the lock is released on every exit; all executors and the socket are closed in `SnapcastSession.close`; `SnapcastHub` holds only the application context.

### Rule by rule (enforced in code and tested)
- **Connect target** (`PcmFeeder.connect`, `SocketFeedConnection.connect`): takes an `InetAddress` and an int, never a string or URI; refuses null, wildcard, multicast, ports outside 1-65535 before anything opens; no name lookup (`new InetSocketAddress(InetAddress, int)`); a failed connect is an `IOException("feed connection failed")` without cause or address, also for runtime failures of the factory. Tests: `itConnectsToTheGivenAddressAndPortOnly`, `theWildcardAndMulticastAddressesAndBadPortsAreRefusedBeforeAnythingIsOpened`, `aFailedConnectThrowsAFixedMessageWithoutTheAddress`, `connectingToAPortNobodyListensOnFailsFastWithoutTheAddress`. The port that `SnapcastStreams.ensure()` returns is either the candidate YAACC itself asked for (4953-4962) or, for an adopted stream, a port that `isAdoptable` has checked against that range; a status can therefore never steer the feed to another host, and at most to one of ten ports of the control peer.
- **Marker**: 8 hex characters from `SecureRandom` in the production constructor, created once and kept by `MarkerStore`, validated strictly on load (`aStoredValueThatIsNoMarkerIsReplaced`, includes `../../etc`), a failing store still gives a marker, not derived from any device identifier. Backup is off (`allowBackup=false`, `data_extraction_rules.xml` excludes `sharedpref` for cloud backup and device transfer), so a marker kept in preferences does not travel to a second phone.
- **Name and URI**: phone name reduced to letters/digits/space/`-`/`_` (32 code points, surrogate-safe), then percent-encoded with unreserved characters only; `a&mode=client` and `+`/`%` stay inside the value (`aNameWithQueryCharactersStaysInsideTheNameValue`, `percentAndPlusAreEncodedToo`, `theHostilePhoneNameNeverReachesTheServerAsAQueryParameter`).
- **Adoption**: only exact own name, tcp, `name` parameter equal, `mode=server`, expected sample format, host `0.0.0.0`, port in own range; anything else with our name is replaced only when no group uses it, else CONFLICT with nothing changed (tests for six shapes, the pipe scheme, the group-in-use case).
- **Removal/restore**: removal only of an id that carries the marker and is tcp, and is not used by any group, with a fresh `getStatus` before the removal in `shutdown()`; leftovers at most 8 per call; a foreign `AddStream` answer id is refused and nothing is recorded or removed; restore only while the group is still on our stream and the previous stream still exists; records are pruned to existing groups (bounded by the 64-group cap). Tests include 60 hostile look-alike streams (nothing removed), pipe stream with our id (kept in shutdown), a group the user moved onto the stream (stream kept), a failed restore (stream kept), re-read before leftover removal.
- **Ports**: YAACC's own range of 10, ports named by any stream URI excluded, only error -32603 moves to the next port, any other error stops (`atMostTenPortsAreTried...`, `whenEveryPortOfTheRangeIsNamedNothingIsAdded`).
- **Feeder resources**: 2 daemon threads per feeder (writer, watchdog), ring of at most 8 chunks (chunk at most 100 ms, so at most about 150 KB at the extreme config, 15 KB at the default), `write` waits at most `writeWaitMillis` (200 ms default, 10 s max) and drops-and-counts, send buffer at most 16 chunks and `TCP_NODELAY` set before connect (tested over a real loopback socket), watchdog closes a socket whose write exceeds 10 s (a closed socket ends the blocked write), `fail`/`close` are idempotent, wake the waiters and interrupt the other thread, a throwing listener is swallowed, `close()` from the listener does not deadlock. The data sent is PCM and zero chunks only: no header, no name, no identifier.
- **Logging/leaks**: none in the package; exceptions carry fixed texts or only an enum kind (`failedResult` uses `getKind()` and the cleaned, 200-character-capped server reason, which is display text).
- **Tap** (`PcmTapAudioProcessor`, `FeedTapChain`): no file, log or network access; buffers are reused and bounded by the player's buffer size; unsupported formats raise `UnhandledAudioFormatException` instead of passing unknown data; muted mode outputs zeros; `onFlush` discards queued audio; `onReset` drops the buffers. Converter: ranges checked with `long` arithmetic, NaN becomes silence, infinity is clamped before the mix (no exception path from untrusted decoder output).
- **Pacer**: arithmetic cannot overflow (`sentBytes` is kept below one second of bytes, at most about 12 MB at the extreme format), tests with a clock at 0, negative and near `Long.MAX_VALUE`.

### Attack scenarios walked
- *Another user's stream id in an AddStream answer*: refused (`REFUSED`), nothing recorded, nothing removed. *Group.SetStream/RemoveStream errors*: typed results, records kept or dropped by the rules above.
- *Stream URIs naming other hosts or ports*: ignored for the feed target; for adoption a foreign host/port/scheme/mode/format means "not ours, not adopted"; for port choice they only remove candidates (worst case NO_FREE_PORT, which the server could cause by refusing anyway).
- *Names that imitate the marker*: need the exact id or the exact `YAACC ... <marker>` shape plus tcp plus no group; the marker is visible to every controller of that server (it is in the stream id), so it identifies, it does not authenticate: whoever forges it can only get his own unused tcp streams removed.
- *64 streams*, *a status that changes between read and removal*: the removal path re-reads once; the remaining window is one round trip (see S30).
- *A status that never lets the idle cleanup finish* (group parked on our stream): the stream stays (by rule), nothing grows; each `removeIfIdle` costs two status reads (see S28).
- *Answers that make YAACC move or remove other controllers' streams*: YAACC moves only the group id its caller passes and restores only while that group is still on our stream; it removes only marker-bearing, unused, tcp streams.
- *The peer is not the snapserver (a LAN host answers the control connection)*: the feeder connects to that peer (the control peer is the rule) on one of ten ports and sends it the phone's audio and nothing else; it is limited by Group 3's selection rules (no feed to a server the user has not picked). See S29 for the confidentiality note.
- *Resource exhaustion, stalled receiver, close paths*: covered above and by `aPeerThatDoesNotReadIsDetectedByTheWatchdog...`, `closeStopsBothThreadsAndTheConnectionAndIsIdempotent`, `closeWakesAProducerThatWaitsForRoom`.

### W1 (a running feed survived "remove server"): fixed
- `SnapcastSession.close()` is guarded by an `AtomicBoolean` (`closing`, compareAndSet), sets `closed`/`online`, calls `fireChanged()` once on the calling thread, then clears the listeners, closes the rpc and shuts the executors down. Second and re-entrant calls (a listener that calls `close()` again) return at once: no double notification, no recursion. `fireChanged` walks a `CopyOnWriteArrayList` and skips a listener that throws. Events of the rpc after `closed` is set return early, so the offline notice cannot be followed by a late "online" one. No lock of the session is held.
- Callers: the only production caller of `close()` is `SnapcastReceivers.Work.run`, always after the receivers' lock is released, and `Work.run` removes the receivers' own listener (`afterClose`) before it closes the link, so `onLinkChanged` (which takes the receivers' lock) is not called by the close: no echo, no lock cycle. `SnapcastReceivers.shutdown()` has no production caller. `closeIdle` still skips retained servers.

- **Parsers under fuzz.** 400 000 mutated frames of eight message types through `SnapcastMessageCodec.decode` (bit flips, 0xFF/0x00 bytes, fixed and broken size fields) and 400 000 mutated or truncated headers through `PcmFormat.parse` and `FlacStreamInfo.parse`: the only exception type that left them was `SnapcastProtocolException` (226 240 accepted, 173 760 refused, none other). No log call exists anywhere in the package (searched), the exception texts are fixed words (the one place that holds server text, the unsupported codec name, is cleaned and cut at 32 characters and only reaches the user as display text).
- **JSON.** Hello/ServerSettings/ClientInfo go through `SnapcastJson.parseObject` (quote-aware depth 32 and 10 000-token pre-scan, lenient forms refused, trailing data refused, `StackOverflowError` handler) on at most 64 KiB; numbers are clamped without `intValue()` (bufferMs 0..10 000, latency -10 000..10 000, volume 0..100), strings cut at 1 KiB then at 128; a failed parse is MALFORMED without a cause. The four public entry points of `SnapcastJson` are the only change to the control package (the diff is the visibility, nothing else).
- **Timestamps and clock.** All micro arithmetic is `long` (`sec * 1_000_000L`), inputs are at most 2^31 s plus an `int` of microseconds, the filter refuses any side beyond 4e15 and a round trip outside 0..500 ms, so sums cannot overflow; `ChunkScheduler` additionally saturates every add/subtract. A 2-million-sample random run of the filter (extreme and random values): no exception, `max|offset|` stayed bounded by the accepted samples (243 ms in that run), 1.86 million samples refused. A 2-million-chunk random run of the scheduler with random `bufferMs`/latency and extreme timestamps: no exception, the 512 chunks / 4 MiB bound never exceeded, the decisions are DROP_LATE or DROP_TOO_FAR_AHEAD for garbage as intended, the -10 s latency case does not drop fresh chunks. The server is the time authority by design: a consistent hostile clock can place chunks anywhere inside the 5 s window and cause audible resyncs, but it cannot make the client play outside that window, queue more than the bound, or overflow; the answer-consistency check (network time not above the client's own round trip + 1 ms), the 16 outstanding requests and the `refersTo` match all hold in the code.
- **Slow drip.** A frame has a deadline of `messageDeadlineMs` from its first byte, and inside a frame the receive timeout is the time left (`ReadTimeout`): a chunk header dripped one byte per 300 ms against a 2 000 ms deadline ended after 2 026 ms with TIMEOUT. Between frames the idle (10 s) and handshake (10 s) limits apply; the stalls inside a frame no longer depend on the 100 ms wake-up of the time-sync timer (W1 of the general review, fixed and tested).
- **Authorization and disclosure.** No `Auth` is sent or settable; Error 401/403 gives the permanent reason UNAUTHORIZED (no retry), an unsupported codec or format is permanent too; the Hello carries a fixed MAC and cleaned fields only; the server's error text reaches the user only as `Loss.getDetail()`, cleaned and cut at 80 characters.
- **Connect target and reconnect.** Nothing from the server is a connect target (no host, port, URI or redirect is parsed anywhere); one connection per object, one reader thread per attempt, 1 s backoff doubling to 30 s, five failures in a row give up (`GAVE_UP`) until `retry()`, a permanent loss gives up at once, the failure count restarts only after a handshaked connection that held for 10 s, so the server can force at most one reconnect per about 11 s; `onLost` once per outage. No reconnect storm is possible beyond that (see S60 for the target vetting that belongs to the caller).
- **Threads and lifecycle.** `close()` closes the socket (ends a blocked read), joins the reader for at most 2 s, shuts down the executors it owns, and nothing is delivered afterwards; a close during a connect, from a listener, or twice is safe by the generation/state checks; the reader catches `Throwable` at the boundary (INTERNAL loss); a listener that throws a `RuntimeException` is skipped, and the counters of chunks/headers are released in `finally` blocks, so even an `Error` in a listener does not leak the bound. Every listener-bound queue is bounded (chunks 256 / 4 MiB with drops counted, settings and offsets latest-wins, headers 8 then PROTOCOL_ERROR, `onLost`/`onGaveUp` by the reconnect rules). The executors and the retry scheduler are daemon threads created lazily.
- **Test hooks.** `awaitTimeSamples`, `awaitFramesRead`, `isReaderRunning`, `parseHeader`, `decodeBody` and the `Frame` constructor are package-private; the injectable `MicroClock`/`RetryScheduler`/`Executor` are constructor arguments, not global switches. `Config` setters can widen the limits but only a caller in code can use them. `SnapcastBinaryRigTest` is skipped without `-Dsnapcast.rig=<host>`; `yaacc/build.gradle` forwards the three rig properties only when they are set.

### Warning
- **W1 [`MediaCodecFlacDecoder.java:122-150` `drain()`; `EngineHost.java:222-246` `loop()`]: a hostile FLAC chunk can pin the engine thread with no bound, and the thread keeps working after Stop.** (a) `drain()` is `while (true)` that ends only on `INFO_TRY_AGAIN_LATER`. When the output limit is exceeded it sets `tooMuch` but keeps draining (and releasing) every further buffer until the codec stops producing; there is no iteration or wall-clock bound, although the class comment says every call is bounded by short timeouts. The input cap is 512 KiB (`MAX_INPUT_BYTES`) and the header's STREAMINFO block sizes are not validated (`FlacStreamInfo` keeps min/max block size unchecked, up to 65 535), so a chunk of tiny constant-subframe frames can decode to orders of magnitude more PCM than it carries (whether a given platform decoder accepts several frames per input buffer is device dependent, the code itself calls this a guess); each output buffer is a binder round trip. The thread runs at `THREAD_PRIORITY_URGENT_AUDIO`. (b) `EngineHost.loop()` runs up to 256 events per round (`handled++ < 256`) without looking at `running`/`abandoned`. Measured with a scratch test (decoder that takes 20 ms per chunk, 700 chunks queued): `stop()` returned after its 2 s join with 110 decodes done, and the thread went on to 256 decodes (5.1 s) after the user had stopped; the same happens after `abandon()` from the watchdog, so a server that queued a few hundred expensive chunks keeps a daemon thread busy after Stop and after the wake lock is gone. (c) The same 256-event round is longer than the 5 s stall limit when each event takes 20 ms (`loopStartedNanos` is set once per round), so a slow-decode flood ends the session as `STALLED`. (d) While the thread is busy the host queue grows to 768 chunks (`CHUNK_LIMIT`) of up to 4 MiB each; it is bounded in count, not bytes, so a stall of the 5 to 7 s watchdog period at Wi-Fi speed holds hundreds of MB on a phone heap (the connection's own 4 MiB budget is released as soon as a chunk is handed to the host queue). *Remediation:* in `drain()`, stop at the first over-limit buffer (release the rest without draining further), add a per-chunk deadline (for example 100 to 200 ms and a maximum buffer count), and on over-limit or deadline close/re-create the codec (`reset()`) and throw `OVERSIZED`/`DECODE_FAILED`; tighten `MAX_INPUT_BYTES` to the raw size of `maxChunkMs` for the stream (or 64 KiB for typical rates). In `EngineHost.loop()` check `running` between events, bound a round by time as well as by count, and refresh `loopStartedNanos` per event; bound the host queue in bytes (sum of queued payload lengths, drop and `onChunkLost` above, for example, 8 MiB). Add a test with a slow decoder that checks that nothing is decoded after `stop()` returns.

### Suggestion
- **S30 [`LocalMediaSessionPlayer.trackFailedAt`]: `index < items.size()` followed by `items.get(index).getTitle()` is a check-then-act on a `CopyOnWriteArrayList` that an OpenHome controller edits from another thread** (delete-all or remove while an error event is delivered). The window is a few instructions, but a lost race throws `IndexOutOfBoundsException` in ExoPlayer's listener on the main thread (app crash), and a `null` entry would throw `NullPointerException` the same way. A size check alone does not help (the list can shrink between the check and the read); wrap the lookup in `try { ... } catch (RuntimeException e) { title = null; }` (the "Track N" fallback then applies) and skip a `null` entry.
- **S31 [skip-loop limit, `TrackFailurePolicy` / `TrackFailurePolicyTest`]: judged acceptable, no bound required.** The loop needs every track to reach `READY` and then fail, in a repeat-all list the user chose to play from a server the user chose; each cycle costs a connection, buffering and an audible start, so a hostile server gets no more traffic or battery than by serving a long valid stream, and the toast rate equals the track rate (Android limits the toasts an app can have queued). If it is ever wanted, the cheap bound is a failure budget of about 10 failures per 60 s regardless of `READY` (STOP when exceeded, one extra timestamp in the policy), which also covers a toast flood when the title is long.
- **S32 [`TrackToastText.title`, `player_track_skipped`]: two cosmetic display points.** (a) Strong right-to-left letters in a title (not control characters, so they are kept) can reorder the neighbouring quote and comma of the fixed sentence; wrap the argument with `BidiFormatter.getInstance().unicodeWrap(shown)` (the isolates are added by the app at display time, after the cleaner). (b) `looksLikeAddress` catches schemes, `content:` and `file:`, not a scheme-less host such as `192.168.1.5/x` or `evil.example/login`; this is plain text in a non-clickable toast and the server can show the same text in the browse list, so it is not a risk, but the "no addresses" rule of the spec is then literally true only for schemes. A host-like pattern check (no regex needed: contains `/` after a `.` and no space) would close it, with the cost of rejecting some honest titles.
- **S33 [`LocalMediaSessionPlayer.stopWhenFree`]: the retry chain is not cancelled in `onDestroy`.** It ends by itself after about 1 s and holds the player until then; after a destroy it still calls `stop()` and, on success, shows the toast "Playback stopped" for a player that is gone. Add a `destroyed` flag (set in `onDestroy`) and return early; no resource risk, tidiness.
- **S34 [informational, unchanged by this diff]: the audio-only safety net for Snapcast is keyed on the type string the server sends.** A video file labelled `audio/*` still reaches the Snapcast player (and an audio file labelled `video/*` is hidden from it); the new picker filter reads the same strings and does not widen this. Same trust model as before: the server controls its own labels, the effect is limited to the user's own receiver choice.
