# Security Review: Issue #307 MusicCast (YXC) support

## Slice 2 — cycle 1 — 2026-11-02
Reviewing: commits 514c345e..94f17156 (device state, event plan, discovery, UDP listener, monitor, row feed and row text, binder wiring).

Threat model: attacker on the same LAN (or a device that is itself hostile or compromised). UDP source addresses can be forged on a home LAN; SSDP announcements, device descriptions and YXC answers are all attacker-controlled; the devices have no authentication. Impact considered: crash, hang or starvation of the app, false status display, traffic amplification, data exposure.

Checked and found sound (no finding):
- Manifest: not touched in the range; no new permission, no new exported component. `usesCleartextTraffic` was already true app-wide; plain http to LAN devices is inherent to the protocol.
- Description fetch: scheme must be http, host required, no user-info, redirects off, 3 s connect / 5 s read timeouts, body capped at 768 KB and 256K chars (YxcHttpDescriptionFetcher.java:73-83, 45-67). The control endpoint host is always the host of the registry URL; the host a document names is only used to take over the port when it is the same host (YxcDiscovery.java:118), so a document cannot redirect control calls to a third party. Control path from the document must match a plain-path pattern with no `..` and no `//` (YxcDescriptionParser.java:62, 238).
- XML: a document containing `<!DOCTYPE` or `<!ENTITY` (case-insensitive) is refused before parsing, `FEATURE_PROCESS_DOCDECL` is off, so no entity or external resource can be declared; depth 32, value length 256 and total size capped. Malformed XML returns "not a YXC device".
- Discovery cache: bounded (MAX_ENTRIES 256, and in practice at most the 64 watched UDNs); a failed look is retried only every 2 minutes; the network call is made outside the lock.
- Transport: host validated by pattern (IPv4/hostname/IPv6 literal), port range checked, path validated and `..` refused, `Proxy.NO_PROXY`, redirects off, response bounded at 1 MB, status checked. `X-AppPort` is the real local port of the event socket (`source.getPort()`, YxcMonitor.java:414) and `X-AppName` is a constant; nothing sensitive goes to the device.
- Event trust: datagram is acted upon only when `active`, parsable, the source address equals the host of a device our own discovery accepted, and the `device_id` matches when both sides have one (YxcMonitor.java:292-334). Mismatches fail closed (also for textual IPv6 differences).
- Event source lifetime: opened only on subscribe, closed 30 s after the last unsubscribe, poll cancelled with it, stale generations dropped (YxcMonitor.java:249-273).
- Refresh storms: debounce coalesces flag events per device, reads are serialized per device by `reading`/`pending` (one read loop per device), so a storm gives at most one read round (3 calls) per ~500 ms per device plus the read duration; nothing is queued per event.
- Logging: YaaccLogger calls log only fixed texts, exception classes and "call: HTTP status / response_code N"; YxcException deliberately leaves the body out, `YxcDeviceState.toString` leaves names and tracks out. No secrets, tokens or PII found in logs.
- UI: device strings go to `TextView.setText` as plain text (no Html/Linkify, no autoLink in the layout), and into `getString(..., %1$s)` as an argument, not as the format string, so there is no format-string injection and nothing is executed. The text view is limited to 2 lines with ellipsis.
- No dependency or build file changed in the range.

### Critical
- [yaacc/src/main/java/de/yaacc/yxc/YxcClient.java:187 (with YxcMonitor.java:359-361)] **Remote crash of the app by a hostile device: no nesting-depth bound on the JSON answers, and a StackOverflowError is not caught.** Since slice 2 the monitor automatically calls `getZoneStatus` / `getDistributionInfo` / `getPlayInfo` on every LAN device whose description contains an `X_yxcControlURL` (trivial for an attacker to fake via SSDP) whenever the receiver tab or sheet is open. `YxcClient.answer` hands up to 1 MB of the answer to `new JSONObject(text)` (MAX_BODY_BYTES in the transport). A body such as `{"a":[[[[ ...` repeated 500 000 times recurses in the parser; Android's libcore `org.json` has no depth limit (the json-java 20250517 used by the unit tests stops at 512 levels with a JSONException, which is why tests do not show it). `StackOverflowError` is an Error: `answer` catches only `JSONException | NullPointerException`, `readLoop` catches only `RuntimeException` (YxcMonitor.java:359), so it leaves the worker thread. On Android an uncaught throwable on any thread goes to the default handler and terminates the process (a crash dialog for every attacker packet); in addition `device.reading` would stay true. The event parser has a depth guard for exactly this reason; the HTTP answer path, which takes far larger input from an equally untrusted peer, has none.
  Remediation: apply the same bound to every JSON text that comes from a device. Move the depth check to a shared helper used by `YxcClient.answer` (and by `YxcEventParser`), make it robust as described in the first Warning, and additionally catch `StackOverflowError` around `new JSONObject(...)` in `answer` and `new JSONObject(...)` in `YxcEventParser.parse` (converting to `YxcException.malformed` / `unparsable()`), and in `readLoop` make the `reading = false` / `client = null` reset a `finally`-style path so no throwable leaves the flag set. Add a test with an answer of 100 000 nested brackets that expects a `YxcException`, not an Error.

### Warning
- [yaacc/src/main/java/de/yaacc/yxc/YxcEventParser.java:128-150, 65 and YxcEventListener.java:83] **The datagram depth guard can be bypassed, and the parse runs before the trust check.** `nestingDepth` treats only `"` as a string delimiter, but `org.json` also accepts `'`-quoted strings. A payload like `{'a':'"','b':[[[[ ... ]]]],'c':'"'}` makes the guard enter "string" state at the `"` inside the single-quoted string and skip every bracket up to the next `"`; verified with json-java 20250517: the guard reports depth 1 while the parser accepts 100 levels (the same text with ~4000 levels fits a 4096-byte datagram). With Android's unlimited recursion this is the same StackOverflowError path as the Critical item, on the `yxc-events` thread, which only catches RuntimeException. Because `parser.parse(...)` is called in the listener before `receiver.onEvent` checks the source address (YxcEventListener.java:83), any host that can reach the UDP port (a port scan of the ephemeral range on the LAN is enough, no address forging needed) can feed it, not only a forged device address.
  Mitigation: (a) count `{`/`[` outside of both quote styles, or simply reject a datagram whose total number of `{` and `[` characters (ignoring quoting) exceeds a small bound such as 64, which no real event approaches; (b) catch `StackOverflowError` as in the Critical item; (c) cheap pre-filter in `YxcEventListener.run`: ask the receiver whether the source address belongs to a watched device (for example a `boolean accepts(InetAddress)` on the receiver) before parsing, so unknown senders cost one hash lookup, not a parse.
- [yaacc/src/main/java/de/yaacc/yxc/YxcHttpDescriptionFetcher.java:52-67, YxcHttpTransport.java:145-146, YxcMonitor.java:149] **No overall deadline on a read; four threads serve all devices, so four slow peers can block the feature.** The 5 s read timeout is per `read()` call, not per response. A hostile "device" that sends one byte every 4 s keeps a description fetch (up to 768 KB) or a YXC answer (up to 1 MB) open for days. All reads and discoveries run on `Executors.newFixedThreadPool(4)`. Four such devices (the cap is 64 watched UDNs, all of them could be fake SSDP announcements) occupy all four threads; the real devices are then never read or discovered until the process restarts, while `reading` stays true for them. This is a LAN-adjacent availability attack on the feature (not on playback, which uses other threads).
  Mitigation: enforce a total time budget per exchange (check `System.nanoTime()` in the read loops of both classes and abort after, say, 10 s for a description and 15 s for a YXC answer; `disconnect()` from a watchdog also works), and bound a single device's share of the pool (for example at most one read in flight per device, which exists, plus a pool queue/limit so a stuck device cannot take every thread, or a per-read watchdog that closes the connection).
- [yaacc/src/main/java/de/yaacc/yxc/YxcMonitor.java:302-305 and yaacc/src/main/java/de/yaacc/browser/YxcRowFeed.java:67-73] **Every state change posts to the main thread; no coalescing, and the notification fires also for fields the row does not show.** `onEvent` fires a notification whenever the state differs, including volume and mute, which are not part of the row text; `YxcRowFeed.onStateChanged` posts one `Runnable` (and one `notifyItemChanged`) per notification. A sender that forges the device's source address (possible on a normal home LAN; `device_id` is optional in the check and is anyway derivable from the public UDN) and alternates `volume` values can drive the main looper at the datagram rate while a receiver screen is open, causing jank and ANR. Legitimate devices also generate many volume events while the user drags a slider.
  Mitigation: notify only when something the row renders changed (power, input/input text, reachability, group role/name, client count), and coalesce posts in `YxcRowFeed` (one pending post per UDN, for example a `Set<String> pending` guarded by the handler thread, or `removeCallbacks` / `postDelayed` 100-250 ms). Also see the Suggestion on a minimum interval between event-triggered reads.

### Suggestion
- [yaacc/src/main/java/de/yaacc/yxc/YxcMonitor.java:164-197, 184] The `watched` map has no eviction and counts every UPnP device the registry shows (also those that turn out not to speak the protocol). 64 forged SSDP announcements (devices that Cling later expires) fill it for the rest of the process lifetime, and real MusicCast devices that appear afterwards are silently never watched. Remove entries that are no longer in the subscribed set when `subscribe` is called by the screen (the screen passes the complete current list), and/or count only devices with an endpoint toward the cap.
- [yaacc/src/main/java/de/yaacc/yxc/YxcMonitor.java:315 and 336-342] Add a per-device minimum interval between event-triggered reads (for example 2 s) so a flag-event stream cannot make yaacc query a device about every 0.5 s indefinitely (amplification onto a small device); and create the scheduler with `setRemoveOnCancelPolicy(true)` so canceled debounce tasks do not sit in the queue until their delay passes (at a high event rate that is rate x 0.5 s objects).
- [yaacc/src/main/java/de/yaacc/yxc/YxcEventListener.java:48] The event socket is bound to the wildcard address. Binding it to the address of the Wi-Fi interface the devices are on (or at least not accepting from other interfaces) removes exposure on VPN or other interfaces; keep the source-address trust check as is.
- [yaacc/src/main/java/de/yaacc/browser/YxcRowText.java:80-104 and YxcDeviceState.java:111] Device-supplied strings (group name, input text, and an `input` id that an event can deliver with up to 16K characters) are shown without sanitising. Strip control and format characters (bidirectional overrides U+202A-202E, U+2066-2069, zero-width characters, newlines) and cap the length (for example 64-128 chars) before they reach the TextView, so a hostile or compromised device cannot spoof the row text (reversed text, text that looks like another state) or make the layout work on very long strings. `YxcDescriptionParser.clean` already does this for description values; reuse it.
- [yaacc/src/main/java/de/yaacc/yxc/YxcHttpDescriptionFetcher.java:43] The description fetch does not use `Proxy.NO_PROXY`, unlike `YxcHttpTransport`. On a device with a global HTTP proxy the LAN request would go to the proxy (information leak of LAN addresses, and a request to a LAN URL made by the proxy). Use `url.openConnection(Proxy.NO_PROXY)` for consistency.
- [yaacc/src/main/java/de/yaacc/yxc/YxcDiscovery.java:100-119] The description host is whatever the SSDP announcement named (Cling already fetches it, so this is not new reach), but every 2 minutes a failing entry is fetched again, and a literal loopback / non-private address would be a GET target. Optionally refuse literal addresses that are not site-local, link-local or unique-local, and ignore `localhost`.
- [yaacc/src/main/java/de/yaacc/yxc/YxcMonitor.java:302-305] Events set power, volume, mute and input directly in the shown state, trusting only the forgeable source address. This is acceptable now, because the state is display-only and the 30 s poll corrects it, but no later slice should take a control decision (for example sending a group command) from event-derived state without reading it from the device first. Record that as a rule in design.md for slices 3 and 4.
- Informational: after the event socket closes, a device keeps the registration for roughly its timeout and keeps pushing datagrams to that port; if Android reuses the ephemeral port for another app, that app could receive the device's status events (power, volume, input; no secrets). Nothing to do beyond keeping the 30 s close delay short.

### Verdict: FAIL

## Slice 2 — cycle 1 follow-up (fixes by the orchestrator)
- Critical, unbounded JSON nesting in `YxcClient`: fixed with `YxcJson.parseObject` (quote-agnostic bracket depth, max 32 for answers, 16 for events; `StackOverflowError` turned into `JSONException`); `readLoop` also catches `StackOverflowError`. Tests: `YxcClientTest.anAnswerNestedTooDeeplyIsAMalformedAnswerNotACrash`, `YxcEventParserTest` (single-quote bypass, huge nesting).
- Warning, guard bypass and parsing before trust: guard is quote-agnostic now; `YxcEventSource.Receiver.accepts(address)` is asked before a datagram is parsed (monitor: only watched addresses while active). Tests: `YxcEventListenerTest.datagramsFromAddressesThatDoNotMatterAreNotParsed`, `YxcMonitorTest.onlyTheAddressesOfWatchedDevicesAreAskedFor`.
- Warning, no total deadline: 15 s per body in `YxcHttpTransport.readBounded` and `YxcHttpDescriptionFetcher` (the fetch also uses `Proxy.NO_PROXY` now). Test: `YxcHttpTransportTest.aBodyThatTakesTooLongIsRefused`.
- Warning, main-thread storm: listeners are told only when the row's content changes (`YxcDeviceState.sameForRow`; volume and mute only update the stored state), and `YxcRowFeed` coalesces posts per drain. Tests: `aVolumeChangeAloneDoesNotWakeTheListeners`, `aPowerChangeWakesTheListeners`.
- Suggestions taken: cleaned and capped names in the row (`YxcRowText.clean`), `setRemoveOnCancelPolicy(true)`, `Proxy.NO_PROXY`, trust rule noted in design.md.
- Suggestions left open: eviction of `watched` entries that are not devices of this kind, binding the socket to the Wi-Fi interface, private-address-only discovery, minimum interval between event-triggered reads (debounce is the limit), port reuse after close (device registration expires by itself).

### Warning
- [yaacc/src/main/java/de/yaacc/yxc/YxcHttpDescriptionFetcher.java:53-56 and YxcHttpTransport.java:141-148] **The 15 s deadline does not cover the response headers, so a slow-drip peer still holds a worker thread (cycle 1 Warning "no overall deadline" only partly closed).** The deadline starts after `getResponseCode()` returned (fetcher) / after `getResponseCode()` (transport), and is only checked between body reads. A hostile "device" can send the status line and then one header line every 2-4 s; each read is within the 5 s read timeout, so `getResponseCode()` never returns. Reproduced on the JVM with `HttpURLConnection` (connect 3 s, read 5 s): `getResponseCode()` was still blocked after 60 s, only because the test server stopped; Android's OkHttp-based connection has the same per-read timeout and a header limit of 256 KiB, i.e. effectively unbounded. Four such devices (watched cap 64, fakes via SSDP) block the 4-thread pool as before.
  Mitigation: make the deadline cover the whole exchange, not only the body: arm a watchdog when the request starts (a shared daemon `ScheduledExecutorService`: `schedule(connection::disconnect, 15 s)`, cancelled in `finally`), which interrupts a blocked `getResponseCode()`/`read()` on Android and on the JVM; keep the in-loop check as well. Test with a server that drips headers.

### Suggestion
- [yaacc/src/main/java/de/yaacc/yxc/YxcJson.java:75-87] `bracketDepth` is still bypassable: it counts a `]`/`}` inside a string as a closer. Verified with json-java 20250517: `{"a":[`x30 `"` `]`x30 `",` repeated 12 times gives guard depth 31 while the parser accepts real depth 360 (with a 1 MB answer the real depth can be ~480,000). The guard is therefore no longer what protects; the `StackOverflowError` catch in `parseObject` is. That is acceptable on ART (a stack overflow on a Java thread is a catchable Error), but do not rely on one mechanism: make the guard a real tokenizer-aware scan (track both quote kinds and escape), or count the raw number of opening brackets in the text and refuse above a bound (events: 64; answers: size-proportional, e.g. 20,000), or parse with a depth-limited parser. Add a test that nests with closers inside strings.
- Open suggestions from cycle 1 left by the orchestrator (all accepted as such): eviction of `watched` (YxcMonitor.java:184), wildcard bind of the event socket (YxcEventListener.java:48), private-address-only discovery, minimum interval between event-triggered reads, port reuse after close. None gets worse with 146b214f.
- Newly introduced: nothing found. `accepts` is cheap (one hash-free loop over at most 64 devices and one address string per datagram) and exceptions from it are caught by the existing `RuntimeException` handler; the new `sameForRow` leaves `clientCount` out, which the row does not show.

### Suggestion
- [yaacc/src/main/java/de/yaacc/yxc/YxcJson.java:75-96] The quote-aware depth guard is still not equivalent to the tokenizer of `org.json`, so it can be bypassed; the `StackOverflowError` catch in `parseObject` (YxcJson.java:57-62) remains the real protection and is sufficient on ART. Verified bypass with json-java 20250517: `{"a":[x',` + `[`x300 + `]`x300 + `,y']}` gives guard depth 2 and the parser accepts real depth 300. Cause: an unquoted literal may contain a quote character (`x'`), which the scan reads as the start of a string and so hides the brackets that follow until the next `'`. Android's libcore tokenizer reads literals up to `{}[]/\:,=;# \t\f`, so the same form works there; it also skips `#`, `//` and `/* */` comments, which the scan does not understand (not reproducible with json-java, which rejected my comment variants; not verified on Android). The guard can not be made exact without reimplementing the tokenizer. Options: keep the guard as a cheap first filter and document it as such (the comment in the code already says the handler is the last line of defense), and add a test that makes a stack overflow happen (a deep answer built with the bypass above, on a thread with a small stack) so the catch is exercised, not only the guard. Do not remove the catch.
- [yaacc/src/main/java/de/yaacc/yxc/YxcWatchdog.java:50 and the callers] Edge case: the watchdog is armed before the name of the host is resolved. `disconnect()` on a connection that is not connected yet does nothing, so if a host name (the host pattern allows names, not only addresses) takes longer than 15 s to resolve (a slow resolver controlled by the peer's domain), the one-shot watchdog fires early and the headers phase then runs without a limit. Fix by re-arming (`scheduleWithFixedDelay`, 1 s, until cancelled) or by arming after `connect()`; low risk because most hosts are IP literals from the SSDP source.
- Open suggestions from earlier cycles are unchanged (eviction of `watched`, wildcard bind, private-address-only discovery, minimum interval between event-triggered reads, port reuse after close).
- Newly introduced: nothing else found. The watchdog thread is a single daemon with trivial tasks; a `disconnect()` that blocked would delay other deadlines, which no JDK or Android implementation does.

### Verdict: PASS
