# Capture tools for issue #307 (read-only)

These scripts record what a device that speaks the YXC API answers, for the test fixtures (task "Capture answers" in tasks.md). They only read; nothing is changed on the device.

1. `./capture.sh <device-ip> <dir> <label>` - records the read-only answers (device info, features, status of the zones, distribution info, play info, the UPnP description).
   Do it for each device, and for the distribution info also while the device is not linked, linked as server and linked as client (run it again with another label, e.g. `deviceA_server`).
2. `python3 listen_events.py <device-ip> 90 <dir>/deviceA_events.json` - records the pushed UDP events while you operate the device with its own app (volume, input, play / pause, link, unlink). Needs a free UDP port 41100 on your computer and the device in the same network.
3. `python3 scrub.py <dir>` - replaces MAC addresses, IPs, serial numbers, names, SSID, group ids and the free text of play infos, tuner infos and preset lists (artist, album, track, station and service names, radio text, cover art URLs); for a test that needs a readable value write an invented text by hand. Open the files and check them. Only then share them (or put them into `yaacc/src/test/resources/yxc/`).
4. For the volume experiment (does the server's volume reach the linked clients?): link two devices with the app of the manufacturer, change the volume of the server with that app and look at `main/getStatus` of the client (`curl http://<client-ip>/YamahaExtendedControl/v1/main/getStatus`); then do the opposite. Write down what happens.
5. For the group calls (issue #307, slice 3): `./link_test.sh <server-ip> <client-ip> [num ...]` links the client to the server with the same call sequence the app will use, tries the given `num` values of `startDistribution` (default `0 1`; the word `none` leaves `num` out), shows the answers and the group info of both devices, and unlinks again. `ERRORS=1 ./link_test.sh ...` also probes calls a device should refuse. It changes state (link, unlink), needs both devices in no group at the start, and tries to leave them in no group at the end. Start music on the server first and listen whether the client plays in sync. Tested against a simulated pair of devices only.
6. For the net source and tuner experiment (issue #307, slice 5): `./source_test.sh <device-ip> net [preset-number]` (start a net radio station or a streaming source on the device first) and `./source_test.sh <device-ip> tuner [band] [preset-number]` (select the tuner input first) try the playback, repeat, shuffle, preset and tuner seek calls and print the play info before and after. It changes what plays on that one device (and puts repeat and shuffle back), nothing else. Run `./capture.sh` as well while the station / the tuner plays: it now also records the preset lists. Check the output for station names and track titles before you send it.
